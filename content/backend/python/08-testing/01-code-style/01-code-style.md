## Теория
Код читают намного чаще, чем пишут: на ревью, при поиске бага, через полгода, когда нужно добавить скидку. Если каждый в команде пишет по-своему — где-то `CalcTotal`, где-то `calc_total`, отступы по 2 и по 4 пробела, — читатель тратит внимание на форму вместо смысла. Поэтому в Python есть общее соглашение о стиле — **PEP 8**. Его соблюдают почти все проекты и библиотеки, и код любого из них выглядит знакомо.

Главное из PEP 8:
- **имена:** переменные и функции — `snake_case` (`calc_total`), классы — `CapWords` (`OrderItem`), константы — `UPPER_CASE` (`MAX_ITEMS`); имя говорит, что лежит внутри, а не как устроено (`total`, а не `tmp2`);
- **отступы** — 4 пробела; **пробелы** вокруг `=` и операторов (`total = price * qty`), после запятой; без пробелов вокруг `=` в именованных аргументах (`discount=None`) и перед двоеточием;
- **пустые строки:** две между функциями и классами верхнего уровня, одна — между методами;
- **импорты** — в начале файла: стандартная библиотека, потом сторонние пакеты, потом свои модули;
- **сравнение с `None`** — через `is` / `is not`, а не `==`; с `True`/`False` не сравнивают вовсе (`if is_paid:`).

Следить за этим руками никто не хочет, для этого есть инструменты двух видов:
- **форматтер** сам переписывает файл: расставляет пробелы, пустые строки, переносит длинные строки. Самые известные — **Black** и **ruff format** (форматирует так же, как Black). Спорить о пробелах на ревью больше не нужно: как отформатировал инструмент, так и правильно;
- **линтер** ничего не меняет, а находит проблемы и сообщает о них: неиспользуемый импорт, переменная, которую не читают, `== None`, нарушения PEP 8. Известные — **flake8** и **ruff check**.

Обычно в проекте настроены оба, а их проверка запускается автоматически перед каждым коммитом и на сервере CI: код, который не прошёл линтер, не попадает в основную ветку. Устанавливают их через `pip` (курс «Терминал и Git»), в тренажёре сайта их нет — в задачах этой темы вы исправляете код по правилам сами.

## Наглядно
**Таблица 1.** Имена по PEP 8.

| Что | Стиль | Пример |
|---|---|---|
| Переменная, функция, метод, модуль | `snake_case` | `order_total`, `calc_total()`, `cart.py` |
| Класс, исключение | `CapWords` | `OrderItem`, `OutOfStockError` |
| Константа модуля | `UPPER_CASE` | `MAX_ITEMS`, `FREE_DELIVERY_FROM` |
| «Внутреннее» имя | `_` в начале | `_reserve()`, `self._items` |

**Таблица 2.** Форматтер и линтер.

| | Форматтер (ruff format, Black) | Линтер (flake8, ruff check) |
|---|---|---|
| Что делает | переписывает файл | сообщает о проблемах |
| Пробелы, отступы, пустые строки | исправляет сам | сообщает (`E225`, `E302`) |
| Неиспользуемый импорт, лишняя переменная | не трогает | находит (`F401`, `F841`) |
| `== None` | не трогает | находит (`E711`) |
| Плохие имена (`CalcTotal`, `tmp2`) | не трогает | по умолчанию не видит — это ревью |

## На практике
Задача: функцию расчёта суммы корзины написали наспех. Привести её к стилю PEP 8 с помощью инструментов и руками.

### Шаг 1. Исходный код
Функция работает, но читать её тяжело:

Файл `cart.py`:
```python
import os
from decimal import Decimal
def CalcTotal(items,Discount = None):
    Total=Decimal("0")
    for item in items :
        Total+=item["price"]*item["qty"]
    if Discount == None:
        return Total
    result = Total
    return Total-Total*Discount/100
```

### Шаг 2. Линтер
Запускаем flake8 (7.4.1) на файле:
```bash
flake8 cart.py
```
Результат:
```
cart.py:1:1: F401 'os' imported but unused
cart.py:3:1: E302 expected 2 blank lines, found 0
cart.py:3:20: E231 missing whitespace after ','
cart.py:3:29: E251 unexpected spaces around keyword / parameter equals
cart.py:3:31: E251 unexpected spaces around keyword / parameter equals
cart.py:4:10: E225 missing whitespace around operator
cart.py:5:22: E203 whitespace before ':'
cart.py:6:14: E225 missing whitespace around operator
cart.py:7:17: E711 comparison to None should be 'if cond is None:'
cart.py:9:5: F841 local variable 'result' is assigned to but never used
```
Каждая строка — файл, строка, столбец, код правила и описание. Коды на `E` — нарушения PEP 8 (pycodestyle), на `F` — вероятные ошибки в логике (pyflakes).

### Шаг 3. Форматтер
Форматтер исправит всё, что касается пробелов и пустых строк, а линтер покажет, что осталось:
```bash
ruff format cart.py
flake8 cart.py
```
Результат:
```
1 file reformatted
cart.py:1:1: F401 'os' imported but unused
cart.py:9:17: E711 comparison to None should be 'if cond is None:'
cart.py:11:5: F841 local variable 'result' is assigned to but never used
```
Остались проблемы смысла: форматтер не удаляет код и не меняет сравнения — это решает человек.

### Шаг 4. Руками
Удаляем лишний импорт и переменную, меняем `== None` на `is None` и переименовываем по PEP 8. Имена линтер не проверял — `CalcTotal` и `Total` нашли бы только на ревью:

Файл `cart.py`:
```python
from decimal import Decimal


def calc_total(items, discount=None):
    total = Decimal("0")
    for item in items:
        total += item["price"] * item["qty"]
    if discount is None:
        return total
    return total - total * discount / 100
```
Проверяем ещё раз:
```bash
flake8 cart.py
ruff format --check cart.py
```
Результат:
```
1 file already formatted
```
flake8 молчит — замечаний нет. `--check` не меняет файл, а только проверяет: так форматтер запускают в CI.

## Частые ошибки
- **`== None` вместо `is None`.** Работает почти всегда, но класс может переопределить `==`, а `None` — единственный объект, и проверять его надо на тождество.
- **Неиспользуемые импорты и переменные.** Не мешают работе, но путают читателя («зачем тут `os`?») и иногда скрывают баг: значение посчитали в `result`, а вернули другое.
- **Имена без смысла и в чужом стиле.** `CalcTotal` выглядит как класс, `d` и `tmp2` ничего не говорят. Линтер этого не заметит.
- **Спорить о пробелах на ревью.** Форматтер решает это раз и навсегда; на ревью обсуждают логику.
- **Отформатировать весь старый проект одним коммитом вместе с изменениями.** В diff смешаются тысячи строк форматирования и одна настоящая правка — форматирование выносят в отдельный коммит.

## Итог
**PEP 8**
- Имена: `snake_case` — переменные и функции, `CapWords` — классы, `UPPER_CASE` — константы.
- 4 пробела, пробелы вокруг операторов, две пустые строки между функциями.
- Сравнение с `None` — `is` / `is not`.

**Инструменты**
- Форматтер (ruff format, Black) переписывает форму кода.
- Линтер (flake8, ruff check) сообщает о проблемах: `E` — стиль, `F` — вероятные ошибки.
- Имена и смысл проверяет человек на ревью.

**В команде**
- Форматтер и линтер настроены в проекте и запускаются автоматически: перед коммитом и в CI.

## Вопросы на собеседовании
<details><summary>Что такое PEP 8 и зачем его соблюдать?</summary>

Соглашение о стиле кода Python: имена, отступы, пробелы, длина строк, порядок импортов. Код в едином стиле читается быстрее, а diff показывает только настоящие изменения. Большинство проектов следуют PEP 8 и проверяют его автоматически.
</details>

<details><summary>Чем форматтер отличается от линтера?</summary>

Форматтер (Black, ruff format) переписывает файл в единый вид и не меняет поведения кода. Линтер (flake8, ruff check) только анализирует код и сообщает о проблемах: нарушениях стиля, неиспользуемых импортах и переменных, подозрительных конструкциях. В проекте обычно используют оба.
</details>

<details><summary>Почему с `None` сравнивают через `is`?</summary>

`None` существует в одном экземпляре, и `is` проверяет, что это тот самый объект. `==` вызывает метод `__eq__`, который класс может переопределить как угодно, — сравнение может дать неожиданный результат. Кроме того, `is` чуть быстрее и так принято в PEP 8.
</details>

<details><summary>Как в команде добиваются единого стиля?</summary>

Настраивают форматтер и линтер в конфигурации проекта (`pyproject.toml`), запускают их автоматически перед коммитом (pre-commit) и в CI. Код, который не прошёл проверки, не сливают в основную ветку. Тогда стиль не зависит от дисциплины людей.
</details>
