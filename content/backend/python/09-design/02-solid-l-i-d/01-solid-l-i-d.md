## Теория
Прошлая тема разделила код на части. Эта — о том, как части **договариваются** между собой: что наследник обещает вместо родителя, сколько методов требовать от класса и от чего должен зависеть сервис.

**L — подстановка Лисков.** Если код работает с объектом родителя, он должен так же работать с любым наследником — без проверок `isinstance` и без сюрпризов. Наследник может делать больше, но не может:
- выбрасывать ошибку там, где родитель работал (`NotImplementedError` в «ненужном» методе);
- требовать больше на входе (родитель принимал любую сумму, наследник — только до 10 000);
- обещать меньше на выходе (родитель возвращал `Decimal`, наследник — строку или `None`).

Классический пример с собеседований: квадрат — это прямоугольник в геометрии, но `Square(Rectangle)` ломает код, который меняет ширину и ждёт, что высота останется прежней.

**I — разделение интерфейса.** Не заставляйте класс реализовывать методы, которые ему не нужны. Абстрактный `Notifier` с `send_email`, `send_sms` и `send_push` вынуждает Telegram-бота писать заглушки для почты и SMS. Заглушка с `raise NotImplementedError` — сразу и нарушение L. Лучше несколько узких интерфейсов (или один общий метод `send(text)`), а класс берёт только те, что умеет.

**D — инверсия зависимостей.** Сервис верхнего уровня (оформление заказа) не должен зависеть от деталей нижнего (SMTP-клиент, конкретный банк). Оба зависят от **абстракции**: «нечто, что умеет `send(text)`». В Python абстракцию записывают через `Protocol` (тема 7.08) или `ABC` (тема 7.09). Тогда смена почты на Telegram не трогает сервис, а в тесте вместо банка подставляется заглушка.

**Таблица 1.** Похожие принципы, которые путают.

| | О чём | Вопрос |
|---|---|---|
| S | обязанности класса | сколько причин его менять? |
| I | интерфейс, который навязывают классу | все ли методы ему нужны? |
| L | наследник вместо родителя | сломается ли код, если подставить наследника? |
| D (принцип) | от чего зависит код | от абстракции или от конкретного класса? |
| DI (приём) | как зависимость попадает в объект | передаётся снаружи, а не создаётся внутри |

| Принцип | Признак в коде |
|---|---|

## На практике
Задача: посчитать вес корзины для доставки, разослать уведомления по разным каналам и сделать сервис заказа независимым от канала.

### Шаг 1. Наследник ломает общий код
Электронная книга — товар, но веса у неё нет, и наследник «честно» сообщает об этом исключением:
```python
from decimal import Decimal


class Product:
    def __init__(self, name, kg):
        self.name = name
        self.kg = kg

    def weight(self):
        return self.kg


class DigitalProduct(Product):
    def __init__(self, name):
        super().__init__(name, None)

    def weight(self):
        raise NotImplementedError("у цифрового товара нет веса")


def cart_weight(products):
    return sum(p.weight() for p in products)


cart = [Product("Чайник", Decimal("1.2")), DigitalProduct("Книга")]
print(cart_weight(cart))
```
Результат:
```
Traceback (most recent call last):
  File "main.py", line 26, in <module>
    print(cart_weight(cart))
          ^^^^^^^^^^^^^^^^^
  File "main.py", line 22, in cart_weight
    return sum(p.weight() for p in products)
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "main.py", line 22, in <genexpr>
    return sum(p.weight() for p in products)
               ^^^^^^^^^^
  File "main.py", line 18, in weight
    raise NotImplementedError("у цифрового товара нет веса")
NotImplementedError: у цифрового товара нет веса
```
`cart_weight` написана для любого `Product` — и упала на наследнике. Чинить её через `if isinstance(p, DigitalProduct)` — значит каждый общий код учить про каждого наследника.

### Шаг 2. Наследник держит обещание родителя
Обещание `weight()` — «вес для доставки в кг». Для цифрового товара честный ответ — ноль:
```python
class DigitalProduct(Product):
    def __init__(self, name):
        super().__init__(name, Decimal("0"))


cart = [Product("Чайник", Decimal("1.2")), DigitalProduct("Книга")]
print(cart_weight(cart))
```
Результат:
```
1.2
```
Общий код не изменился и работает с любым наследником. Если «нулевой вес» не подходит по смыслу (например, цифровой товар вообще нельзя класть в посылку), значит, наследование неверно: такой товар — не разновидность физического, и нужны разные классы.

### Шаг 3. Толстый интерфейс
Абстрактный уведомитель требует сразу три канала. Telegram-боту нужен только один, но реализовать приходится все:
```python
from abc import ABC, abstractmethod


class Notifier(ABC):
    @abstractmethod
    def send_email(self, text): ...

    @abstractmethod
    def send_sms(self, text): ...

    @abstractmethod
    def send_push(self, text): ...


class TelegramNotifier(Notifier):
    def send_email(self, text):
        raise NotImplementedError

    def send_sms(self, text):
        raise NotImplementedError

    def send_push(self, text):
        print("telegram:", text)


TelegramNotifier().send_push("Заказ №1042 оплачен")
TelegramNotifier().send_sms("Заказ №1042 оплачен")
```
Результат:
```
telegram: Заказ №1042 оплачен
Traceback (most recent call last):
  File "main.py", line 27, in <module>
    TelegramNotifier().send_sms("Заказ №1042 оплачен")
  File "main.py", line 20, in send_sms
    raise NotImplementedError
NotImplementedError
```
Две заглушки из трёх методов, и каждая — ловушка для кода, который «по интерфейсу» имеет право её вызвать.

### Шаг 4. Узкий интерфейс
Сервису не важно, каким каналом уйдёт сообщение, — ему нужно «отправить текст». Это и есть интерфейс:
```python
from typing import Protocol


class Notifier(Protocol):
    def send(self, text): ...


class EmailNotifier:
    def __init__(self, email):
        self.email = email

    def send(self, text):
        print(f"email {self.email}:", text)


class TelegramNotifier:
    def __init__(self, chat_id):
        self.chat_id = chat_id

    def send(self, text):
        print(f"telegram {self.chat_id}:", text)


for channel in [EmailNotifier("anna@example.com"), TelegramNotifier(5513)]:
    channel.send("Заказ №1042 оплачен")
```
Результат:
```
email anna@example.com: Заказ №1042 оплачен
telegram 5513: Заказ №1042 оплачен
```
Каждый класс реализует ровно то, что умеет. Адрес и чат — данные конкретного канала, они в `__init__`, а не в интерфейсе.

### Шаг 5. Сервис зависит от абстракции
`OrderService` знает только про `Notifier` — «что-то с методом `send`». Какой канал — решают снаружи:
```python
class OrderService:
    def __init__(self, notifier: Notifier):
        self.notifier = notifier

    def pay(self, order_id, total):
        self.notifier.send(f"Заказ №{order_id} оплачен: {total} ₽")


class FakeNotifier:
    def __init__(self):
        self.sent = []

    def send(self, text):
        self.sent.append(text)


OrderService(TelegramNotifier(5513)).pay(1042, Decimal("2998.00"))
fake = FakeNotifier()
OrderService(fake).pay(1043, Decimal("490.00"))
print(fake.sent)
```
Результат:
```
telegram 5513: Заказ №1042 оплачен: 2998.00 ₽
['Заказ №1043 оплачен: 490.00 ₽']
```
Зависимость «перевернулась»: не сервис подстраивается под SMTP-клиент, а каналы подстраиваются под интерфейс, который нужен сервису. В модуле сервиса нет ни одного `import` конкретного канала.

## Частые ошибки
- **`NotImplementedError` в наследнике.** Родитель обещал метод — наследник его отменил. Это нарушение L: общий код падает. Либо наследник выполняет обещание, либо наследование неверно.
- **`isinstance` по наследнику в общем коде.** `if isinstance(p, DigitalProduct): …` — признак, что подстановка не работает. Различия — в методах наследников.
- **Один абстрактный класс «на всё».** `Notifier` с десятью методами для всех каналов. Делите на узкие интерфейсы по тому, что нужно вызывающему коду.
- **Путать D и DI.** Принцип D — «зависеть от абстракции». Внедрение зависимостей — способ это сделать: передать объект снаружи. Можно передавать снаружи конкретный `SmtpClient` с аннотацией `SmtpClient` — это DI, но не D.
- **Абстракция под одну реализацию «на будущее».** `Protocol` ради единственного класса, который никогда не заменят, — лишний слой. Абстракция окупается, когда реализаций две и больше (заглушка в тестах — тоже реализация).

## Итог
**L**
- Наследник работает везде, где родитель: не выбрасывает новых ошибок, не сужает вход, не меняет тип результата.
- Не получается — значит, наследование неверно.

**I**
- Узкие интерфейсы: класс реализует только то, что умеет.
- Заглушки `raise NotImplementedError` — признак толстого интерфейса.

**D**
- Сервис зависит от абстракции (`Protocol`, `ABC`), детали её реализуют.
- Канал, банк, хранилище меняются без правки сервиса; в тестах — заглушка.

## Вопросы на собеседовании
<details><summary>Сформулируйте принцип Лисков на примере.</summary>

Объект наследника можно подставить туда, где ждут родителя, и программа продолжит работать правильно. Пример нарушения: `Square(Rectangle)` — код меняет ширину прямоугольника и ждёт прежнюю высоту, а квадрат меняет обе стороны. В магазине — `DigitalProduct.weight()`, который выбрасывает исключение, хотя `Product.weight()` всегда возвращал число.
</details>

<details><summary>Чем принцип разделения интерфейса отличается от единственной ответственности?</summary>

S — про сам класс: у него должна быть одна причина для изменения. I — про интерфейс, который навязывают классу снаружи: в нём не должно быть методов, которые классу не нужны. Толстый интерфейс заставляет простой класс писать заглушки, даже если сам класс отвечает за одно.
</details>

<details><summary>Чем принцип инверсии зависимостей отличается от внедрения зависимостей?</summary>

Принцип (DIP) говорит, **что** делать: модули верхнего уровня и детали зависят от общей абстракции. Внедрение (DI) — **как**: зависимость передают объекту снаружи (в конструктор, параметром), а не создают внутри. DI — самый частый способ выполнить DIP.
</details>
