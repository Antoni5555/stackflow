## Теория
Некоторые объекты в приложении должны существовать в одном экземпляре: настройки (их читают из `.env` один раз), пул соединений с базой, логгер. Если каждый модуль создаёт свои `Settings()`, они могут разойтись, а файл настроек читается сотни раз. **Singleton** (одиночка) — паттерн, который гарантирует, что объект класса один, и даёт к нему общую точку доступа.

Способы в Python:
- **модуль** — самый питоновский. Модуль выполняется один раз, при первом `import`, и дальше Python берёт его из кэша `sys.modules`. Объект, созданный на верхнем уровне модуля (`settings = Settings()`), — уже одиночка. Так устроен `django.conf.settings`;
- **`functools.cache` на функции** — `get_settings()` создаёт объект при первом вызове и дальше возвращает тот же (так рекомендует FastAPI). В тестах кэш сбрасывают: `get_settings.cache_clear()`;
- **`__new__`** — классическая реализация из книг. `__new__` — метод, который **создаёт** объект до `__init__` (тот объект только заполняет). Переопределив его, можно всегда возвращать один и тот же экземпляр. Ловушка: `__init__` всё равно вызывается при **каждом** `Settings()` и может перезаписать состояние.

**Почему Singleton часто называют антипаттерном.** Одиночка — это глобальная переменная в красивой обёртке:
- **скрытая зависимость** — код берёт `Settings()` сам, а не получает параметром (тема «Внедрение зависимостей»): по сигнатуре функции не видно, что она зависит от настроек;
- **общее состояние в тестах** — один тест поменял настройку, и следующий упал, хотя сам по себе верен;
- **жёсткая привязка** — подставить другие настройки для одного сервиса нельзя.

Разумный компромисс: создать объект **один раз в точке сборки** (или получить из модуля) и **передавать** его в сервисы. «Один экземпляр» обеспечивает приложение, а не сам класс.

## На практике
Задача: сделать настройки магазина общими для всего приложения и увидеть, где подстерегают ловушки.

### Шаг 1. Модуль — уже одиночка
Настройки в отдельном модуле. Файл `config.py`:
```python
print("читаю настройки")


class Settings:
    def __init__(self):
        self.debug = False
        self.currency = "RUB"


settings = Settings()
```
Импортируем модуль дважды, как будто из двух разных файлов проекта:
```python
import sys

import config
from config import settings

import config as again

print(again is config, settings is config.settings)
print("config" in sys.modules)
```
Результат:
```
читаю настройки
True True
True
```
«читаю настройки» напечаталось один раз: второй импорт взял модуль из `sys.modules`. Все, кто импортирует `settings`, получают один и тот же объект.

### Шаг 2. Singleton через `__new__`
Классическая реализация. Обратите внимание, что печатает `__init__`:
```python
class AppSettings:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

    def __init__(self):
        print("__init__")
        self.debug = False


a = AppSettings()
a.debug = True
b = AppSettings()
print(a is b, a.debug)
```
Результат:
```
__init__
__init__
True False
```
Объект один, но второй вызов `AppSettings()` снова выполнил `__init__` и сбросил `debug`, который поменяли через `a`.

### Шаг 3. Защита от повторного `__init__`
Запоминаем, что объект уже заполнен:
```python
class AppSettings:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

    def __init__(self):
        if getattr(self, "_ready", False):
            return
        print("__init__ один раз")
        self.debug = False
        self._ready = True


a = AppSettings()
a.debug = True
print(AppSettings().debug, AppSettings() is a)
```
Результат:
```
__init__ один раз
True True
```
Работает, но уже видно, сколько трюков нужно, чтобы класс сам следил за своей «единственностью».

### Шаг 4. Функция с кэшем
Проще и удобнее для тестов — `functools.cache`:
```python
from functools import cache


class Settings:
    def __init__(self, env):
        self.debug = env.get("DEBUG") == "True"


ENV = {"DEBUG": "False"}


@cache
def get_settings():
    print("создаю Settings")
    return Settings(ENV)


print(get_settings() is get_settings())
ENV["DEBUG"] = "True"
get_settings.cache_clear()
print(get_settings().debug)
```
Результат:
```
создаю Settings
True
создаю Settings
True
```
Пока кэш жив, `get_settings()` возвращает тот же объект. `cache_clear()` — «забыть» его: так тест получает свежие настройки.

### Шаг 5. Общее состояние в тестах
Два теста сервиса, который сам берёт одиночку `AppSettings` из шага 3:
```python
def price_label(amount):
    settings = AppSettings()
    return f"{amount} ₽ [debug]" if settings.debug else f"{amount} ₽"


def test_debug_label():
    AppSettings().debug = True
    assert price_label(100) == "100 ₽ [debug]"


def test_normal_label():
    assert price_label(100) == "100 ₽"


AppSettings().debug = False
test_debug_label()
test_normal_label()
```
Результат:
```
Traceback (most recent call last):
  File "main.py", line 17, in <module>
    test_normal_label()
  File "main.py", line 12, in test_normal_label
    assert price_label(100) == "100 ₽"
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^
AssertionError
```
Каждый тест верен по отдельности, но первый оставил `debug = True` в общем объекте, и второй упал. Порядок тестов начал влиять на результат. Если передавать настройки параметром — `price_label(amount, settings)`, — каждый тест создаёт свои.

## Частые ошибки
- **Singleton «на всякий случай».** Класс, которому не нужно быть одним, становится глобальной переменной со всеми её проблемами. Сначала спросите: а что сломается, если объектов будет два?
- **Забыть, что `__init__` вызывается каждый раз.** `__new__` вернул старый объект, а `__init__` перезаписал его поля. Нужна защита или другой способ.
- **Одиночка внутри логики.** `Settings()` в теле функции — скрытая зависимость: в сигнатуре её не видно, в тесте не подменить без трюков. Передавайте настройки параметром.
- **Тесты делят состояние.** Изменили общий объект и не вернули — следующие тесты падают «случайно». Сбрасывайте кэш (`cache_clear()`) или не используйте одиночку в тестируемом коде.
- **`from config import settings` и замена объекта.** Если тест сделает `config.settings = Settings()`, модули, уже импортировавшие `settings`, продолжат видеть старый объект (как с `patch` в теме 8.04). Меняют поля объекта или передают настройки явно.

## Итог
**Что это**
- Один экземпляр класса и общая точка доступа: настройки, пул соединений.

**Как в Python**
- Модуль: объект на верхнем уровне создаётся один раз (`sys.modules`).
- `@cache` на `get_settings()`; в тестах — `cache_clear()`.
- `__new__` + `_instance`; помнить, что `__init__` вызывается каждый раз.

**Осторожно**
- Это глобальное состояние: скрытые зависимости, тесты влияют друг на друга.
- Лучше: создать один раз в точке сборки и передавать.

## Вопросы на собеседовании
<details><summary>Как реализовать Singleton в Python?</summary>

Проще всего — объектом на уровне модуля: модуль выполняется один раз, и все импорты получают тот же объект. Другие способы — функция с `functools.cache`, которая создаёт объект при первом вызове, или переопределение `__new__`, который возвращает сохранённый `_instance`. В последнем случае нужно помнить, что `__init__` вызывается при каждом создании.
</details>

<details><summary>Почему Singleton считают антипаттерном?</summary>

Это глобальное состояние: код получает объект сам, а не через параметры, поэтому зависимость скрыта, объект трудно подменить, а тесты влияют друг на друга через общие поля. Обычно достаточно создать объект один раз при старте приложения и передавать его туда, где он нужен.
</details>

<details><summary>Чем `__new__` отличается от `__init__`?</summary>

`__new__` — метод класса, который создаёт и возвращает новый объект; `__init__` получает уже созданный объект и заполняет его атрибуты. Python вызывает `__init__` для объекта, который вернул `__new__`, если тот — экземпляр этого класса. Переопределяют `__new__` редко: для одиночек и для наследников неизменяемых типов (`str`, `int`, `tuple`).
</details>

## Глубже
⚠️ Singleton через декоратор класса (встречается в конспектах) подменяет класс функцией: после этого `isinstance(obj, Settings)` выбрасывает `TypeError`, а наследовать от `Settings` нельзя. В Django настройки — модуль `django.conf.settings`, в тестах их меняют через `override_settings`. Где хранить и как передавать такие общие объекты в приложении — следующая тема, «Слои приложения».
