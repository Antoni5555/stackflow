## Теория
Код магазина живёт годами: меняется скидка, добавляется способ доставки, письмо переезжает в Telegram. Если вся логика оформления заказа лежит в одном классе, любая правка задевает всё остальное, а тест на скидку вдруг требует почтовый сервер. **SOLID** — пять принципов (сформулировал Роберт Мартин), которые помогают раскладывать код так, чтобы изменения были маленькими и предсказуемыми.

**Таблица 1.** SOLID одной строкой.

| Буква | Принцип | Коротко |
|---|---|---|
| **S** | единственной ответственности (Single Responsibility) | у класса одна причина для изменения |
| **O** | открытости/закрытости (Open/Closed) | новое поведение добавляют, не правя старый код |
| **L** | подстановки Лисков (Liskov Substitution) | наследник работает везде, где работает родитель |
| **I** | разделения интерфейса (Interface Segregation) | не заставлять класс реализовывать ненужные методы |
| **D** | инверсии зависимостей (Dependency Inversion) | зависеть от абстракций, а не от конкретных классов |

Эта тема — про **S** и **O**, следующая — про L, I и D.

**S — одна причина для изменения.** «Причина» — это тот, кто попросит поменять код. Расчёт суммы меняет отдел продаж (скидки), текст письма — маркетинг, хранение заказов — разработчики базы. Если всё это в одном `OrderService`, класс меняют три разных человека по трём разным поводам — и каждый может сломать чужое. Разделяем по причинам: расчёт, хранилище, уведомления — отдельные классы, а `OrderService` только **координирует**: вызывает их по порядку.

**O — открыт для расширения, закрыт для изменения.** Цепочка `if method == "courier" … elif method == "pickup" …` растёт с каждым новым способом доставки, и каждый раз правят уже проверенную функцию. Вместо этого каждый способ — отдельный объект с общим методом (`price(total)`, полиморфизм из раздела 7), а выбор — по словарю «название → объект». Новый способ — новый класс и одна строка в словаре; старый код не трогаем.

Принципы — не самоцель. Скрипт на 30 строк дробить на пять классов не нужно: разделяют, когда части начинают меняться по разным причинам или появляется третий `elif`.

**Таблица 2.** S и O на практике.

| | Нарушение | Как исправляют |
|---|---|---|
| S | один класс считает, сохраняет и пишет письма | отдельные классы, сервис их координирует |
| S | метод на 80 строк с комментариями «шаг 1… шаг 4» | каждый шаг — функция или класс со своим именем |
| O | `if/elif` по типу растёт с каждой новинкой | объекты с общим методом + словарь «название → объект» |
| O | новая скидка — правка функции расчёта | список правил скидки; новое правило — новый объект в списке |

## На практике
Задача: разобрать сервис оформления заказа, в котором смешано всё, и сделать так, чтобы новый способ доставки добавлялся без правки старого кода.

### Шаг 1. «Толстый» сервис
Всё в одном методе: сумма, скидка, доставка, сохранение, письмо:
```python
from decimal import Decimal


class OrderService:
    def __init__(self):
        self.orders = []
        self.outbox = []

    def checkout(self, order_id, items, email, delivery):
        total = sum(price * qty for _, price, qty in items)
        if total >= Decimal("5000"):
            total = total * Decimal("0.95")
        if delivery == "courier":
            total += Decimal("300")
        elif delivery == "pickup":
            total += Decimal("0")
        else:
            raise ValueError(f"неизвестная доставка: {delivery}")
        self.orders.append({"id": order_id, "total": total})
        self.outbox.append(f"{email}: заказ №{order_id} на {total} ₽")
        return total


service = OrderService()
items = [("Монитор", Decimal("4990"), 1), ("Кабель", Decimal("490"), 2)]
print(service.checkout(1042, items, "anna@example.com", "courier"))
print(service.outbox)
```
Результат:
```
5971.50
['anna@example.com: заказ №1042 на 5971.50 ₽']
```
Работает, но поменять текст письма, порог скидки или добавить почту России — значит править один и тот же метод. А чтобы проверить скидку, приходится создавать весь сервис с хранилищем и письмами.

### Шаг 2. Делим по ответственностям
Каждая причина для изменения — свой класс. Сервис только вызывает их по порядку:
```python
class PriceCalculator:
    def total(self, items):
        total = sum(price * qty for _, price, qty in items)
        if total >= Decimal("5000"):
            total = total * Decimal("0.95")
        return total


class OrderRepository:
    def __init__(self):
        self.orders = []

    def save(self, order_id, total):
        self.orders.append({"id": order_id, "total": total})


class EmailNotifier:
    def __init__(self):
        self.outbox = []

    def order_created(self, email, order_id, total):
        self.outbox.append(f"{email}: заказ №{order_id} на {total} ₽")


calc = PriceCalculator()
print(calc.total(items))
print(calc.total([("Кабель", Decimal("490"), 2)]))
```
Результат:
```
5671.50
980
```
Скидку теперь проверяют одной строкой, без хранилища и писем: от 5000 ₽ — 5 %, меньше — без скидки.

### Шаг 3. Доставка без if/elif
Каждый способ — класс с методом `price(total)`, выбор — по словарю:
```python
class Courier:
    def price(self, total):
        return Decimal("300")


class Pickup:
    def price(self, total):
        return Decimal("0")


DELIVERY = {"courier": Courier(), "pickup": Pickup()}


def delivery_price(method, total):
    if method not in DELIVERY:
        raise ValueError(f"неизвестная доставка: {method}")
    return DELIVERY[method].price(total)


print(delivery_price("courier", Decimal("5671.50")))
print(delivery_price("pickup", Decimal("980")))
```
Результат:
```
300
0
```
`delivery_price` больше не знает, какие способы бывают, — она берёт объект из словаря и вызывает общий метод.

### Шаг 4. Новый способ — без правки старого кода
Почта: 250 ₽, бесплатно от 3000 ₽. Пишем класс и добавляем строку в словарь:
```python
class Post:
    def price(self, total):
        return Decimal("0") if total >= Decimal("3000") else Decimal("250")


DELIVERY["post"] = Post()
print(delivery_price("post", Decimal("980")))
print(delivery_price("post", Decimal("5671.50")))
```
Результат:
```
250
0
```
`Courier`, `Pickup` и `delivery_price` не менялись — значит, и сломаться не могли.

### Шаг 5. Сервис-координатор
`OrderService` собирает части и сам ничего не считает:
```python
class OrderService:
    def __init__(self, calc, repo, notifier):
        self.calc = calc
        self.repo = repo
        self.notifier = notifier

    def checkout(self, order_id, items, email, delivery):
        goods = self.calc.total(items)
        total = goods + delivery_price(delivery, goods)
        self.repo.save(order_id, total)
        self.notifier.order_created(email, order_id, total)
        return total


repo, notifier = OrderRepository(), EmailNotifier()
service = OrderService(PriceCalculator(), repo, notifier)
print(service.checkout(1042, items, "anna@example.com", "post"))
print(repo.orders, notifier.outbox)
```
Результат:
```
5671.50
[{'id': 1042, 'total': Decimal('5671.50')}] ['anna@example.com: заказ №1042 на 5671.50 ₽']
```
Кода стало больше, но каждый кусок меняется по своей причине и проверяется отдельно. Части передаются в `__init__` — как уведомитель в разделе 7; подробнее — тема «Внедрение зависимостей».

## Частые ошибки
- **«Одна ответственность» = «один метод».** Класс с единственным методом на каждое действие — тоже плохо: логика размазана по десяткам файлов. Ответственность — это причина для изменения, а не число методов.
- **Дробить заранее.** Пять классов для скрипта на 30 строк, который никто не будет менять. Разделяют, когда появились разные причины изменений или третий `elif`.
- **`if/elif` по типу в нескольких местах.** Цена доставки, срок доставки, название для письма — три одинаковые цепочки. Добавили способ и забыли одну — ошибка. Всё, что зависит от способа, — в его классе.
- **«Закрыт для изменения» = «старый код нельзя трогать никогда».** Ошибки исправляют, конечно. Принцип о другом: **новое поведение** добавляется новым кодом, а не вставкой в старый.
- **Координатор снова толстеет.** В `OrderService` возвращаются расчёты «на одну строчку». Сервис только вызывает части; считает калькулятор.

## Итог
**SOLID**
- Пять принципов, чтобы изменения были маленькими: S, O, L, I, D.

**S**
- Одна причина для изменения — одна ответственность.
- Сервис-координатор вызывает части и сам не считает.

**O**
- Новое поведение — новым классом, а не новым `elif`.
- Объекты с общим методом + словарь «название → объект».

**Мера**
- Разделяют, когда части меняются по разным причинам, а не «на всякий случай».

## Вопросы на собеседовании
<details><summary>Расшифруйте SOLID.</summary>

S — единственная ответственность: у класса одна причина для изменения. O — открытость/закрытость: расширяем новым кодом, а не правкой старого. L — подстановка Лисков: наследник работает везде, где родитель. I — разделение интерфейса: не навязывать ненужные методы. D — инверсия зависимостей: зависеть от абстракций, а не от конкретных классов.
</details>

<details><summary>Что значит «одна причина для изменения»?</summary>

Причина — это источник требований: бизнес-правила скидок, формат писем, способ хранения. Если класс придётся менять по просьбе разных людей и по разным поводам, у него несколько ответственностей, и правка одной может сломать другую. Такой класс делят, а общий сценарий оставляют координатору.
</details>

<details><summary>Как избавиться от длинной цепочки if/elif по типу объекта?</summary>

Поведение, которое зависит от типа, переносят в классы с общим методом (полиморфизм), а выбор делают по словарю «ключ → объект» или фабрикой. Новый тип — новый класс и запись в словаре; функция, которая вызывает общий метод, не меняется. Это и есть принцип открытости/закрытости.
</details>

## Глубже
Как наследник может сломать код, который ждёт родителя, и почему сервис должен зависеть от абстракции, а не от `EmailNotifier`, — следующая тема. Словарь «название → объект» вырастет в фабрику — тема «Фабрика».
