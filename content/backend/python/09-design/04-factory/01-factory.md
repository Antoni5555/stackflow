## Теория
Магазин принимает оплату картой и через СБП, и способ приходит из настроек или из формы — **строкой**: `"card"`, `"sbp"`. Где-то эту строку надо превратить в объект нужного класса. Если `if name == "card": CardGateway(...)` написан во view, в фоновой задаче и в админке, то новый банк — правка в трёх местах, а опечатка в одном из них всплывёт в продакшене. **Фабрика** — паттерн, который собирает логику создания объектов в одно место: код просит «дай шлюз `sbp`» и не знает, какие классы бывают.

Формы фабрики в Python:
- **простая фабрика** — функция `get_gateway(name, **options)`. Внутри — словарь «название → класс» (классы в Python — обычные значения, их можно класть в словарь и вызывать). Неизвестное название — понятная ошибка со списком допустимых;
- **реестр с декоратором** — классы сами записываются в словарь: `@register("sbp")` над классом. Новый шлюз — новый класс в своём модуле, фабрику не трогают (принцип O). Главная ловушка: класс попадёт в реестр, только если его модуль **импортирован**;
- **альтернативный конструктор** — `@classmethod`, который собирает объект из другого вида данных: `SmsNotifier.from_env(env)`, `Order.from_dict(data)` (тема 7.03). Это фабрика, встроенная в сам класс;
- **фабричный метод** (Factory Method из книги «банды четырёх») — базовый класс задаёт общий сценарий и вызывает метод `create_…()`, а наследники решают, какой объект создать. В Python его встречают реже: вместо иерархии фабрик обычно передают сам класс или функцию-конструктор параметром.

Фабрика хорошо сочетается с внедрением зависимостей: точка сборки (прошлая тема) читает из настроек `PAYMENT = "sbp"`, вызывает фабрику и передаёт готовый шлюз в сервис.

## На практике
Задача: создавать платёжный шлюз по названию из настроек, добавлять новые шлюзы без правки фабрики и собирать уведомитель из переменных окружения.

### Шаг 1. Классы шлюзов
Два шлюза с общим интерфейсом `charge(amount)`. У каждого свои параметры подключения:
```python
from decimal import Decimal


class CardGateway:
    def __init__(self, shop_id, secret):
        self.shop_id = shop_id
        self.secret = secret

    def charge(self, amount):
        return f"card: магазин {self.shop_id}, списано {amount} ₽"


class SbpGateway:
    def __init__(self, shop_id):
        self.shop_id = shop_id

    def charge(self, amount):
        return f"sbp: магазин {self.shop_id}, QR на {amount} ₽"
```

### Шаг 2. Простая фабрика
Словарь «название → класс» и функция, которая создаёт объект:
```python
GATEWAYS = {"card": CardGateway, "sbp": SbpGateway}


def get_gateway(name, **options):
    if name not in GATEWAYS:
        known = ", ".join(sorted(GATEWAYS))
        raise ValueError(f"неизвестный шлюз {name!r}, есть: {known}")
    return GATEWAYS[name](**options)


gateway = get_gateway("sbp", shop_id=42)
print(gateway.charge(Decimal("2490.00")))
print(get_gateway("card", shop_id=42, secret="s3cr3t").charge(Decimal("990.00")))
get_gateway("cash")
```
Результат:
```
sbp: магазин 42, QR на 2490.00 ₽
card: магазин 42, списано 990.00 ₽
Traceback (most recent call last):
  File "main.py", line 14, in <module>
    get_gateway("cash")
  File "main.py", line 7, in get_gateway
    raise ValueError(f"неизвестный шлюз {name!r}, есть: {known}")
ValueError: неизвестный шлюз 'cash', есть: card, sbp
```
`GATEWAYS[name]` — это класс, `(**options)` — его вызов. Ошибка сразу подсказывает, какие названия допустимы: опечатку в настройках видно при запуске, а не на первом платеже.

### Шаг 3. Реестр с декоратором
Чтобы новый шлюз не требовал правки `GATEWAYS`, класс записывается в реестр сам. `register(name)` — декоратор с параметром (тема 3.09): записывает класс и возвращает его без изменений:
```python
GATEWAYS = {}


def register(name):
    def decorator(cls):
        GATEWAYS[name] = cls
        return cls
    return decorator


@register("card")
class CardGateway:
    def __init__(self, shop_id, secret):
        self.shop_id = shop_id

    def charge(self, amount):
        return f"card: списано {amount} ₽"


@register("installment")
class InstallmentGateway:
    def __init__(self, shop_id, months=6):
        self.months = months

    def charge(self, amount):
        return f"рассрочка на {self.months} мес.: {amount / self.months:.2f} ₽ в месяц"


print(sorted(GATEWAYS))
print(get_gateway("installment", shop_id=42).charge(Decimal("45990.00")))
```
Результат:
```
['card', 'installment']
рассрочка на 6 мес.: 7665.00 ₽ в месяц
```
`get_gateway` не менялась — она читает тот же словарь `GATEWAYS`. В проекте каждый шлюз живёт в своём модуле, и модуль нужно импортировать (например, в `gateways/__init__.py`), иначе декоратор не выполнится и названия в реестре не будет.

### Шаг 4. Альтернативный конструктор
Уведомитель настраивается переменными окружения. Разбор окружения — в `@classmethod`, а `__init__` остаётся простым:
```python
class SmsNotifier:
    def __init__(self, api_key, sender="SHOP"):
        self.api_key = api_key
        self.sender = sender

    @classmethod
    def from_env(cls, env):
        if "SMS_API_KEY" not in env:
            raise ValueError("SMS_API_KEY не задан")
        return cls(env["SMS_API_KEY"], env.get("SMS_SENDER", "SHOP"))


sms = SmsNotifier.from_env({"SMS_API_KEY": "k-91"})
print(sms.api_key, sms.sender)
```
Результат:
```
k-91 SHOP
```
В работе передают `os.environ`, в тесте — обычный словарь. `cls(...)` вместо `SmsNotifier(...)` — чтобы наследник через `from_env` создавал объект своего класса.

### Шаг 5. Фабрика в точке сборки
Настройки → фабрика → сервис (внедрение зависимостей из прошлой темы):
```python
class CheckoutService:
    def __init__(self, gateway):
        self.gateway = gateway

    def pay(self, amount):
        return self.gateway.charge(amount)


SETTINGS = {"PAYMENT": "installment", "PAYMENT_OPTIONS": {"shop_id": 42, "months": 12}}


def build_checkout(settings):
    gateway = get_gateway(settings["PAYMENT"], **settings["PAYMENT_OPTIONS"])
    return CheckoutService(gateway)


print(build_checkout(SETTINGS).pay(Decimal("45990.00")))
```
Результат:
```
рассрочка на 12 мес.: 3832.50 ₽ в месяц
```
Чтобы переключить магазин на другой банк, меняют настройку — код сервиса, фабрики и тестов остаётся прежним.

## Частые ошибки
- **`if/elif` создания в нескольких местах.** Новый класс — правка во всех, и где-то забудут. Создание — в одной фабрике.
- **Фабрика молча возвращает `None`.** `GATEWAYS.get(name)` без проверки — ошибка всплывёт позже, как `'NoneType' object has no attribute 'charge'`. Неизвестное имя — сразу понятное исключение со списком допустимых.
- **Декоратор забыл `return cls`.** Класс записан в реестр, но имя `CardGateway` в модуле теперь `None`.
- **Модуль с классом не импортирован.** Декоратор не выполнился, имени нет в реестре: «неизвестный шлюз», хотя класс написан. Импортируйте модули реализаций в `__init__.py` пакета.
- **Иерархия фабрик там, где хватит словаря.** `CardGatewayFactory`, `SbpGatewayFactory` с одним методом `create()` — лишний код. В Python класс и так «умеет создавать» — его можно передать или положить в словарь.
- **`SmsNotifier(...)` внутри `@classmethod`.** Наследник через `from_env` получит объект родителя. Пишите `cls(...)`.

## Итог
**Зачем**
- Создание объектов по названию — в одном месте; код не знает конкретных классов.

**Как в Python**
- Словарь «название → класс» + функция; понятная ошибка на неизвестное имя.
- Реестр с декоратором `@register("…")` — новые классы без правки фабрики; модуль должен быть импортирован.
- `@classmethod` `from_…` — объект из словаря, строки, окружения; внутри — `cls(...)`.

**Вместе с DI**
- Точка сборки: настройки → фабрика → готовый объект в конструктор сервиса.

## Вопросы на собеседовании
<details><summary>Зачем нужна фабрика?</summary>

Чтобы собрать логику создания объектов в одном месте. Вызывающий код говорит, что ему нужно (`get_gateway("sbp")`), и не знает конкретных классов и их параметров. Новый вариант добавляется в фабрику, а не во все места, где объекты создаются.
</details>

<details><summary>Чем простая фабрика отличается от фабричного метода?</summary>

Простая фабрика — одна функция или метод, который по параметру выбирает и создаёт объект (обычно через словарь или `if`). Фабричный метод — приём с наследованием: базовый класс описывает общий сценарий и вызывает `create_…()`, а каждый наследник переопределяет этот метод и создаёт свой тип объекта. В Python фабричный метод часто заменяют передачей класса или функции.
</details>

<details><summary>Почему в `@classmethod` пишут `cls(...)`, а не имя класса?</summary>

`cls` — класс, у которого вызвали метод. Если наследник вызовет `Child.from_env(...)`, `cls(...)` создаст `Child`, а жёстко прописанное имя родителя — объект родителя. Так альтернативный конструктор работает и для наследников.
</details>

## Глубже
⚠️ В некоторых конспектах базовый класс с фабричным методом называют «абстрактной фабрикой» — это другой паттерн: **абстрактная фабрика** создаёт **семейство** связанных объектов (например, кнопку и поле ввода одной темы оформления). Реестры с декораторами — так устроены `admin.register` в Django и маршруты `@app.get` в FastAPI. Как сделать, чтобы объект настроек был один на всё приложение, — следующая тема, «Singleton».
