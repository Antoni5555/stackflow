## Теория
В разделе 7 уведомитель стал параметром `Order(id, notifier)` — и заказ удалось проверить заглушкой. Это и есть **внедрение зависимостей** (dependency injection, DI): объект не создаёт и не ищет то, от чего зависит, а **получает** это снаружи. Здесь — как применять приём во всём коде: какие бывают зависимости, где собирать объекты и чем DI лучше `patch` в тестах.

**Зависимость** — всё, что код берёт не из своих параметров: платёжный шлюз, хранилище, уведомитель, а ещё **текущее время**, случайные числа, настройки. Скрытые зависимости — самые коварные: функция `is_active(promo)`, которая внутри вызывает `date.today()`, сегодня проходит тест, а 1 января — падает.

Как передавать:
- **через конструктор** — основной способ для сервисов: `CheckoutService(gateway, notifier, clock)`. Все зависимости видны в одном месте, объект сразу готов к работе;
- **через параметр функции** — для простых функций: `cancel_order(order_id, repo, notifier)`;
- **значение по умолчанию** — когда почти всегда нужен один вариант: `clock=date.today`. Объект по умолчанию создают через `None` внутри (тема 7.10), а функцию — `date.today` без скобок — можно передать сразу.

**Где создавать объекты.** Код сервисов зависимости только получает. Создаёт и связывает их одно место — **точка сборки** (composition root): функция `build_checkout()` или `main()`. Там написано, что в работе используется банк и почта; тесты собирают тот же сервис со своими заглушками. Если конструктор требует пять–шесть зависимостей, это сигнал, что у класса слишком много ответственностей (принцип S).

**DI и `patch`.** `patch` (тема 8.04) подменяет имя внутри модуля — тест знает, *где и как* код импортирует зависимость, и ломается при переносе импорта. С DI тест просто передаёт заглушку в конструктор. `patch` остаётся для чужого кода, который вы не можете поменять.

## На практике
Задача: сделать оформление заказа с промокодом проверяемым — без банка, почты и зависимости от сегодняшней даты.

### Шаг 1. Скрытая зависимость от даты
Промокод действует до 31 декабря. Сервис сам узнаёт сегодняшнюю дату:
```python
from datetime import date
from decimal import Decimal


class PromoChecker:
    def __init__(self, until):
        self.until = until

    def is_active(self):
        return date.today() <= self.until
```
Результат `is_active()` зависит от дня запуска: тест «промокод действует», написанный в декабре, начнёт падать в январе, а проверить «последний день акции» вообще нельзя — сегодня не 31 декабря.

### Шаг 2. Дата — тоже зависимость
Передаём функцию, которая возвращает «сегодня». По умолчанию — настоящая `date.today`:
```python
class PromoChecker:
    def __init__(self, until, clock=date.today):
        self.until = until
        self.clock = clock

    def is_active(self):
        return self.clock() <= self.until


new_year = date(2026, 12, 31)
print(PromoChecker(new_year, clock=lambda: date(2026, 12, 31)).is_active())
print(PromoChecker(new_year, clock=lambda: date(2027, 1, 1)).is_active())
```
Результат:
```
True
False
```
Граница акции проверена без ожидания Нового года. В работе `clock` не передают — используется `date.today`.

### Шаг 3. Сервис получает всё через конструктор
Оформление заказа: списать деньги, отправить письмо, применить промокод:
```python
class CheckoutService:
    def __init__(self, gateway, notifier, promo):
        self.gateway = gateway
        self.notifier = notifier
        self.promo = promo

    def checkout(self, order_id, total):
        if self.promo.is_active():
            total -= Decimal("500")
        payment_id = self.gateway.charge(total)
        self.notifier.send(f"Заказ №{order_id} оплачен: {total} ₽ ({payment_id})")
        return payment_id
```
Внутри нет ни одного `BankGateway()`, `EmailNotifier()` или `date.today()` — только то, что передали.

### Шаг 4. Заглушки для теста
Заглушки (fake) — простые классы с тем же интерфейсом, которые запоминают вызовы:
```python
class FakeGateway:
    def __init__(self):
        self.charges = []

    def charge(self, amount):
        self.charges.append(amount)
        return f"fake_{len(self.charges)}"


class FakeNotifier:
    def __init__(self):
        self.sent = []

    def send(self, text):
        self.sent.append(text)


gateway, notifier = FakeGateway(), FakeNotifier()
promo = PromoChecker(new_year, clock=lambda: date(2026, 12, 31))
service = CheckoutService(gateway, notifier, promo)
print(service.checkout(1042, Decimal("2990.00")))
print(gateway.charges, notifier.sent)
```
Результат:
```
fake_1
[Decimal('2490.00')] ['Заказ №1042 оплачен: 2490.00 ₽ (fake_1)']
```
Тест проверил скидку, сумму списания и текст письма — без сети, денег и календаря. В отличие от `Mock` (тема 8.04), заглушка — обычный класс: её поведение видно целиком, и опечатка в имени метода сразу даст `AttributeError`.

### Шаг 5. Точка сборки
Настоящие классы связываются в одном месте. Банк и почта здесь — учебные, они печатают, что делают:
```python
class BankGateway:
    def charge(self, amount):
        print(f"банк: списано {amount} ₽")
        return "pay_8812"


class EmailNotifier:
    def send(self, text):
        print("email:", text)


def build_checkout():
    promo = PromoChecker(date(2026, 12, 31))
    return CheckoutService(BankGateway(), EmailNotifier(), promo)


service = build_checkout()
print(type(service.gateway).__name__, service.promo.clock == date.today)
```
Результат:
```
BankGateway True
```
Чтобы заменить почту на Telegram, правят одну строку в `build_checkout` — сервис и тесты не меняются. В Django такую сборку часто пишут в модуле `services.py` или прямо во view, в FastAPI для этого есть `Depends`.

## Частые ошибки
- **Зависимость создаётся внутри.** `self.gateway = BankGateway()` в `__init__` — сервис нельзя проверить без банка. Принимайте зависимость параметром.
- **Скрытое время и случайность.** `date.today()`, `datetime.now()`, `random`, `uuid4()` внутри логики делают результат непредсказуемым в тестах. Передавайте `clock` или генератор.
- **`clock=date.today()` со скобками.** Дата вычислится один раз при определении функции, и сервис навсегда застрянет в этом дне. Передают саму функцию — без скобок.
- **Сборка размазана по коду.** `EmailNotifier()` создаётся в пяти местах; сменить канал — значит найти все. Создание — только в точке сборки.
- **Конструктор на восемь параметров.** Внедрение зависимостей сделало видимым, что класс делает слишком много. Делите по принципу S.
- **`patch` для своего кода.** Тест знает пути импортов и ломается при рефакторинге. Свой код проектируйте под DI; `patch` — для чужого.

## Итог
**Приём**
- Объект получает зависимости снаружи, а не создаёт и не ищет их.
- Зависимости — это и шлюзы, и хранилища, и время, и случайность.

**Как**
- Конструктор — для сервисов, параметр — для функций, значение по умолчанию — для частого варианта.
- Создание и связывание — в одной точке сборки.

**Тесты**
- Заглушки — простые классы с тем же интерфейсом; передаются в конструктор.
- `patch` — для чужого кода.

## Вопросы на собеседовании
<details><summary>Что такое внедрение зависимостей и зачем оно нужно?</summary>

Приём, при котором объект получает зависимости (шлюз, хранилище, уведомитель, часы) снаружи — обычно через конструктор, — а не создаёт их сам. Так класс не привязан к конкретным реализациям: в работе ему передают настоящие, в тестах — заглушки, а смена реализации не требует правки класса.
</details>

<details><summary>Как протестировать код, который зависит от текущей даты?</summary>

Сделать дату зависимостью: передавать функцию `clock` (по умолчанию `date.today`) в конструктор или параметром, а в тесте подставлять `lambda: date(2026, 12, 31)`. Альтернатива — подменять время библиотекой (например, `freezegun`), но явная зависимость проще и не требует магии.
</details>

<details><summary>Что такое composition root?</summary>

Единственное место приложения, где создаются конкретные объекты и связываются друг с другом: функция сборки, `main`, настройка приложения. Остальной код только получает готовые зависимости. Поэтому замена реализации — правка в одном месте, а тесты собирают тот же граф объектов со своими заглушками.
</details>

<details><summary>Чем заглушка (fake) отличается от Mock?</summary>

Fake — простой класс с рабочей упрощённой логикой: хранит списания в списке, отдаёт заданный ответ. Mock принимает любые вызовы и записывает их, а проверяют его через `assert_called_…`. Fake нагляднее и ловит опечатки в именах методов; Mock удобен, когда нужно проверить порядок и аргументы вызовов или подменить чужой код.
</details>
