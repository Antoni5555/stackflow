## Теория
Оформляя заказ, сервер магазина спрашивает склад, банк и службу доставки. Каждый отвечает за 0,1–0,2 секунды, и всё это время программа ничего не делает — **ждёт**. Если спрашивать по очереди, время складывается. А пока ждём банк, можно было бы уже спросить доставку. Как это сделать — тема всего раздела.

Задачи бывают двух видов:
- **ждущие (I/O-bound)** — сеть, база данных, диск. Процессор почти свободен, время уходит на ожидание ответа. Таких задач на сервере большинство;
- **считающие (CPU-bound)** — сжатие фото, расчёт отчёта за год, шифрование. Время уходит на работу процессора.

Два похожих слова:
- **конкурентность** — несколько задач **в работе** одновременно, но выполняются они по очереди, переключаясь, пока другие ждут. Один повар ставит воду, пока она греется — режет овощи;
- **параллелизм** — несколько задач **выполняются** в один момент на разных ядрах процессора. Несколько поваров.

Для ждущих задач хватает конкурентности: пока одна ждёт, работает другая. Для считающих нужен параллелизм — иначе быстрее не станет.

**GIL** (Global Interpreter Lock) — замок в стандартном Python (CPython): в один момент Python-код выполняет только **один поток** процесса. Он упрощает управление памятью, но поэтому потоки не ускоряют вычисления. Во время ожидания сети или диска поток отпускает GIL — и для ждущих задач потоки работают.

В Python три подхода:
- **потоки** (`threading`) — для ожидания; общая память, а значит риск гонки данных;
- **процессы** (`multiprocessing`) — для вычислений; у каждого процесса свой GIL и своя память, работают по-настоящему параллельно, но запуск дороже;
- **asyncio** — для ожидания в одном потоке: функция сама говорит «тут я жду» (`await`), и цикл событий запускает другую. Переключение дешёвое — можно держать тысячи соединений.

## На практике
Задача: посмотреть, как меняется время, если ждать сервисы по очереди и конкурентно, и убедиться, что вычисления так не ускорить. Время округляем до десятых.

### Шаг 1. По очереди
Сервисы имитируем функцией, которая просто ждёт (`time.sleep`):
```python
import time


def ask(name, seconds):
    time.sleep(seconds)
    return name


start = time.perf_counter()
answers = [ask("склад", 0.1), ask("банк", 0.2), ask("доставка", 0.1)]
print(answers, round(time.perf_counter() - start, 1))
```
Результат:
```
['склад', 'банк', 'доставка'] 0.4
```
Время сложилось: 0,1 + 0,2 + 0,1. Всё это время процессор простаивал.

### Шаг 2. Конкурентно через asyncio
Та же имитация, но ожидание — `await asyncio.sleep`, а запросы запускает `gather` (подробно — темы 03–04):
```python
import asyncio


async def ask_async(name, seconds):
    await asyncio.sleep(seconds)
    return name


async def main():
    return await asyncio.gather(
        ask_async("склад", 0.1), ask_async("банк", 0.2), ask_async("доставка", 0.1)
    )


start = time.perf_counter()
answers = asyncio.run(main())
print(answers, round(time.perf_counter() - start, 1))
```
Результат:
```
['склад', 'банк', 'доставка'] 0.2
```
Три ожидания шли одновременно — время по самому медленному, банку. Поток при этом один.

### Шаг 3. Вычисления asyncio не ускоряет
Две «тяжёлые» задачи без `await` внутри. Печатаем начало и конец каждой:
```python
async def compress(name):
    print(name, "начал")
    sum(i * i for i in range(200_000))
    print(name, "закончил")


async def main():
    await asyncio.gather(compress("фото 1"), compress("фото 2"))


asyncio.run(main())
```
Результат:
```
фото 1 начал
фото 1 закончил
фото 2 начал
фото 2 закончил
```
Второе фото не начинается, пока первое не закончено: переключиться можно только на `await`, а при счёте ждать нечего. Для вычислений нужны процессы — следующая тема.

### Шаг 4. Ожидание в потоках
Потоки тоже подходят для ожидания: пока один спит в `time.sleep`, GIL свободен для других:
```python
from concurrent.futures import ThreadPoolExecutor

start = time.perf_counter()
with ThreadPoolExecutor() as pool:
    answers = list(pool.map(ask, ["склад", "банк", "доставка"], [0.1, 0.2, 0.1]))
print(answers, round(time.perf_counter() - start, 1))
```
Результат:
```
['склад', 'банк', 'доставка'] 0.2
```
Тот же выигрыш без `async`, с обычной функцией `ask`. Цена — общая память: потоки могут испортить общие данные (гонка, следующая тема). В браузерном тренажёре потоков нет — этот шаг выполнен на обычном Python.

## Частые ошибки
- **Ждать ускорения вычислений от потоков или asyncio.** GIL пропускает один поток, а `async` переключается только на `await`. Вычисления ускоряют процессы.
- **Путать конкурентность и параллелизм.** asyncio — конкурентность в одном потоке, а не «параллельные вычисления».
- **Распараллеливать мелочь.** Запуск процесса стоит десятки миллисекунд — дороже задачи на 5 мс.
- **Считать, что async ускоряет каждый запрос.** Отдельный запрос не быстрее; выигрыш — в том, что за то же время обслуживается больше запросов.
- **Писать `time.sleep` внутри `async def`.** Он блокирует весь поток, и остальные корутины стоят. В асинхронном коде ждут `await asyncio.sleep` (тема 07).

## Итог
**Виды задач**
- Ждущие (сеть, база, диск) — ускоряет конкурентность.
- Считающие — ускоряет только параллелизм на нескольких ядрах.

**GIL**
- Один поток Python-кода в процессе за раз; во время ожидания отпускается.

**Выбор**
- Ожидание — asyncio или потоки; вычисления — процессы; тысячи соединений — asyncio.

## Вопросы на собеседовании
<details><summary>Чем конкурентность отличается от параллелизма?</summary>

Конкурентность — несколько задач в работе одновременно, но выполняются по очереди: пока одна ждёт, работает другая. Параллелизм — задачи выполняются в один момент на разных ядрах. Конкурентность ускоряет ожидание, параллелизм — вычисления.
</details>

<details><summary>Что такое GIL и на что он влияет?</summary>

Global Interpreter Lock — замок в CPython, который позволяет выполнять Python-код только одному потоку процесса за раз. Из-за него потоки не ускоряют вычисления. На ожидание сети и диска он почти не влияет: поток отпускает GIL, пока ждёт. Обходят GIL процессами — у каждого свой интерпретатор и свой GIL.
</details>

<details><summary>Чем потоки отличаются от процессов с точки зрения памяти?</summary>

Потоки одного процесса делят память: общие объекты видны всем, поэтому возможна гонка данных и нужны блокировки. Процессы изолированы: у каждого своя память, данные передают явно (очереди, каналы, сериализация). Это безопаснее, но обмен данными дороже.
</details>

<details><summary>Зачем нужны специальные асинхронные библиотеки?</summary>

Обычные библиотеки (`requests`, драйвер базы без async) ждут ответа, блокируя поток, — и в asyncio вместе с ним стоят все корутины. Асинхронные (`httpx.AsyncClient`, `asyncpg`) на ожидании отдают управление циклу событий через `await`, и тот запускает другие задачи.
</details>

<details><summary>Приведите задачу, где asyncio подходит лучше потоков.</summary>

Сервер чата поддержки с десятками тысяч открытых соединений, которые почти всё время ждут сообщений. Поток на каждое соединение — гигабайты памяти и дорогие переключения; корутина весит килобайты, и тысячи их живут в одном потоке.
</details>
