## Теория
Прошлая тема сравнила подходы. Здесь — как запускать потоки и процессы в Python и что может пойти не так. В браузерном тренажёре потоков и процессов нет, поэтому примеры урока выполнены на обычном Python 3.12; повторить их можно в терминале на своём компьютере.

**Процесс** — запущенная программа со своей памятью и своим интерпретатором Python (и своим GIL). **Поток** — линия выполнения внутри процесса; все потоки процесса делят его память: одни и те же переменные, списки, объекты.

Потоки:
- `threading.Thread(target=функция, args=(…))` — создать, `start()` — запустить, `join()` — дождаться;
- поток сам ничего не возвращает: результат кладут в общий список или берут пул (ниже).

**Гонка данных** (race condition) — ошибка, когда результат зависит от того, в каком порядке потоки выполнили свои шаги. Классика магазина — «проверить, потом изменить»: два покупателя одновременно видят «остаток 1», оба покупают, остаток становится `-1`. Защита — **блокировка** `threading.Lock`: `with lock:` пускает в участок кода только один поток, остальные ждут у входа. Участок под блокировкой делают коротким.

**`concurrent.futures`** — удобный интерфейс поверх потоков и процессов:
- `ThreadPoolExecutor(max_workers=N)` — пул потоков, `ProcessPoolExecutor` — пул процессов, интерфейс у них одинаковый;
- `pool.map(функция, данные)` — результаты по порядку данных;
- `pool.submit(функция, аргументы)` возвращает **Future** — «обещание результата»; `future.result()` ждёт и возвращает значение или **выбрасывает** исключение, случившееся в потоке.

Процессы:
- данные и функция передаются в другой процесс через сериализацию (`pickle`), поэтому функция должна лежать на верхнем уровне модуля, а не быть `lambda` или вложенной;
- запуск пула пишут под `if __name__ == "__main__":` — на Windows и macOS дочерний процесс заново импортирует модуль, и без этой проверки начнёт запускать пулы сам;
- общей памяти нет: процесс меняет свою копию списка, а не ваш.

В Python 3.13 появилась экспериментальная сборка без GIL (free-threaded): в ней потоки могут считать параллельно. Обычный Python 3.12 и 3.13 по умолчанию — с GIL.

## На практике
Задача: ждать три сервиса в потоках, поймать гонку при продаже последнего товара, исправить её и посчитать «тяжёлую» работу в процессах.

### Шаг 1. Три потока
Каждый поток «спрашивает» сервис и кладёт ответ в общий список:
```python
import threading
import time

answers = []


def ask(name):
    time.sleep(0.1)
    answers.append(name)


start = time.perf_counter()
threads = [threading.Thread(target=ask, args=(n,)) for n in ["склад", "банк", "доставка"]]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(sorted(answers), round(time.perf_counter() - start, 1))
```
Результат:
```
['банк', 'доставка', 'склад'] 0.1
```
Три ожидания прошли одновременно. Порядок в `answers` заранее неизвестен — кто раньше проснулся, тот и записал, — поэтому печатаем отсортированный.

### Шаг 2. Гонка: продали последний товар дважды
Остаток — 1. Покупка: проверить остаток, сходить в банк (0,05 с), уменьшить остаток:
```python
stock = 1
sold = []


def buy(name):
    global stock
    if stock > 0:
        time.sleep(0.05)
        stock -= 1
        sold.append(name)


threads = [threading.Thread(target=buy, args=(n,)) for n in ["Анна", "Борис"]]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(stock, sorted(sold))
```
Результат:
```
-1 ['Анна', 'Борис']
```
Пока Анна была «в банке», Борис тоже увидел `stock > 0`. Каждый поток сам по себе написан правильно — ломается только их сочетание.

### Шаг 3. Блокировка
Проверка и изменение должны идти одним куском, без вклинивания других потоков:
```python
stock = 1
sold = []
lock = threading.Lock()


def buy(name):
    global stock
    with lock:
        if stock > 0:
            time.sleep(0.05)
            stock -= 1
            sold.append(name)


threads = [threading.Thread(target=buy, args=(n,)) for n in ["Анна", "Борис"]]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(stock, len(sold))
```
Результат:
```
0 1
```
Второй поток ждал у `with lock`, а войдя, увидел `stock = 0`. В настоящем магазине остаток хранится в базе, и там ту же задачу решают транзакции и блокировки строк (курс SQL) — `Lock` в Python защищает только память одного процесса.

### Шаг 4. Пул потоков и Future
`submit` возвращает Future; `result()` отдаёт значение — или ошибку, которая случилась в потоке:
```python
from concurrent.futures import ThreadPoolExecutor


def quote(service):
    time.sleep(0.1)
    if service == "почта":
        raise ConnectionError("почта не отвечает")
    return 300


with ThreadPoolExecutor(max_workers=3) as pool:
    futures = {s: pool.submit(quote, s) for s in ["курьер", "почта", "самовывоз"]}

for service, future in futures.items():
    try:
        print(service, future.result())
    except ConnectionError as e:
        print(service, "ошибка:", e)
```
Результат:
```
курьер 300
почта ошибка: почта не отвечает
самовывоз 300
```
Исключение в потоке не роняет программу молча — оно «едет» внутри Future и выбрасывается на `result()`. Выход из `with` ждёт завершения всех задач пула.

### Шаг 5. Пул процессов для вычислений
Функцию для процессов кладём в модуль — её должен найти дочерний процесс. Файл `photos.py`:
```python
import os


def compress(photo_id):
    sum(i * i for i in range(2_000_000))
    return photo_id, os.getpid()
```
Запускаем на двух процессах и смотрим, в скольких разных процессах шла работа:
```python
import os
from concurrent.futures import ProcessPoolExecutor

from photos import compress

if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=2) as pool:
        results = list(pool.map(compress, [1, 2, 3, 4]))
    print([photo for photo, _ in results])
    print(len({pid for _, pid in results}), os.getpid() in {pid for _, pid in results})
```
Результат:
```
[1, 2, 3, 4]
2 False
```
Результаты — по порядку фото, работали два процесса, и ни один из них — не основная программа. Каждый со своим GIL, поэтому на двух ядрах вычисления идут одновременно.

## Частые ошибки
- **«Проверить, потом изменить» без блокировки.** `if stock > 0: … stock -= 1` в потоках продаёт товар дважды. Проверку и изменение — под одним `with lock`.
- **Долгая работа под блокировкой.** Запрос к банку внутри `with lock` превращает потоки обратно в очередь. Под блокировкой — только короткая работа с общими данными.
- **Забыть `join()` или результат Future.** Программа печатает итог раньше, чем потоки закончили; ошибка в потоке, у которой не спросили `result()`, теряется.
- **`lambda` или вложенная функция в пуле процессов.** `pickle` её не передаст — ошибка начинается с `Can't pickle`. Функция — на верхнем уровне модуля.
- **Пул процессов без `if __name__ == "__main__":`.** На Windows и macOS — бесконечный запуск процессов или ошибка. Запуск пула — только под этой проверкой.
- **Ждать изменений общей переменной от процесса.** У процесса своя память: `append` в дочернем процессе не изменит ваш список. Результат возвращают из функции.
- **Пример с `counter += 1` для демонстрации гонки.** ⚠️ В Python 3.12 простой цикл `counter = counter + 1` в двух потоках часто даёт верную сумму: переключения редки. Гонка от этого не исчезла — она проявится под нагрузкой. Надёжно её показывает пауза между проверкой и изменением, как в шаге 2.

## Итог
**Потоки**
- `Thread(target, args)`, `start`, `join`; общая память.
- Гонка «проверить, потом изменить» — `threading.Lock` и `with lock:`.

**Пулы**
- `ThreadPoolExecutor` — ожидание, `ProcessPoolExecutor` — вычисления; `map`, `submit`.
- `future.result()` — значение или исключение из задачи.

**Процессы**
- Своя память и свой GIL; данные — через `pickle`.
- Функция — на верхнем уровне модуля; запуск — под `if __name__ == "__main__":`.

## Вопросы на собеседовании
<details><summary>Что такое состояние гонки и как его избежать?</summary>

Ошибка, при которой результат зависит от порядка выполнения потоков: например, два потока одновременно проверили остаток и оба его уменьшили. Избегают блокировками (`threading.Lock`), атомарными операциями, очередями (`queue.Queue`) вместо общих переменных, а для данных в базе — транзакциями и блокировками строк.
</details>

<details><summary>Чем `ThreadPoolExecutor` отличается от `ProcessPoolExecutor`?</summary>

Интерфейс один (`submit`, `map`, `Future`), разница — в исполнителях. Пул потоков работает в одном процессе с общей памятью и GIL — подходит для ожидания. Пул процессов запускает отдельные интерпретаторы: вычисления идут параллельно на разных ядрах, но функция и данные передаются через `pickle`, а запуск дороже.
</details>

<details><summary>Почему потоки в Python не ускоряют вычисления?</summary>

Из-за GIL: в процессе CPython Python-код в один момент выполняет только один поток. Потоки по очереди получают GIL, а при счёте отпускать его ради ожидания некому. Ускоряют вычисления процессы — у каждого свой GIL — или расширения на C, которые отпускают GIL во время работы (`numpy`).
</details>

<details><summary>Что такое Future?</summary>

Объект-«обещание» результата задачи, которая выполняется в пуле. `future.result()` ждёт завершения и возвращает значение или выбрасывает исключение, случившееся в задаче; `future.done()` — закончена ли она. В asyncio есть свой `Future` и задачи (`Task`) с той же идеей.
</details>
