## Теория
**SSH** — защищённый вход на сервер: всё, что вы делали в этом курсе в терминале сервера, вы делаете через `ssh`. Соединение шифруется, а вход — по **ключу** вместо пароля.

**Пара ключей** создаётся на **вашем** компьютере командой `ssh-keygen -t ed25519`:
- **закрытый** ключ `~/.ssh/id_ed25519` — остаётся у вас, никому не передаётся, права `600` (иначе SSH откажется им пользоваться);
- **открытый** ключ `~/.ssh/id_ed25519.pub` — одна строка `ssh-ed25519 AAAA… комментарий`, её кладут на сервер.

На **сервере** открытые ключи тех, кому можно войти, лежат в `~/.ssh/authorized_keys` пользователя — по строке на ключ. Права: папка `~/.ssh` — `700`, файл — `600`; при более открытых правах SSH ключ не примет. Вход по ключу: сервер проверяет, что у вас есть закрытая пара к одному из ключей в `authorized_keys`, — сам закрытый ключ по сети не передаётся.

Команды на вашем компьютере:
- `ssh shop@203.0.113.10` — войти пользователем `shop`; `-i путь` — каким ключом, `-p 2222` — другой порт;
- `ssh-copy-id shop@203.0.113.10` — дописать ваш открытый ключ в `authorized_keys` на сервере (пока работает вход по паролю);
- **`scp`** — копирование по SSH: `scp shop@сервер:~/backups/media.tar.gz ./` — с сервера к себе, `scp файл shop@сервер:/tmp/` — на сервер; `-r` — папку;
- `ssh shop@сервер 'команда'` — выполнить одну команду без входа (так работают скрипты деплоя).

Файл **`~/.ssh/config`** на вашем компьютере избавляет от длинных команд:
```
Host shop
    HostName 203.0.113.10
    User shop
    Port 22
    IdentityFile ~/.ssh/id_ed25519
```
Теперь `ssh shop` и `scp shop:~/backups/media.tar.gz ./`.

При первом подключении SSH показывает **отпечаток** (fingerprint) ключа сервера и спрашивает `yes/no`. После `yes` отпечаток запоминается в `~/.ssh/known_hosts`; если однажды он изменится — SSH предупредит о возможной подмене сервера.

После настройки входа по ключу на сервере **отключают вход по паролю и вход `root`** (`PasswordAuthentication no`, `PermitRootLogin no` в `/etc/ssh/sshd_config`) — перебор паролей становится бесполезен.

## На практике
Задача: настроить вход на сервер магазина по ключу и скачать бэкап. Ключ создаётся на вашем компьютере (настоящий Ubuntu, OpenSSH 9.6), файл `authorized_keys` настраивается на сервере — это можно повторить в тренажёре.

### Шаг 1. Пара ключей
На своём компьютере, без пароля на ключ (`-N ""` — только для примера; на практике пароль на ключ ставят):
```bash
ssh-keygen -t ed25519 -C "shop-deploy" -f ~/.ssh/id_ed25519 -N ""
ls -l ~/.ssh
```
Результат (рисунок ключа убран):
```
Generating public/private ed25519 key pair.
Your identification has been saved in /home/anna/.ssh/id_ed25519
Your public key has been saved in /home/anna/.ssh/id_ed25519.pub
The key fingerprint is:
SHA256:2J//eEa0i4SZ7/XFLwSabsATFGW7+lXcinlDys3TwKw shop-deploy
total 8
-rw------- 1 anna anna 399 Nov 21 18:56 id_ed25519
-rw-r--r-- 1 anna anna  93 Nov 21 18:56 id_ed25519.pub
```
Закрытый ключ сразу создан с правами `600`, открытый — `644`: его можно показывать кому угодно.

### Шаг 2. Ключ на сервере
На сервере пользователь `shop` создаёт папку и дописывает открытый ключ (строку из `id_ed25519.pub`, здесь сокращена):
```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
echo "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIIKN… shop-deploy" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
ls -la ~/.ssh
```
Результат (в тренажёре; дата у вас будет своя):
```
total 12
drwx------ 2 shop shop 4096 Nov 21 19:00 .
drwxr-xr-x 4 shop shop 4096 Nov 21 19:00 ..
-rw------- 1 shop shop   56 Nov 21 19:00 authorized_keys
```
`>>`, а не `>`: ключи других разработчиков в файле должны остаться. Обычно эту работу делает `ssh-copy-id` одной командой.

### Шаг 3. Неверные права у ключа
Если закрытый ключ скопировали с правами `644`, SSH откажется (настоящий Ubuntu):
```bash
chmod 644 ~/.ssh/id_ed25519
ssh shop
```
Результат:
```
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@         WARNING: UNPROTECTED PRIVATE KEY FILE!          @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
Permissions 0644 for '/home/anna/.ssh/id_ed25519' are too open.
It is required that your private key files are NOT accessible by others.
This private key will be ignored.
Load key "/home/anna/.ssh/id_ed25519": bad permissions
```
Исправление — `chmod 600 ~/.ssh/id_ed25519`, как в конспекте подключения к серверу.

### Шаг 4. Короткое имя и бэкап
С записью `Host shop` в `~/.ssh/config` (из теории) — вход и копирование бэкапа к себе:
```bash
ssh shop 'ls ~/backups'
scp shop:~/backups/media-2026-11-21.tar.gz ./
```
`ssh` с командой в кавычках выполнит её на сервере и вернёт вывод, `scp` скачает архив в текущую папку. Если сервер недоступен, ошибка та же, что у `curl`: `ssh: connect to host 203.0.113.10 port 22: Connection refused` — не запущен SSH или закрыт порт.

## Частые ошибки
- **Отправить кому-то закрытый ключ.** Это ваш пароль от сервера. Передают только `.pub`; украденный закрытый — удалить его строку из `authorized_keys`.
- **Права `644` у закрытого ключа или `authorized_keys`.** SSH молча игнорирует ключ (на сервере) или пишет `UNPROTECTED PRIVATE KEY FILE!` (у вас). `600`, папка — `700`.
- **`>` вместо `>>` в `authorized_keys`.** Ключи коллег стёрты — они больше не войдут.
- **Отключить вход по паролю, не проверив ключ.** Закрыли себе доступ. Сначала войти по ключу в отдельном окне, потом выключать пароль.
- **Отвечать `yes` на изменившийся отпечаток не думая.** `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!` — либо переустановили сервер, либо подмена. Уточнить, потом `ssh-keygen -R адрес`.
- **Один ключ на всё.** Для CI/деплоя — отдельный ключ: его можно отозвать, не трогая свой.

## Итог
**Ключи**
- `ssh-keygen -t ed25519`; закрытый — у вас (`600`), открытый — в `~/.ssh/authorized_keys` на сервере (`600`, папка `700`).

**Команды**
- `ssh пользователь@сервер`, `ssh сервер 'команда'`, `scp откуда куда`, `ssh-copy-id`; `~/.ssh/config` — короткие имена.

**Безопасность**
- Отпечаток в `known_hosts`; после настройки ключей — вход по паролю и `root` выключены.

## Вопросы на собеседовании
<details><summary>Как работает вход по SSH-ключу?</summary>

На сервере в `authorized_keys` лежит открытый ключ. При подключении сервер предлагает подписать данные сессии; клиент подписывает их закрытым ключом, сервер проверяет подпись открытым. Закрытый ключ не покидает клиент, поэтому его нельзя перехватить в сети, а перебор паролей невозможен.
</details>

<details><summary>Почему SSH не принимает ключ с правами 644?</summary>

Закрытый ключ, читаемый другими пользователями, считается скомпрометированным — SSH отказывается его использовать (`UNPROTECTED PRIVATE KEY FILE`). На сервере аналогично: при слишком открытых правах на домашнюю папку, `~/.ssh` или `authorized_keys` (StrictModes) ключи игнорируются. Нужны `700` на `~/.ssh` и `600` на ключи.
</details>

<details><summary>Как защитить SSH на сервере?</summary>

Вход только по ключам (`PasswordAuthentication no`), запрет входа `root` (`PermitRootLogin no`), отдельный пользователь с `sudo`, файрвол (открыт только 22, при желании — другой порт), `fail2ban` против перебора, отдельные отзываемые ключи для CI и людей.
</details>
