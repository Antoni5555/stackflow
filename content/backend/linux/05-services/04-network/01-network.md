## Теория
Запрос покупателя проходит на сервере такой путь: интернет → порт **80/443** → **Nginx** → порт **8000** на `127.0.0.1` → **Gunicorn** → Django. Если сайт не открывается, ищут, на каком участке оборвалось. Для этого три команды.

**`ss -tlnp`** — какие программы **слушают** порты:
- `-t` — TCP, `-l` — только слушающие (ждут подключений), `-n` — номера портов, а не имена, `-p` — какой процесс (чужие процессы видны только через `sudo`);
- колонка `Local Address:Port` — адрес и порт: `127.0.0.1:8000` — принимает подключения **только с самого сервера**, `0.0.0.0:80` — **со всех адресов**, то есть из интернета.

Gunicorn слушает `127.0.0.1:8000` — из интернета к нему не попасть, только через Nginx. Это правильно: Nginx отдаёт статику, держит HTTPS и защищает от медленных клиентов. `0.0.0.0:8000` у Gunicorn — дыра.

**`curl`** (курс «Веб и API») — отправить запрос на нужный участок: `curl -I http://127.0.0.1:8000/` — прямо в Gunicorn, мимо Nginx; `curl -I http://shop.example/` — через Nginx. Ответ 200 напрямую и 502 через Nginx — проблема в связке Nginx → Gunicorn.

**`ping адрес`** — доходят ли пакеты до машины и сколько идут (`-c 3` — три попытки). Проверяет **машину**, а не сайт: сервер может отвечать на `ping` и не отдавать страницы. Многие хостинги запрещают `ping` вовсе.

Ещё два понятия:
- **порт** — номер «двери» программы на машине: 22 — SSH, 80 — HTTP, 443 — HTTPS, 5432 — PostgreSQL, 8000 — Gunicorn у нас. На одном адресе и порту может слушать только одна программа (`Address already in use`);
- **файрвол** `ufw` пропускает снаружи только разрешённые порты: на сервере магазина — 22, 80, 443. Базу (5432) и Gunicorn (8000) наружу не открывают.

## На практике
Задача: сайт отвечает `502 Bad Gateway`. Найти, какой участок сломан. В тренажёре сетевых команд нет; `curl` и `ping` выполнены на настоящем Ubuntu, а вывод `ss` в шаге 1 — пример сервера магазина в настоящем формате (PID и набор служб у вас будут свои).

### Шаг 1. Кто слушает порты
Слушающие TCP-порты с процессами:
```bash
sudo ss -tlnp
```
Результат (Gunicorn остановлен):
```
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
LISTEN 0      511          0.0.0.0:80         0.0.0.0:*     users:(("nginx",pid=1123,fd=6),("nginx",pid=1122,fd=6))
LISTEN 0      4096         0.0.0.0:22         0.0.0.0:*     users:(("sshd",pid=812,fd=3))
LISTEN 0      200        127.0.0.1:5432       0.0.0.0:*     users:(("postgres",pid=905,fd=6))
```
Nginx на 80 есть, PostgreSQL — только для самого сервера, а порта 8000 нет: Gunicorn не запущен. Nginx пересылает запросы в пустоту — отсюда 502.

### Шаг 2. Прямой запрос в Gunicorn
Проверка участка Nginx → Gunicorn с самого сервера:
```bash
curl -sS http://127.0.0.1:8000/; echo "код $?"
```
Результат:
```
curl: (7) Failed to connect to 127.0.0.1 port 8000 after 0 ms: Couldn't connect to server
код 7
```
Код 7 — соединиться не удалось: на порту никто не слушает. Запускаем службу (тема «Сервисы systemd») и проверяем снова:
```bash
sudo systemctl start gunicorn
ss -tlnp | grep 8000
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/api/v1/products/
```
Результат:
```
LISTEN 0      2048       127.0.0.1:8000       0.0.0.0:*    users:(("gunicorn",pid=8265,fd=4),("gunicorn",pid=8264,fd=4),("gunicorn",pid=8262,fd=4))
200
```
Gunicorn слушает `127.0.0.1:8000` — порт открыт master'ом и унаследован воркерами, поэтому в `users:` три процесса. Django отвечает 200 — значит, и сайт через Nginx заработает.

### Шаг 3. Машина в сети
`ping` проверяет только доступность машины (здесь — самого сервера, `127.0.0.1`):
```bash
ping -c 2 127.0.0.1
```
Результат:
```
PING 127.0.0.1 (127.0.0.1) 56(84) bytes of data.
64 bytes from 127.0.0.1: icmp_seq=1 ttl=64 time=0.065 ms
64 bytes from 127.0.0.1: icmp_seq=2 ttl=64 time=0.073 ms

--- 127.0.0.1 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1046ms
rtt min/avg/max/mdev = 0.065/0.069/0.073/0.004 ms
```
`0% packet loss` — пакеты доходят, `time` — задержка. С вашего компьютера `ping` до сервера показывает, жива ли машина и сеть до неё, — но не работает ли сайт.

## Частые ошибки
- **Gunicorn на `0.0.0.0:8000`.** Приложение доступно из интернета в обход Nginx (без HTTPS и защиты). Только `127.0.0.1`.
- **Считать `ping` проверкой сайта.** Сервер отвечает на `ping` при упавшем Gunicorn; сайт проверяют `curl`.
- **`ss -tlnp` без `sudo`.** У процессов `root` и `www-data` колонка `Process` пуста — кажется, что порт «ничей».
- **Открыть 5432 или 8000 в файрволе «для удобства».** База и приложение становятся целью перебора паролей и сканеров. Наружу — только 22, 80, 443.
- **`Address already in use`.** Порт держит другой процесс (часто — старый Gunicorn, запущенный руками). `sudo ss -tlnp | grep :8000` — найти его PID, остановить.
- **Проверять только через Nginx.** 502 не говорит, кто виноват. Запрос напрямую в `127.0.0.1:8000` разделяет проблему на два участка.

## Итог
**Путь запроса**
- Nginx `0.0.0.0:80/443` → Gunicorn `127.0.0.1:8000` → Django; база `127.0.0.1:5432`.

**Команды**
- `ss -tlnp` — кто слушает (с `sudo` — все процессы); `curl -I` — ответ участка; `ping -c` — доступность машины.

**Безопасность**
- Наружу — 22, 80, 443 (`ufw`); приложение и база — на `127.0.0.1`.

## Вопросы на собеседовании
<details><summary>Чем `127.0.0.1` отличается от `0.0.0.0` в адресе, который слушает программа?</summary>

`127.0.0.1` (loopback) принимает подключения только с этой же машины. `0.0.0.0` — со всех сетевых интерфейсов, то есть из внешней сети тоже. Приложение за обратным прокси слушает `127.0.0.1`, наружу открыт только прокси.
</details>

<details><summary>Сайт отдаёт 502. Как найти причину?</summary>

502 отдаёт Nginx, когда не получил ответ от приложения. Проверить, слушает ли приложение свой порт (`ss -tlnp`), отвечает ли оно напрямую (`curl 127.0.0.1:8000`), состояние службы (`systemctl status`, `journalctl -u`), лог Nginx (`/var/log/nginx/error.log` — `connect() failed (111: Connection refused)`), совпадает ли адрес в `proxy_pass` с адресом в `--bind`.
</details>

<details><summary>Как узнать, какой процесс занял порт?</summary>

`sudo ss -tlnp | grep :порт` (или `sudo lsof -i :порт`, раньше — `netstat -tlnp`): в колонке процесса — имя и PID. Дальше — `ps -p PID -o cmd` и остановка через systemd или `kill`.
</details>
