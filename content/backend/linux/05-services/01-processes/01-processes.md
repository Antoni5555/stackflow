## Теория
**Процесс** — запущенная программа. У каждого — номер **PID**, пользователь, от имени которого он работает, родитель (**PPID** — кто его запустил), занятая память и процессор. Сайт магазина на сервере — это процессы: Nginx, Gunicorn, PostgreSQL.

Gunicorn устроен так:
- **master** — главный процесс: открывает порт, следит за воркерами, не обрабатывает запросы;
- **воркеры** (`--workers 2`) — дочерние процессы, обрабатывают запросы. Упал или завис воркер — master запускает новый.

Посмотреть процессы:
- **`ps aux`** — все процессы: пользователь, PID, `%CPU`, `%MEM`, состояние, время запуска, команда; `ps aux | grep gunicorn` — только нужные;
- `ps -ef` — с PPID (видно, кто чей родитель); `pgrep -a gunicorn` — PID и команды по имени;
- **`top`** или **`htop`** — живая таблица, по умолчанию сверху самые прожорливые по процессору; `q` — выход. В `htop` удобнее: стрелки, `F6` — сортировка, `F9` — сигнал.

Остановить процесс — послать **сигнал** командой **`kill`**:
- `kill PID` — **SIGTERM** (15): «пожалуйста, завершись». Программа заканчивает текущие запросы, закрывает файлы и выходит — **корректная остановка**;
- `kill -9 PID` — **SIGKILL**: процесс убивает ядро мгновенно, без уборки — недописанные файлы, оборванные запросы. Только если `kill` не помог;
- `kill -HUP PID` — **SIGHUP**: многие службы перечитывают настройки (Gunicorn плавно перезапускает воркеры);
- `Ctrl+C` в терминале — **SIGINT** процессу, запущенному в этом терминале.

Посылать сигналы можно только своим процессам; чужим — через `sudo`. Службы вроде Gunicorn обычно останавливают не `kill`, а через `systemctl` (тема «Сервисы systemd») — он пошлёт тот же SIGTERM и не даст службе тут же перезапуститься.

## На практике
Задача: сайт отвечает медленно — найти процессы Gunicorn, убрать зависший воркер и корректно остановить сервер. Команды выполнены на настоящем Ubuntu; пути и PID — как на сервере магазина, длинные строки сокращены. Те же команды работают в тренажёре — там учебные процессы со своими PID.

### Шаг 1. Найти процессы
Процессы Gunicorn со строкой заголовка:
```bash
ps aux | head -n 1
ps aux | grep [g]unicorn
```
Результат:
```
USER         PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
shop        8262  4.5  0.1 113020 22368 ?        Sl   18:55   0:00 /srv/shop/venv/bin/python3 /srv/shop/venv/bin/gunicorn --workers 2 --bind 127.0.0.1:8000 config.wsgi:application
shop        8264 16.2  0.2  58064 43152 ?        S    18:55   0:00 /srv/shop/venv/bin/python3 /srv/shop/venv/bin/gunicorn --workers 2 --bind 127.0.0.1:8000 config.wsgi:application
shop        8265 16.7  0.2  58064 43152 ?        S    18:55   0:00 /srv/shop/venv/bin/python3 /srv/shop/venv/bin/gunicorn --workers 2 --bind 127.0.0.1:8000 config.wsgi:application
```
Три процесса от `shop`: master и два воркера. `[g]unicorn` в шаблоне — приём, чтобы `grep` не нашёл сам себя (в строке его команды стоит `[g]unicorn`, а не `gunicorn`).

### Шаг 2. Кто чей
С родителями — видно, где master:
```bash
ps -o pid,ppid,user,stat,etime -p 8262,8264,8265
```
Результат:
```
    PID    PPID USER     STAT     ELAPSED
   8262       1 shop     Sl         00:10
   8264    8262 shop     S          00:10
   8265    8262 shop     S          00:10
```
У воркеров `PPID 8262` — master; у master родитель — `1` (systemd).

### Шаг 3. Убить зависший воркер
Воркер 8264 завис — `kill -9`:
```bash
kill -9 8264
pgrep -a gunicorn | cut -c1-40
```
Результат:
```
8262 /srv/shop/venv/bin/python3 /srv/sho
8265 /srv/shop/venv/bin/python3 /srv/sho
8479 /srv/shop/venv/bin/python3 /srv/sho
```
Master заметил потерю и запустил воркер 8479. В его логе:
```
[2026-11-21 18:56:05 +0300] [8262] [ERROR] Worker (pid:8264) was sent SIGKILL! Perhaps out of memory?
[2026-11-21 18:56:05 +0300] [8479] [INFO] Booting worker with pid: 8479
```
«Perhaps out of memory» — так выглядит и настоящая беда: ядро убивает процесс сигналом SIGKILL, когда на сервере кончается память.

### Шаг 4. Остановить корректно
SIGTERM master'у — и проверка:
```bash
kill 8262
ps -p 8262; echo $?
```
Результат:
```
    PID TTY          TIME CMD
1
```
Процесса нет, `ps` вернул 1. В логе Gunicorn — аккуратное завершение:
```
[2026-11-21 18:56:06 +0300] [8262] [INFO] Handling signal: term
[2026-11-21 18:56:06 +0300] [8265] [INFO] Worker exiting (pid: 8265)
[2026-11-21 18:56:06 +0300] [8479] [INFO] Worker exiting (pid: 8479)
[2026-11-21 18:56:06 +0300] [8262] [INFO] Shutting down: Master
```
Чужой процесс так не остановить: `kill 1` — `bash: kill: (1) - Operation not permitted`.

## Частые ошибки
- **Сразу `kill -9`.** Процесс не успевает дописать файлы и ответить на запросы. Сначала `kill`, `-9` — если через несколько секунд он всё ещё жив.
- **Убивать воркеры по одному, чтобы перезапустить сайт.** Master тут же запустит новые. Останавливают master — а для службы `systemctl restart`.
- **`kill` службы, которую держит systemd.** С `Restart=always` systemd поднимет её снова. Останавливать — `systemctl stop`.
- **`grep gunicorn` находит сам себя.** В выводе лишняя строка с `grep`. `grep [g]unicorn` или `pgrep`.
- **Путать `%MEM` и свободную память.** Высокий `%MEM` у одного процесса — повод смотреть утечку; общую картину даёт `free -h` или `htop`.
- **Перепутать PID.** `kill` не спрашивает подтверждения. Перед `kill` — проверить PID в `ps`.

## Итог
**Процессы**
- PID, PPID, пользователь, `%CPU`/`%MEM`; Gunicorn — master + воркеры.
- `ps aux`, `ps -ef`, `pgrep -a`, `top`/`htop`.

**Сигналы**
- `kill` — SIGTERM (корректно), `kill -9` — SIGKILL (в крайнем случае), `-HUP` — перечитать настройки, `Ctrl+C` — SIGINT.

## Вопросы на собеседовании
<details><summary>Чем SIGTERM отличается от SIGKILL?</summary>

SIGTERM (15, `kill` по умолчанию) — просьба завершиться: процесс может её перехватить, закончить работу, закрыть ресурсы и выйти. SIGKILL (9) перехватить нельзя — ядро снимает процесс сразу, без очистки. Поэтому сначала SIGTERM, и только если процесс не завершился — SIGKILL.
</details>

<details><summary>Как устроены процессы Gunicorn?</summary>

Master-процесс открывает сокет и управляет воркерами — дочерними процессами, которые обрабатывают запросы. Master перезапускает упавшие воркеры, по SIGHUP плавно меняет их на новые (перечитав код и настройки), по SIGTERM корректно останавливает всё. Число воркеров задают `--workers`, обычно `2 × ядра + 1`.
</details>

<details><summary>Что такое зомби-процесс?</summary>

Процесс, который уже завершился, но родитель ещё не прочитал его код выхода (`wait`). Он не занимает память и процессор, только строку в таблице процессов (`Z` в `STAT`). Много зомби — ошибка в родителе; исчезают, когда родитель их «прочитает» или завершится сам.
</details>
