## Теория
**Переменная окружения** — пара `ИМЯ=значение`, которую процесс получает при запуске от родителя. Так программам передают настройки, не меняя код: Django читает `SECRET_KEY` и `DEBUG` из окружения (`os.environ`, `os.getenv`), библиотеки — `DATABASE_URL`, оболочка — `HOME`, `USER`, `PATH`.

Переменные в оболочке:
- `ИМЯ=значение` — переменная **только этой оболочки**: программы, которые она запустит, её не увидят;
- **`export ИМЯ=значение`** (или `export ИМЯ` для уже заданной) — переменная окружения: её получат все **дочерние** процессы;
- `ИМЯ=значение команда` — переменная только для одной команды: `DEBUG=True python manage.py runserver`;
- `echo $ИМЯ` — значение; `env` — все переменные окружения; `unset ИМЯ` — удалить.

Окружение передаётся **только от родителя к детям** и только в момент запуска. Поэтому `export` в одном терминале не виден в другом, а изменения `.env` не подхватит уже запущенный Gunicorn — его нужно перезапустить.

**`PATH`** — список папок через `:`, где оболочка ищет программы по имени. `ls` — это `/usr/bin/ls`, потому что `/usr/bin` есть в `PATH`. Нет папки в `PATH` — `command not found`, хотя программа на диске есть. Активация `venv` и `pyenv` (прошлый раздел) работают именно так: ставят свою папку **в начало** `PATH`.

Где задавать переменные надолго:
- **`~/.bashrc`** — выполняется при каждом открытии терминала пользователя: `export`, `PATH`, `pyenv init`. После правки — новый терминал или `source ~/.bashrc`;
- **`.env` проекта** — секреты приложения; его читает Django (через `python-dotenv` или `django-environ`) или systemd (`EnvironmentFile=`, следующая тема);
- `/etc/environment` — для всех пользователей системы (на сайтах почти не нужно).

Службы systemd **не читают `~/.bashrc`**: переменные для Gunicorn задают в его unit-файле.

## На практике
Задача: понять, почему Django на сервере не видит переменную, а скрипт — `command not found`. Команды выполнены на настоящем Ubuntu от пользователя `shop`.

### Шаг 1. Что уже есть
Путь поиска программ, домашняя папка и пользователь:
```bash
echo $PATH
echo $HOME $USER
```
Результат:
```
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
/home/shop shop
```

### Шаг 2. Без export и с export
Переменная, а потом дочерний процесс:
```bash
SHOP_ENV=prod
echo "в оболочке: $SHOP_ENV"
bash -c 'echo "в дочерней: $SHOP_ENV"'
export SHOP_ENV
bash -c 'echo "после export: $SHOP_ENV"'
```
Результат:
```
в оболочке: prod
в дочерней:
после export: prod
```
Без `export` переменная живёт только в текущей оболочке — дочерний `bash` (а значит, и `python manage.py`) её не получил.

### Шаг 3. Глазами Python
Так переменные видит Django; `DEBUG` задан только для одной команды:
```bash
DEBUG=True bash -c 'echo "на одну команду: $DEBUG"'
bash -c 'echo "DEBUG потом: $DEBUG"'
python3 -c 'import os; print(os.environ.get("SHOP_ENV"), os.getenv("DEBUG", "False"))'
```
Результат:
```
на одну команду: True
DEBUG потом:
prod False
```
`os.getenv("DEBUG", "False")` вернул значение по умолчанию: `DEBUG` был только у первой команды. Значения окружения — всегда строки: `"False"` в Python истинна, поэтому в `settings.py` пишут `os.getenv("DEBUG") == "True"`.

### Шаг 4. command not found
Скрипт `mytool` лежит в `~/bin`, но этой папки нет в `PATH`:
```bash
mytool
export PATH="$HOME/bin:$PATH"
echo $PATH
```
Результат:
```
mytool: command not found
/home/shop/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```
Теперь `~/bin` — первая в поиске, и `mytool` найдётся. Чтобы так было в каждом новом терминале, ту же строку `export PATH=…` дописывают в `~/.bashrc`. А если `PATH` испортить — `PATH=` — пропадут даже `ls` и `cat` (`bash: ls: No such file or directory`, код 127), пока не откроете новый терминал.

## Частые ошибки
- **Забыть `export`.** Переменная есть в оболочке, но программа её не видит.
- **`export` в одном терминале — ждать её в другом или в службе.** Окружение передаётся только детям при запуске. Надолго — `~/.bashrc`; для службы — unit-файл.
- **Пробелы вокруг `=`.** `SHOP_ENV = prod` — bash ищет команду `SHOP_ENV`. Пишут слитно.
- **`PATH=$HOME/bin` без старого значения.** Все системные команды пропадают. Добавляют к существующему: `PATH="$HOME/bin:$PATH"`.
- **`if os.getenv("DEBUG"):`.** Строка `"False"` — истина, отладка включится на сервере. Сравнивают со строкой.
- **Секреты в `~/.bashrc` или в коде.** Попадают в бэкапы домашней папки и в git. Секреты — в `.env` с правами `600`.

## Итог
**Переменные**
- `ИМЯ=значение` — только оболочка; `export` — и дочерние процессы; `ИМЯ=значение команда` — одна команда.
- Окружение — от родителя к детям, в момент запуска; значения — строки.

**PATH**
- Папки поиска программ через `:`; добавлять в начало: `export PATH="папка:$PATH"`.

**Надолго**
- `~/.bashrc` — терминал пользователя; `.env` и unit-файл — приложение и служба.

## Вопросы на собеседовании
<details><summary>Чем переменная оболочки отличается от переменной окружения?</summary>

Переменная оболочки существует только в текущем процессе bash. Переменная окружения (после `export`) копируется в окружение каждого запускаемого дочернего процесса. Изменение окружения в дочернем процессе не влияет на родителя.
</details>

<details><summary>Почему программа не находится, хотя файл есть на диске?</summary>

Оболочка ищет команды только в папках из `PATH` (и проверяет право `x`). Если папки нет в `PATH`, запускают по пути (`./script.sh`, `/opt/tool/bin/tool`) или добавляют папку в `PATH`. Ещё причины — нет права на выполнение или неверный shebang.
</details>

<details><summary>Как передать настройки Django на сервере?</summary>

Через переменные окружения: в `settings.py` — `os.environ["SECRET_KEY"]`, `os.getenv("DEBUG") == "True"`; значения — в `.env` с правами `600`, которые загружает `python-dotenv`/`django-environ` или systemd (`EnvironmentFile=`). Секреты не хранят в коде и репозитории (12-factor app).
</details>
