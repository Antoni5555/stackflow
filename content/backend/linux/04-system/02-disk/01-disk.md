## Теория
У небольшого сервера диск — 15–40 ГБ, и заканчивается он незаметно: логи растут каждый день, бэкапы копятся, Docker хранит старые образы. Когда места нет, ломается всё сразу: база не может записать данные, Nginx — лог, загрузка фото падает с ошибкой `No space left on device`.

Две команды:
- **`df -h`** — сколько места на **дисках** целиком: размер, занято, свободно, процент, куда подключён (`/` — основной диск). `-h` — в понятных единицах (`G`, `M`);
- **`du -sh путь…`** — сколько занимает **папка** или файл: `-s` — одна строка итога на путь, `-h` — в понятных единицах. `du -sh /var/log/*` — размер каждого файла и папки внутри.

Поиск «кто съел диск» идёт сверху вниз:
1. `df -h` — какой диск заполнен и насколько;
2. `du -sh` по большим папкам (`/var/log`, `/home`, `/srv`, `/var/lib`) — где больше всего;
3. `du -sh папка/*` внутри самой большой — и так до конкретных файлов;
4. найденное удалить, сжать или перенести; повторный `df -h` — проверить, что место освободилось.

Чтобы отсортировать размеры, есть два способа: `du -sh … | sort -h -r` — `sort -h` понимает `1.8G` и `95M`; или `du -s` без `-h` (числа в килобайтах) и `sort -n -r`. Обычный `sort -n` с `1.8G` и `95M` ошибётся: сравнит только `1.8` и `95`.

Обычные «пожиратели» диска на сервере сайта: старые логи (`/var/log`), бэкапы в домашней папке, временные загрузки в `media/tmp`, образы Docker (`/var/lib/docker`), дампы базы. Чистят их регулярно, по расписанию (раздел «Автоматизация»), а не когда сайт уже упал.

Удаляя большой файл, который ещё открыт программой (лог работающего сервиса), место не освобождается, пока программа его держит. Такой лог не удаляют, а обнуляют (`: > app.log` или `truncate -s 0 app.log`) или перезапускают службу.

## На практике
Задача: мониторинг прислал «диск заполнен на 53 % и быстро растёт». Найти, что занимает место, и освободить его. Команды выполнены в терминале сервера, пользователь `shop`.

### Шаг 1. Сколько места
Диски сервера:
```bash
df -h
```
Результат:
```
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        15G  7.9G  7.2G  53% /
tmpfs           982M     0  982M   0% /dev/shm
```
Основной диск `/` — 15 ГБ, занято 7,9. `tmpfs` — память, а не диск, его не трогаем.

### Шаг 2. Какая папка
Три главных подозреваемых:
```bash
du -sh /var/log /srv/shop /home/shop
```
Результат:
```
1.9G	/var/log
34M	/srv/shop
1.9G	/home/shop
```
Код магазина весит 34 МБ — дело не в нём. Логи и домашняя папка — почти по 2 ГБ.

### Шаг 3. Какие файлы
Внутри логов (по убыванию) и бэкапов:
```bash
du -sh /var/log/shop/* | sort -h -r
du -sh ~/backups/*
```
Результат:
```
1.8G	/var/log/shop/app.log.1
95M	/var/log/shop/app.log.2.gz
4.0K	/var/log/shop/app.log
900M	/home/shop/backups/media-2026-11-01.tar.gz
950M	/home/shop/backups/media-2026-11-20.tar.gz
```
Вчерашний лог `app.log.1` — 1,8 ГБ несжатым (позавчерашний сжат — всего 95 МБ). В бэкапах — архив трёхнедельной давности.

### Шаг 4. Освободить и проверить
Старый лог — сжать, старый бэкап — удалить:
```bash
sudo gzip /var/log/shop/app.log.1
rm ~/backups/media-2026-11-01.tar.gz
df -h
```
Результат:
```
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        15G  5.8G  9.3G  39% /
tmpfs           982M     0  982M   0% /dev/shm
```
Свободно 9,3 ГБ вместо 7,2: бэкап ушёл целиком, а лог сжался с 1,8 ГБ до 540 МБ (текст жмётся примерно втрое). Дальше — найти причину: почему лог вырос до 1,8 ГБ за день (ошибка, которая пишется в цикле?) и почему бэкапы не удаляются автоматически.

## Частые ошибки
- **Удалять наугад.** `rm -r /var/log/*` или папки в `/var/lib` ломают службы. Сначала `du`, понять, что это, потом удалять.
- **Удалить открытый лог.** Работающий сервис продолжает писать в удалённый файл — место не освобождается. Обнулить файл или перезапустить службу.
- **`du -sh /` от обычного пользователя.** Сотни `Permission denied` и неполный итог. Ищут по конкретным папкам или через `sudo du`.
- **Сортировать `du -sh` через `sort -n`.** `1.8G` окажется меньше `95M`. Для размеров — `sort -h`, или числа без `-h` (`du -s`) и `sort -n`.
- **Чистить, когда диск уже 100 %.** База и сайт к этому моменту уже падают. Мониторинг с порогом 80 % и регулярная очистка.
- **Бэкапы на том же диске.** Занимают место и пропадут вместе с диском. Хранить на другом сервере, локально — 2–3 последних.

## Итог
**Команды**
- `df -h` — диски целиком, `du -sh путь` — папка или файл; `du -s … | sort -n -r` — по убыванию.

**Порядок поиска**
- `df` → `du` по большим папкам → внутрь самой большой → удалить, сжать или перенести → снова `df`.

**Чистка**
- Логи сжимать (`gzip`), старые бэкапы удалять, открытые логи — обнулять, а не удалять.

## Вопросы на собеседовании
<details><summary>Чем `df` отличается от `du`?</summary>

`df` спрашивает у файловой системы, сколько места занято и свободно на всём разделе. `du` обходит папки и складывает размеры файлов. Их итоги могут не совпасть: удалённые, но открытые файлы `df` учитывает, а `du` уже не видит; ещё часть места резервируется для `root`.
</details>

<details><summary>На сервере закончилось место. Ваши действия?</summary>

`df -h` — какой раздел заполнен; `du -sh` по крупным папкам (`/var/log`, `/var/lib/docker`, `/home`, `/tmp`) и вглубь; удаление старых логов и бэкапов, `docker system prune`, `journalctl --vacuum-size`. Если `df` и `du` расходятся — искать удалённые открытые файлы (`lsof | grep deleted`) и перезапускать держащую их службу. Потом — ротация логов и мониторинг, чтобы не повторилось.
</details>

<details><summary>Почему после удаления большого лога место не освободилось?</summary>

Процесс, который пишет в лог, держит файл открытым: имя из папки удалено, а данные остаются, пока файл не закрыт. Место вернётся после перезапуска процесса. Чтобы не попадать в эту ситуацию, работающий лог обнуляют (`truncate -s 0 файл`) или используют `logrotate` с `copytruncate` либо сигналом службе.
</details>
