## Теория
Иногда один и тот же файл нужен в двух местах: настройки сайта лежат в одной папке, а Nginx читает другую; текущая версия кода — в папке `releases/2026-11-21`, а сервис запускает её по постоянному пути `current`. Копия не годится — исправишь одну, другая устареет. Для этого есть **ссылки**.

**Символическая ссылка** (symlink, `ln -s цель имя_ссылки`) — маленький файл, в котором записан **путь** к цели. Программа, открывшая ссылку, на деле открывает цель:
- в `ls -l` видна буквой `l` в начале и стрелкой: `shop -> /etc/nginx/sites-available/shop`;
- может указывать на папку и на файл на другом диске;
- если цель удалить или переименовать, ссылка становится **битой**: `No such file or directory`;
- относительный путь цели считается **от папки, где лежит ссылка**, а не от текущей — поэтому надёжнее писать абсолютный путь;
- удалить ссылку — `rm имя_ссылки`: удаляется только ссылка, цель остаётся.

**Жёсткая ссылка** (`ln цель имя`, без `-s`) — второе **имя** того же файла. Данные одни, имён два — равноправных: в `ls -l` число после прав (счётчик ссылок) становится 2. Файл исчезает, только когда удалено последнее имя. Ограничения: только для файлов (не папок) и только в пределах одного диска. В работе backend-разработчика встречается редко — главное отличать её от символической.

Где символические ссылки на сервере:
- **Nginx на Ubuntu**: настройки сайтов — в `/etc/nginx/sites-available/`, а читает Nginx только `/etc/nginx/sites-enabled/`. «Включить сайт» — создать ссылку в `sites-enabled`, «выключить» — удалить ссылку; сам файл настроек остаётся;
- **выкладка версий**: `current -> releases/2026-11-21` — переключение на новую версию одной командой и откат на старую;
- `/usr/bin/python3 -> python3.12` — системные «псевдонимы» программ.

## На практике
Задача: включить сайт магазина в Nginx. Настройки уже лежат в `/etc/nginx/sites-available/shop`, папка `sites-enabled` пуста. Команды выполнены в терминале сервера, пользователь `shop`.

### Шаг 1. Включить сайт
Что есть и создание ссылки (папка принадлежит `root` — нужен `sudo`):
```bash
cd /etc/nginx
ls sites-available sites-enabled
sudo ln -s /etc/nginx/sites-available/shop /etc/nginx/sites-enabled/shop
ls -l sites-enabled/shop
```
Результат:
```
sites-available:
shop

sites-enabled:
lrwxrwxrwx 1 root root 31 Nov 21 14:03 sites-enabled/shop -> /etc/nginx/sites-available/shop
```
Размер ссылки — 31 байт: столько символов в пути `/etc/nginx/sites-available/shop`. Права `rwxrwxrwx` у ссылки ничего не значат — проверяются права цели.

### Шаг 2. Через ссылку видна цель
Чтение через ссылку и повторное создание:
```bash
cat sites-enabled/shop
sudo ln -s /etc/nginx/sites-available/shop /etc/nginx/sites-enabled/shop
```
Результат:
```
server {
    listen 80;
    server_name shop.example;
}
ln: failed to create symbolic link '/etc/nginx/sites-enabled/shop': File exists
```
Ссылка уже есть — второй раз `ln -s` не перезаписывает (для замены есть `ln -sf`).

### Шаг 3. Относительный путь — ловушка
Из папки `sites-enabled` создаём ссылку с относительной целью:
```bash
cd sites-enabled
sudo ln -s sites-available/shop shop2
cat shop2
```
Результат:
```
cat: shop2: No such file or directory
```
Ссылка создалась, но путь `sites-available/shop` считается от папки ссылки: `/etc/nginx/sites-enabled/sites-available/shop` — такого нет. На настоящем Ubuntu `ls -l shop2` покажет её как `shop2 -> sites-available/shop`, а Nginx при проверке настроек сообщит, что файла нет. Правильно — `../sites-available/shop` или абсолютный путь.

### Шаг 4. Выключить сайт
Удаляем обе ссылки:
```bash
sudo rm shop2 shop
ls
ls ../sites-available
```
Результат:
```
shop
```
`sites-enabled` пуст, а файл настроек в `sites-available` на месте — сайт выключен, настройки сохранены.

### Шаг 5. Жёсткая ссылка
Для сравнения — оба вида ссылок на `.env` в папке проекта:
```bash
cd /srv/shop
ln -s .env env-link
ln .env env-hard
rm .env
cat env-link
cat env-hard
```
Результат:
```
cat: env-link: No such file or directory
SECRET_KEY=change-me
DEBUG=False
```
Символическая ссылка хранила путь `.env` — имени не стало, ссылка битая. Жёсткая — второе имя тех же данных, они живы, пока есть хоть одно имя.

## Частые ошибки
- **Копировать настройки в `sites-enabled`.** `cp` вместо `ln -s`: правите `sites-available`, а Nginx читает старую копию.
- **Относительная цель от не той папки.** `ln -s sites-available/shop sites-enabled/shop` из `/etc/nginx` даёт битую ссылку: путь считается от `sites-enabled`. Абсолютный путь — надёжно.
- **Перепутать порядок аргументов.** `ln -s цель ссылка` — как у `cp`: откуда, потом куда.
- **`rm -r` по ссылке на папку со `/` на конце.** `rm -r current/` может удалить содержимое цели. Ссылку удаляют без `/`: `rm current`.
- **Удалить файл в `sites-available`, «выключая» сайт.** Настройки пропали насовсем. Выключение — удаление ссылки в `sites-enabled`.
- **Ждать, что жёсткая ссылка переживёт перезапись редактором.** Некоторые редакторы сохраняют файл как новый — связь имён рвётся. На практике — символические.

## Итог
**Символическая**
- `ln -s цель ссылка` — хранит путь; `l` и `->` в `ls -l`; битая, если цели нет; относительная цель — от папки ссылки.

**Жёсткая**
- `ln цель имя` — второе имя тех же данных; только файлы и один диск.

**На сервере**
- Nginx: `sites-available` → ссылка в `sites-enabled` — включить, `rm` ссылки — выключить.

## Вопросы на собеседовании
<details><summary>Чем жёсткая ссылка отличается от символической?</summary>

Жёсткая — ещё одна запись каталога, указывающая на тот же inode: данные общие, имена равноправны, файл удаляется с последним именем; не работает для каталогов и между файловыми системами. Символическая — отдельный файл с путём к цели: может указывать на каталог и другой диск, становится битой при удалении цели.
</details>

<details><summary>Зачем в Nginx папки `sites-available` и `sites-enabled`?</summary>

В `sites-available` хранятся все конфигурации сайтов, а Nginx подключает (`include`) только `sites-enabled`. Включение сайта — символическая ссылка из `sites-enabled` на файл в `sites-available`, выключение — удаление ссылки без потери настроек. Это соглашение пакета Nginx в Debian/Ubuntu.
</details>

<details><summary>Как сделать переключение версий кода без простоя?</summary>

Каждая версия — в своей папке (`releases/<дата>`), сервис запускается из постоянного пути `current`, который — символическая ссылка. Выкладка: подготовить новую папку, переключить ссылку (`ln -sfn releases/new current`), перезапустить сервис; откат — переключить ссылку обратно.
</details>
