## Теория
Скрипт бэкапа готов, но запускать его каждую ночь руками никто не будет. **cron** — служба, которая сама запускает команды по расписанию: бэкап в 03:00, уборку старых архивов, обновление сертификата, отчёт по понедельникам. На Ubuntu она уже работает (`systemctl status cron`).

Расписание каждого пользователя — его **crontab** (cron table). Каждая строка — время и команда:
```
минута час день_месяца месяц день_недели  команда
0      3   *           *     *            /home/shop/bin/backup.sh media
```
- `*` — любое значение; `1-5` — диапазон; `0,30` — список; `*/15` — каждые 15;
- день недели: `0`–`7`, воскресенье — и `0`, и `7`; `1-5` — будни;
- вместо пяти полей можно `@reboot` (после загрузки), `@daily` (= `0 0 * * *`), `@hourly`, `@weekly`.

Команды для работы с crontab:
- `crontab -l` — показать свой; `crontab -e` — открыть в редакторе (при первом запуске спросит, каким: выбирайте `nano`); после сохранения cron проверит строки и установит их;
- `crontab файл` — заменить crontab содержимым файла (удобно хранить расписание в репозитории проекта);
- `crontab -r` — **удалить** весь crontab без вопросов. `r` стоит рядом с `e` на клавиатуре — опечатка стоит всего расписания;
- `sudo crontab -u www-data -l` — crontab другого пользователя (с `sudo`).

**Задача запускается не из вашего терминала.** У cron своё короткое окружение:
- оболочка — `/bin/sh`, не bash; `~/.bashrc` не читается;
- `PATH=/usr/bin:/bin` — нет `~/bin`, `/usr/local/bin`, `pyenv`, вашего `venv`;
- текущая папка — домашняя;
- вывод команды никто не видит: на сервере без почты он пропадает.

Поэтому в crontab — **полные пути** к скриптам и программам (`/srv/shop/venv/bin/python`), а вывод — в свой лог: `>> /home/shop/backups/backup.log 2>&1`. Знак `%` в строке crontab означает перевод строки — в команде его пишут как `\%`, а лучше прячут в скрипт (`date +%F` внутри `backup.sh` работает как обычно).

Время в crontab — **время сервера** (`timedatectl`); на облачных серверах это часто UTC, а не московское.

Есть и системные расписания: файлы в `/etc/cron.d/` (там шестое поле — от чьего имени запускать) и скрипты в `/etc/cron.daily/`, `/etc/cron.weekly/` — так пакеты Ubuntu чистят логи (`logrotate`). Свои задачи сайта удобнее держать в crontab пользователя `shop`.

## На практике
Задача: запускать бэкап каждую ночь в 03:00, а уборку архивов — в 03:30, и проверить, что всё сработало. Команды выполнены на настоящем Ubuntu от пользователя `shop`.

### Шаг 1. Пустой crontab
Своё расписание у пользователя пока не задано:
```bash
crontab -l
echo $?
```
Результат:
```
no crontab for shop
1
```

### Шаг 2. Строки расписания
`crontab -e` открывает редактор (при первом запуске — с выбором редактора). Дописываем в конец две строки и сохраняем. Файл crontab:
```
# m h  dom mon dow   command
0 3 * * * /home/shop/bin/backup.sh media >> /home/shop/backups/backup.log 2>&1
30 3 * * * find /home/shop/backups -name '*.tar.gz' -mtime +7 -delete
```
После выхода из редактора cron проверяет строки и пишет `crontab: installing new crontab`. Пути — полные: скрипт, лог и папка бэкапов. `2>&1` — в лог попадут и ошибки, а не только «Готово». В конце файла должен быть перевод строки — `nano` его ставит сам.

### Шаг 3. Ошибка в расписании
Если перепутать поля, crontab не установится. Проверка строки с минутой `60` и строки с четырьмя полями времени (`-n` — только проверить, не устанавливая):
```bash
crontab -n bad-minute.cron
crontab -n four-fields.cron
crontab -n good.cron
```
Результат:
```
"bad-minute.cron":0: bad minute
errors in crontab file, can't install.
"four-fields.cron":0: bad day-of-week
errors in crontab file, can't install.
The syntax of the crontab file was successfully checked.
```
В `four-fields.cron` строка `0 3 * * /home/shop/bin/backup.sh`: cron взял путь скрипта за пятое поле — день недели. В `crontab -e` после такой ошибки cron спрашивает `Do you want to retry the same edit?` — ответ `y` возвращает в редактор.

### Шаг 4. Сработало ли
Наутро — журнал cron и лог скрипта:
```bash
journalctl -u cron --since today | grep shop
tail -n 1 /home/shop/backups/backup.log
```
Результат:
```
Nov 23 03:00:01 shop-server CRON[48211]: (shop) CMD (/home/shop/bin/backup.sh media >> /home/shop/backups/backup.log 2>&1)
Nov 23 03:30:01 shop-server CRON[48302]: (shop) CMD (find /home/shop/backups -name '*.tar.gz' -mtime +7 -delete)
Готово: /home/shop/backups/media-2026-11-23.tar.gz
```
Журнал говорит только, что cron **запустил** команду; удалась ли она — видно в логе скрипта. Поэтому вывод и пишут в файл.

### Шаг 5. Знак % в crontab
Строка `0 3 * * * tar -czf /home/shop/backups/media-$(date +%F).tar.gz …` прямо в crontab не работает: cron обрезает команду на `%`, и `/bin/sh` получает `tar -czf /home/shop/backups/media-$(date +`. Так это выглядит для `sh`:
```bash
/bin/sh -c 'tar -czf /home/shop/backups/media-$(date +'
```
Результат:
```
/bin/sh: 1: Syntax error: end of file unexpected (expecting ")")
```
Выхода два: `\%` в строке crontab или — лучше — вся логика в скрипте, а в crontab только его запуск.

## Частые ошибки
- **Относительные пути и команды из `~/bin`, `venv`, `pyenv`.** В cron `PATH=/usr/bin:/bin` и `/bin/sh`: `backup.sh: not found`. Полные пути: `/home/shop/bin/backup.sh`, `/srv/shop/venv/bin/python manage.py …`.
- **Вывод никуда.** Задача падает, а никто не знает. `>> лог 2>&1` в конце строки.
- **`%` в команде.** Команда обрезается на `%`. `\%` или скрипт.
- **Скрипт без `chmod +x` или без shebang.** Из терминала `bash backup.sh` работал, а cron запускает файл напрямую — `Permission denied`.
- **Перепутаны поля.** `3 0 * * *` — это 00:03, а не 03:00: сначала минута, потом час.
- **`crontab -r` вместо `-e`.** Расписание удалено без вопроса. Держат копию: `crontab -l > ~/crontab.bak` или файл в репозитории проекта.
- **Время сервера.** В UTC `0 3 * * *` — это 06:00 по Москве. Проверяют `timedatectl`.
- **`crontab файл` с одной строкой.** Команда **заменяет** весь crontab, а не дописывает. Дописать строку, не потеряв остальные: `(crontab -l; echo "строка") | crontab -`.

## Итог
**Расписание**
- `минута час день месяц день_недели команда`; `*`, `a-b`, `a,b`, `*/N`; `@reboot`, `@daily`.

**Команды**
- `crontab -e` — изменить, `-l` — показать, `файл` — заменить, `-r` — удалить всё.

**Окружение cron**
- `/bin/sh`, `PATH=/usr/bin:/bin`, без `.bashrc`, папка — домашняя: полные пути.
- Вывод — в лог `>> файл 2>&1`; запуск виден в `journalctl -u cron`.

## Вопросы на собеседовании
<details><summary>Почему скрипт работает из терминала, а из cron — нет?</summary>

У cron другое окружение: `/bin/sh` вместо bash, короткий `PATH` (`/usr/bin:/bin`), не читается `~/.bashrc` (нет `export`, `venv`, `pyenv`), текущая папка — домашняя. Плюс `%` в строке crontab — перевод строки. Решение — полные пути к программам и файлам, переменные задавать в скрипте или в начале crontab (`PATH=…`), вывод писать в лог.
</details>

<details><summary>Как запустить задачу каждые 15 минут в рабочее время по будням?</summary>

`*/15 9-18 * * 1-5 команда`: минуты 0, 15, 30, 45; часы с 9 до 18; любой день и месяц; дни недели с понедельника по пятницу.
</details>

<details><summary>Чем cron отличается от таймеров systemd?</summary>

cron — простой и есть везде: одна строка — одна задача. Таймер systemd — пара файлов `.timer` и `.service`: дольше писать, зато вывод сам попадает в `journalctl -u`, есть зависимости от других служб, `Persistent=true` запускает пропущенную задачу, если сервер был выключен, и видно `systemctl list-timers`. В Django-проектах периодические задачи часто делают через Celery Beat.
</details>

## Глубже
В тренажёре есть `crontab -l`, `-e` (в `nano`), `-r`, `crontab файл` и `crontab -` с той же проверкой строк, но задачи по времени не запускаются — проверяется только расписание.

Бэкап базы данных (`pg_dump`) по тому же расписанию — курс «Nginx и деплой»; обновление сертификата HTTPS по cron — там же. Таймеры systemd — `man systemd.timer`.
