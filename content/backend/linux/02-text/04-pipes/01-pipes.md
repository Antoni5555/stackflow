## Теория
**Конвейер** `|` передаёт stdout одной команды на вход следующей — без промежуточных файлов. Каждая команда делает одно маленькое дело, а вместе они отвечают на вопросы «кто чаще всего заходит на сайт» или «какая ошибка самая частая».

Команды-кирпичики:
- **`cut -d " " -f 1`** — вырезать поле: `-d` — разделитель, `-f` — номер поля (`-f 1,9` — два поля, `-f 4-` — с четвёртого до конца);
- **`sort`** — отсортировать строки; `-n` — как числа (иначе `10` встанет раньше `9`), `-r` — по убыванию;
- **`uniq -c`** — схлопнуть **соседние** одинаковые строки и посчитать их. Поэтому перед `uniq` всегда `sort`: иначе одинаковые строки, разбросанные по файлу, посчитаются отдельно;
- **`wc -l`** — число строк;
- **`head -n N`** — первые N строк результата.

Классический рецепт «топ-N»:
```
… | sort | uniq -c | sort -n -r | head -n 10
```
отсортировать → посчитать одинаковые → отсортировать по числу по убыванию → взять первые 10.

Строка журнала Nginx, если делить по пробелам:
```
203.0.113.7 - - [21/Nov/2026:10:16:16 +0300] "POST /checkout/ HTTP/1.1" 500 145
```
поле 1 — IP, 4 — время, 6–8 — запрос (`"POST`, `/checkout/`, `HTTP/1.1"`), 9 — код ответа, 10 — размер в байтах. Запрос целиком удобнее вырезать по кавычкам: `cut -d '"' -f 2`.

`sudo` в конвейере действует только на свою команду: `sudo cut … access.log | sort` — `cut` читает закрытый лог с правами `root`, а `sort` работает как обычно.

## На практике
Задача: после всплеска нагрузки выяснить, кто чаще всего обращается к магазину, какие коды отдаёт сайт и какие запросы падают с 500. Журнал Nginx `/var/log/nginx/access.log` закрыт для `shop`, поэтому первую команду — через `sudo`.

### Шаг 1. Только IP
Сколько всего запросов и первые три IP:
```bash
sudo cat /var/log/nginx/access.log | wc -l
sudo cut -d " " -f 1 /var/log/nginx/access.log | head -n 3
```
Результат:
```
24
203.0.113.7
203.0.113.7
198.51.100.23
```

### Шаг 2. Почему сначала sort
`uniq -c` без сортировки:
```bash
sudo cut -d " " -f 1 /var/log/nginx/access.log | uniq -c | head -n 3
```
Результат:
```
      2 203.0.113.7
      1 198.51.100.23
      1 192.0.2.10
```
`uniq` считает только соседние строки: два первых запроса `203.0.113.7` подряд, а остальные семь — дальше по файлу. С сортировкой:
```bash
sudo cut -d " " -f 1 /var/log/nginx/access.log | sort | uniq -c
```
Результат:
```
      3 192.0.2.10
      6 198.51.100.23
      2 198.51.100.99
      9 203.0.113.7
      4 93.184.216.34
```

### Шаг 3. Топ-3
По числу запросов, по убыванию:
```bash
sudo cut -d " " -f 1 /var/log/nginx/access.log | sort | uniq -c | sort -n -r | head -n 3
```
Результат:
```
      9 203.0.113.7
      6 198.51.100.23
      4 93.184.216.34
```
Больше всего запросов — с `203.0.113.7`. Если это бот, его ограничивают в Nginx (курс «Nginx и деплой»).

### Шаг 4. Коды ответа и падающие запросы
Сколько каких кодов и что именно падает:
```bash
sudo cut -d " " -f 9 /var/log/nginx/access.log | sort | uniq -c
sudo grep " 500 " /var/log/nginx/access.log | cut -d '"' -f 2 | sort | uniq -c
```
Результат:
```
     15 200
      2 302
      3 404
      4 500
      4 POST /checkout/ HTTP/1.1
```
Все четыре ответа 500 — на оформление заказа. В логе приложения — какие ошибки и сколько:
```bash
grep ERROR /var/log/shop/app.log | cut -d " " -f 4- | sort | uniq -c
```
Результат:
```
      3 Internal Server Error: /checkout/
      1 OperationalError: connection to server at "127.0.0.1", port 5432 failed
```
`-f 4-` отрезал дату, время и уровень: одинаковые сообщения стали одинаковыми строками и посчитались вместе.

## Частые ошибки
- **`uniq` без `sort`.** Одинаковые строки не рядом — счёт неверный, как в шаге 2.
- **`sort` вместо `sort -n`.** Числа сортируются как текст: `10` раньше `9`, `100` раньше `20`.
- **`sudo` не там.** `cut … access.log | sudo sort` — `cut` всё равно не прочитает лог. `sudo` — у команды, которая открывает файл.
- **Не тот номер поля.** Двойной пробел в строке даёт пустое поле, и номера сдвигаются. Проверяют на нескольких строках: `… | head -n 3`.
- **`cat файл | grep`.** Работает, но `grep шаблон файл` короче и не запускает лишний процесс.
- **Конвейер в тот же файл.** `sort log | uniq > log` — `>` обнуляет файл до чтения. Результат — в другой файл.

## Итог
**Конвейер**
- `|` — stdout одной команды на вход следующей; каждая делает одно дело.

**Кирпичики**
- `cut -d -f` — поле, `sort` (`-n`, `-r`), `uniq -c` — только после `sort`, `wc -l`, `head -n`.

**Рецепт топ-N**
- `cut … | sort | uniq -c | sort -n -r | head -n N`.

## Вопросы на собеседовании
<details><summary>Как найти 10 IP с наибольшим числом запросов в логе Nginx?</summary>

`awk '{print $1}' access.log | sort | uniq -c | sort -nr | head -n 10` (или `cut -d " " -f 1` вместо `awk`). Сортировка перед `uniq -c` обязательна — он считает только подряд идущие строки; `sort -nr` — по числу по убыванию.
</details>

<details><summary>Почему `uniq` без `sort` даёт неверный результат?</summary>

`uniq` сравнивает каждую строку только с предыдущей — так он работает за один проход без памяти обо всём файле. Одинаковые строки, разделённые другими, он считает разными группами. `sort` ставит одинаковые рядом; вместо `sort | uniq` можно `sort -u`, а со счётом — `sort | uniq -c`.
</details>

<details><summary>Что происходит с кодом выхода конвейера?</summary>

По умолчанию код выхода конвейера — код последней команды: `grep ERROR app.log | wc -l` вернёт 0, даже если `grep` ничего не нашёл. В скриптах включают `set -o pipefail` — тогда конвейер завершается с ошибкой, если упала любая команда.
</details>
