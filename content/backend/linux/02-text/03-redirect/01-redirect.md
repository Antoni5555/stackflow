## Теория
У каждой команды два выхода в терминал:
- **stdout** (поток 1) — обычный вывод: найденные файлы, строки лога;
- **stderr** (поток 2) — сообщения об ошибках: `Permission denied`, `No such file or directory`.

На экране они перемешаны, но это разные потоки, и направить их можно отдельно:
- **`> файл`** — stdout в файл (файл перезаписывается), **`>> файл`** — дописать (тема «Редактирование»);
- **`2> файл`** — stderr в файл, `2>> файл` — дописать;
- **`> файл 2>&1`** — оба потока в один файл: `2>&1` значит «поток 2 — туда же, куда сейчас идёт поток 1»;
- **`/dev/null`** — «чёрная дыра»: всё, что туда записано, исчезает. `2> /dev/null` — спрятать ошибки.

Порядок важен. Перенаправления выполняются **слева направо**:
- `> файл 2>&1` — сначала stdout в файл, потом stderr туда же → в файле всё;
- `2>&1 > файл` — сначала stderr туда, куда **пока** идёт stdout (на экран), потом stdout в файл → ошибки остались на экране.

Зачем это на сервере:
- `find / … 2> /dev/null` — убрать десятки `Permission denied` и увидеть только найденное;
- `команда > журнал.log 2>&1` — сохранить весь вывод скрипта бэкапа, в том числе ошибки, чтобы утром понять, что пошло не так (cron, раздел «Автоматизация»);
- `команда 2> errors.txt` — отделить ошибки от результата.

Код выхода от перенаправления не меняется: `find` с ошибками доступа вернёт 1, даже если сообщения спрятаны в `/dev/null`.

## На практике
Задача: найти на сервере все логи и сохранить список, не утонув в сообщениях о закрытых папках. Команды выполнены в терминале сервера, пользователь `shop`.

### Шаг 1. Два потока на одном экране
Поиск лога приложения по всему серверу:
```bash
find / -name app.log
```
Результат:
```
find: ‘/root’: Permission denied
/var/log/shop/app.log
```
Первая строка — stderr: в `/root` пользователю `shop` нельзя. Вторая — stdout, результат.

### Шаг 2. Результат в файл, ошибки отдельно
Только stdout в файл:
```bash
find / -name app.log > found.txt
cat found.txt
```
Результат:
```
find: ‘/root’: Permission denied
/var/log/shop/app.log
```
Ошибка осталась на экране — `>` перенаправил только поток 1. Ошибки — в свой файл:
```bash
find / -name app.log 2> errors.txt
cat errors.txt
```
Результат:
```
/var/log/shop/app.log
find: ‘/root’: Permission denied
```
Теперь наоборот: результат на экране, ошибка — в `errors.txt` (её вывел `cat`).

### Шаг 3. Спрятать ошибки
Все логи на сервере — без шума:
```bash
find / -name "*.log" 2> /dev/null > ~/logs.txt
cat ~/logs.txt
```
Результат:
```
/var/log/nginx/access.log
/var/log/nginx/error.log
/var/log/shop/app.log
```
Ошибки ушли в `/dev/null`, список — в файл. Порядок двух перенаправлений здесь не важен: они про разные потоки.

### Шаг 4. Порядок `2>&1`
Когда оба потока нужны в одном файле, порядок решает. Команда `ls` с существующим и несуществующим файлом (настоящий Ubuntu):
```bash
cd /srv/shop
ls manage.py nope > out.txt 2>&1
cat out.txt
ls manage.py nope 2>&1 > out2.txt
cat out2.txt
```
Результат:
```
ls: cannot access 'nope': No such file or directory
manage.py
ls: cannot access 'nope': No such file or directory
manage.py
```
Первые две строки — содержимое `out.txt`: в нём и ошибка, и результат. Третья строка — ошибка второй команды, она осталась **на экране**: `2>&1` стоял раньше `>`, и stderr ушёл туда, куда в тот момент шёл stdout. Последняя — `out2.txt`, только результат.

## Частые ошибки
- **`2>&1 > файл`.** Ошибки не попадают в файл — нужен порядок `> файл 2>&1`.
- **`> /dev/null` вместо `2> /dev/null`.** Спрятан результат, а ошибки остались. Ошибки — поток 2.
- **Прятать ошибки, которые важны.** `2> /dev/null` у скрипта бэкапа — и о неудаче никто не узнает. В скриптах ошибки пишут в журнал: `>> backup.log 2>&1`.
- **Пробел в `2 >`.** `ls nope 2 > err.txt` — `2` станет аргументом `ls`, а в файл уйдёт stdout. Пишут слитно: `2>`.
- **`> файл` вместо `>>` для журнала.** Каждый запуск стирает предыдущий журнал.
- **Читать и писать один файл.** `grep ERROR app.log > app.log` — `>` обнуляет файл до запуска `grep`, данные потеряны.

## Итог
**Потоки**
- stdout (1) — результат, stderr (2) — ошибки; на экране вместе, перенаправляются отдельно.

**Перенаправления**
- `>`, `>>` — stdout; `2>`, `2>>` — stderr; `> файл 2>&1` — оба; `/dev/null` — выбросить.
- Выполняются слева направо: `2>&1` после `> файл`.

## Вопросы на собеседовании
<details><summary>Что означает `2>&1`?</summary>

Перенаправить файловый дескриптор 2 (stderr) туда же, куда сейчас указывает дескриптор 1 (stdout). Это копия текущего назначения, а не постоянная связь, поэтому порядок важен: `cmd > file 2>&1` пишет оба потока в файл, `cmd 2>&1 > file` — stderr на экран, stdout в файл. В bash есть сокращение `&> file`.
</details>

<details><summary>Что такое `/dev/null` и когда им пользоваться?</summary>

Специальный файл-устройство: запись в него ничего не сохраняет, чтение сразу даёт конец файла. Используют, чтобы выбросить ненужный вывод (`2> /dev/null` — ошибки доступа у `find`, `> /dev/null 2>&1` — полностью тихий запуск в cron), когда важен только код выхода.
</details>

<details><summary>Почему `sort file > file` оставляет пустой файл?</summary>

Перенаправление выполняет оболочка до запуска команды: `> file` обрезает файл до нуля, и `sort` читает уже пустой файл. Пишут во временный файл и переименовывают (`sort file > tmp && mv tmp file`) или используют `sort -o file file`.
</details>
