## Теория
`UPDATE` меняет значения в существующих строках:
```sql
UPDATE таблица
SET столбец1 = выражение1, столбец2 = выражение2
WHERE условие;
```
**`SET`** перечисляет через запятую, какие столбцы и на что поменять. Справа — не только константа, но и выражение от текущих значений строки: `price = price * 1.1` поднимает цену на 10 %, `stock = stock - 1` списывает одну штуку. Все выражения в `SET` считаются по **старым** значениям строки: в `SET price = price * 2, stock = price` остаток получит прежнюю цену, а не удвоенную.

**`WHERE`** выбирает строки — так же, как в `SELECT`. Без `WHERE` меняются **все** строки таблицы. Отменить такой запрос нечем, кроме бэкапа, поэтому привычка простая: сначала `SELECT` с тем же `WHERE` — посмотреть, какие строки попадут под изменение, потом `UPDATE`.

`UPDATE`, под условие которого не попала ни одна строка, — не ошибка: база ответит `UPDATE 0` и ничего не изменит. Если строк меньше, чем ожидали, виновато условие — опечатка в значении, регистр, `= NULL`.

Ограничения таблицы проверяются и при `UPDATE`: если новая цена отрицательная или остаток уходит ниже нуля (`CHECK (stock >= 0)`), команда падает, и не меняется **ни одна** строка — даже те, что прошли бы проверку.

**`RETURNING`** работает, как в `INSERT`: возвращает изменённые строки с новыми значениями. Удобно, чтобы сразу увидеть результат и показать его пользователю.

## Наглядно
**Таблица 1.** Варианты `UPDATE`.

| Запрос | Что меняется |
|---|---|
| `UPDATE products SET stock = 0 WHERE id = 8` | одна строка — по первичному ключу |
| `… SET price = price * 1.1 WHERE category_id = 9` | цены всех книг — выражение от старого значения |
| `… SET price = 990, stock = 20 WHERE id = 13` | два столбца — через запятую |
| `UPDATE products SET stock = 0` | **все** строки таблицы |
| `… SET price = 1 AND stock = 2 …` | ошибка: в `SET` столбцы разделяет запятая, а не `AND` |
| `… RETURNING id, price` | вернуть изменённые строки |

## На практике
Задача: поднять цены на книги и отключить просроченные промокоды.

### Шаг 1. Сначала посмотреть
Книги — категория 9. Прежде чем менять, смотрим, что попадёт под условие:
```sql
SELECT id, name, price
FROM products
WHERE category_id = 9;
```
Результат:
```
 id |           name           |  price
----+--------------------------+---------
 19 | Книга «Python с нуля»    | 1890.00
 20 | Книга «SQL на практике»  | 1590.00
 21 | Книга «Алгоритмы просто» | 1890.00
(3 rows)
```

### Шаг 2. Поднять цены на 10 %
Тот же `WHERE`, только теперь `UPDATE`:
```sql
UPDATE products
SET price = price * 1.1
WHERE category_id = 9
RETURNING id, name, price;
```
Результат:
```
 id |           name           |  price
----+--------------------------+---------
 19 | Книга «Python с нуля»    | 2079.00
 20 | Книга «SQL на практике»  | 1749.00
 21 | Книга «Алгоритмы просто» | 2079.00
(3 rows)

UPDATE 3
```
`UPDATE 3` — изменено три строки, столько же, сколько показал `SELECT`. Результат умножения сохраняется в `numeric(10,2)`, поэтому лишние знаки после запятой округляются до копеек.

### Шаг 3. Несколько условий
Промокоды, которые закончились до 15 апреля 2026, но всё ещё включены, — выключаем:
```sql
UPDATE promo_codes
SET is_active = false
WHERE valid_until < '2026-04-15' AND is_active
RETURNING code, valid_until, is_active;
```
Результат:
```
    code     | valid_until | is_active
-------------+-------------+-----------
 SUMMER25    | 2025-08-31  | f
 BLACKFRIDAY | 2025-11-30  | f
 NEWYEAR20   | 2026-01-15  | f
(3 rows)

UPDATE 3
```
`AND is_active` — короткая запись `is_active = true`: столбец уже логический. Условие не трогает VIP15 — он и так выключен.

### Шаг 4. Ограничение не пускает
Со склада списали по 3 ноутбука двух моделей:
```sql
UPDATE products
SET stock = stock - 3
WHERE id IN (1, 2);
```
Результат:
```
ERROR:  new row for relation "products" violates check constraint "products_stock_check"
DETAIL:  Failing row contains (2, 3, Ноутбук Aster 16 Pro, 89990.00, -1, {"color": "gray", "ram_gb": 32}, 2025-06-01 10:00:00+03).
```
У модели 2 было всего 2 штуки, остаток стал бы −1. Команда отменена целиком: у ноутбука 1 по-прежнему 5 штук, хотя для него списание было бы корректным.

## Частые ошибки
- **`UPDATE` без `WHERE`.** Меняются все строки таблицы. Сначала `SELECT` с тем же условием.
- **`AND` вместо запятой в `SET`.** `SET discount_percent = 20 AND is_active = true` PostgreSQL читает как одно выражение `20 AND (is_active = true)` и падает: `argument of AND must be type boolean`. В MySQL такой запрос молча запишет ерунду.
- **Приоритет `AND` и `OR` в `WHERE`.** `WHERE category_id = 4 OR category_id = 7 AND price < 1500` — это вся категория 4 плюс дешёвые товары категории 7. Ошибка в `SELECT` даёт лишние строки на экране, в `UPDATE` — испорченные данные. Скобки или `IN`.
- **`UPDATE 0` не заметили.** Ошибки нет, а данные не изменились: условие не нашло строк.
- **Ждать новых значений внутри `SET`.** Все выражения считаются от старой строки.

## Итог
**Синтаксис**
- `UPDATE t SET a = …, b = … WHERE …` — столбцы через запятую.
- Справа — выражение от старых значений строки.
- `RETURNING` — изменённые строки с новыми значениями.

**Безопасность**
- Без `WHERE` — все строки; сначала `SELECT` с тем же условием.
- `UPDATE n` — сколько строк изменено; `UPDATE 0` — не ошибка.
- Нарушено ограничение — не меняется ни одна строка.

## Вопросы на собеседовании
<details><summary>Что будет после `UPDATE t SET a = b, b = a`?</summary>

Значения поменяются местами: все выражения в `SET` вычисляются по старой версии строки, а не по уже изменённой. В некоторых других СУБД (например, MySQL) присваивания выполняются по очереди, и оба столбца получат одно значение.
</details>

<details><summary>Как обезопасить себя от `UPDATE` без `WHERE`?</summary>

Перед изменением выполнить `SELECT` с тем же условием и сверить число строк; на рабочей базе — делать изменения в транзакции (`BEGIN`, `UPDATE`, проверка, `COMMIT` или `ROLLBACK`). Консольный клиент можно настроить так, чтобы он сам открывал транзакцию; в коде приложения изменения идут через ORM, где фильтр задаётся явно.
</details>

<details><summary>Как обновить строки на основе данных другой таблицы?</summary>

Подзапросом в `SET` или `WHERE`: `UPDATE order_items SET price = (SELECT price FROM products p WHERE p.id = order_items.product_id) WHERE order_id = 34`. В PostgreSQL есть и `UPDATE … FROM другая_таблица WHERE связь`, похожий на соединение. Подзапросы и соединения разбираются в следующих разделах.
</details>
