## Теория
Три оператора сокращают частые условия.

**`IN`** — значение входит в список: `category_id IN (3, 5)` вместо `category_id = 3 OR category_id = 5`. `NOT IN` — не входит. Список может быть длинным, и запрос остаётся читаемым.

**`BETWEEN a AND b`** — значение в диапазоне, **обе границы включены**: `price BETWEEN 1000 AND 1500` то же, что `price >= 1000 AND price <= 1500`. С датами-временем здесь ловушка: `created_at BETWEEN '2026-03-01' AND '2026-03-31'` берёт 31 марта только до 00:00 — строка `'2026-03-31'` превращается в полночь. Заказ, сделанный 31-го днём, в выборку не попадёт. Для периодов используют полуоткрытый интервал: `>=` начала и `<` начала следующего периода — `created_at >= '2026-03-01' AND created_at < '2026-04-01'`.

**`LIKE`** — поиск по шаблону в строке. В шаблоне два спецсимвола: `%` — любое число любых символов (в том числе ни одного), `_` — ровно один символ. `name LIKE 'Ноутбук%'` — начинается с «Ноутбук», `'%мышь'` — заканчивается, `'%мыш%'` — содержит. Без `%` и `_` `LIKE` работает как обычное `=`. `LIKE` учитывает регистр; **`ILIKE`** (только PostgreSQL) — нет. Для поиска по названию, который вводит покупатель, нужен именно `ILIKE`.

## Наглядно
**Таблица 1.** Операторы и их полная запись.

| Короткая запись | То же самое |
|---|---|
| `category_id IN (3, 5)` | `category_id = 3 OR category_id = 5` |
| `status NOT IN ('new', 'paid')` | `status <> 'new' AND status <> 'paid'` |
| `price BETWEEN 1000 AND 1500` | `price >= 1000 AND price <= 1500` |
| `name LIKE 'Книга%'` | название начинается с «Книга» (с учётом регистра) |
| `name ILIKE '%книга%'` | название содержит «книга» в любом регистре |

**Таблица 2.** Шаблоны `LIKE`.

| Шаблон | Подходит | Не подходит |
|---|---|---|
| `'Ноутбук%'` | `Ноутбук Aster 14` | `Чехол для ноутбука` |
| `'%мышь'` | `Проводная мышь` | `Коврик для мыши` |
| `'%мыш%'` | `Коврик для мыши`, `Проводная мышь` | `Мышь игровая` (у `LIKE` — регистр) |
| `'VIP__'` | `VIP15` | `VIP150` |

## На практике
Задача: три запроса для каталога — товары в ценовом диапазоне, товары двух категорий и поиск по названию.

### Шаг 1. Диапазон цен
Товары от 1000 до 1500 ₽ включительно:
```sql
SELECT id, name, price
FROM products
WHERE price BETWEEN 1000 AND 1500;
```
Результат:
```
 id |          name           |  price
----+-------------------------+---------
  4 | Беспроводная мышь       | 1499.00
  8 | USB-хаб на 4 порта      | 1499.00
 15 | Футболка базовая белая  | 1290.00
 16 | Футболка базовая чёрная | 1290.00
(4 rows)
```

### Шаг 2. Список категорий
Ноутбуки (3) и смартфоны (5):
```sql
SELECT id, name, category_id
FROM products
WHERE category_id IN (3, 5);
```
Результат:
```
 id |          name          | category_id
----+------------------------+-------------
  1 | Ноутбук Aster 14       |           3
  2 | Ноутбук Aster 16 Pro   |           3
  3 | Ноутбук Nimbus Air     |           3
 10 | Смартфон Pixelon 8     |           5
 11 | Смартфон Pixelon 8 Max |           5
 12 | Смартфон Lumo S        |           5
 13 | Чехол для смартфона    |           5
(7 rows)
```

### Шаг 3. Поиск без учёта регистра
Покупатель набрал в поиске «КНИГА» с включённым Caps Lock:
```sql
SELECT id, name
FROM products
WHERE name ILIKE '%КНИГА%';
```
Результат:
```
 id |           name
----+--------------------------
 19 | Книга «Python с нуля»
 20 | Книга «SQL на практике»
 21 | Книга «Алгоритмы просто»
(3 rows)
```
С `LIKE` запрос не нашёл бы ничего.

### Шаг 4. Заказы за месяц
Заказы за март 2026 — полуоткрытым интервалом:
```sql
SELECT id, created_at
FROM orders
WHERE created_at >= '2026-03-01' AND created_at < '2026-04-01';
```
Результат:
```
 id |       created_at
----+------------------------
 22 | 2026-03-01 09:00:00+03
 23 | 2026-03-08 11:11:00+03
 24 | 2026-03-10 14:30:00+03
 25 | 2026-03-15 18:00:00+03
 26 | 2026-03-22 10:40:00+03
 27 | 2026-03-28 21:15:00+03
(6 rows)
```
В учебных данных 31 марта заказов нет, поэтому `BETWEEN '2026-03-01' AND '2026-03-31'` вернул бы то же самое. Но первый же заказ 31-го числа после полуночи потерялся бы, и отчёт за месяц тихо разошёлся бы с реальностью.

## Частые ошибки
- **`BETWEEN` с датами для `timestamptz`.** Правая граница — полночь, весь последний день теряется. Для периодов — `>=` и `<`.
- **Забыли, что `BETWEEN` включает границы.** «От 1000 до 1500» — обе границы входят; если нужно «строго меньше», пишут `<`.
- **`LIKE` для поиска покупателя.** Регистр учитывается: «мышь» не найдёт «Мышь». Для поиска — `ILIKE`.
- **`LIKE` без `%`.** `name LIKE 'мышь'` ищет точное совпадение, а не «содержит».
- **`_` в искомом тексте.** Подчёркивание — спецсимвол: `LIKE '%_old%'` найдёт любой символ перед `old`. Буквальный `_` экранируют: `'%\_old%'`.

## Итог
**IN и BETWEEN**
- `IN (…)` — значение из списка; `NOT IN` — не из списка.
- `BETWEEN a AND b` — обе границы включены.
- Периоды времени — полуоткрытым интервалом `>= начало AND < следующее начало`.

**LIKE**
- `%` — любые символы, `_` — один символ.
- `LIKE` учитывает регистр, `ILIKE` — нет.

## Вопросы на собеседовании
<details><summary>Включает ли `BETWEEN` границы?</summary>

Да, обе: `x BETWEEN a AND b` — это `x >= a AND x <= b`. Для временных меток это опасно: правая граница-дата означает полночь, и последний день периода почти целиком теряется. Поэтому периоды задают как `>= начала AND < начала следующего`.
</details>

<details><summary>Чем `LIKE` отличается от `ILIKE`?</summary>

`LIKE` сравнивает с учётом регистра, `ILIKE` — без. `ILIKE` есть только в PostgreSQL; в других СУБД пишут `lower(name) LIKE lower('%мышь%')`. Шаблон, начинающийся с `%`, не может использовать обычный индекс — на больших таблицах для поиска по тексту берут триграммный индекс или полнотекстовый поиск.
</details>

<details><summary>Чем `IN` удобнее цепочки `OR`?</summary>

Запись короче и читается как список; смысл тот же. Список для `IN` может прийти и из подзапроса: `WHERE user_id IN (SELECT …)`.
</details>
