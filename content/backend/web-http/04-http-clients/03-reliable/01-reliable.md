## Теория
Внешний сервис рано или поздно подводит: служба доставки перегружена и отвечает 503, сеть теряет пакет, платёжка думает 40 секунд. Код магазина должен пережить это и не навредить. Три инструмента:

**Тайм-ауты** (прошлая тема) — запрос не висит бесконечно. Их подбирают по сервису: на соединение — пара секунд, на чтение — сколько сервис обычно отвечает с запасом. Общий тайм-аут view складывается из тайм-аутов всех вызовов и попыток — он должен быть меньше тайм-аута Gunicorn и Nginx (иначе пользователь получит 504, а запрос продолжит выполняться).

**Повторы** (retry) — временную ошибку часто исправляет вторая попытка. Повторяют только то, что может пройти со второго раза:
- ошибки сети и тайм-ауты (`httpx.TransportError`);
- `429`, `502`, `503`, `504` — сервис занят или временно недоступен;
- **не** 4xx: `400`, `401`, `404`, `422` — запрос неверный, второй такой же получит то же.

Повторы делают с паузой, которая растёт (**экспоненциальная задержка**: 1 с, 2 с, 4 с…), часто со случайной добавкой (jitter), и с ограничением числа попыток. Без паузы тысяча клиентов разом добивает и так перегруженный сервис. Если сервис прислал `Retry-After` — ждут сколько сказано.

**Идемпотентность при повторе.** Повторять безопасно идемпотентные запросы (`GET`, `PUT`, `DELETE` — раздел «HTTP подробнее»). С `POST` ловушка: тайм-аут не значит «не выполнилось». Платёжка могла списать деньги, а ответ потерялся по дороге. Повтор — второе списание.

Решение — **ключ идемпотентности**: клиент генерирует уникальный ключ на одну операцию (`uuid4`) и отправляет его в заголовке `Idempotency-Key`. Сервер запоминает ключ и результат; повтор с тем же ключом получает **сохранённый** ответ, а операция второй раз не выполняется. Ключ создают **один раз на операцию** (на оплату заказа 126), а не на каждую попытку — иначе каждый повтор выглядит новой оплатой. Так работают API платёжных систем.

|---|---|---|

## На практике
Задача: магазин узнаёт цену доставки у перегруженной службы и проводит оплату заказа 126 так, чтобы обрыв связи не списал деньги дважды. Сервисы — обработчики через `MockTransport` (тема «HTTP-клиент на Python»); паузы в примере — сотые доли секунды, в настоящем коде — секунды.

### Шаг 1. Повтор с растущей паузой
Функция повторов и служба доставки, которая два раза отвечает 503:
```python
import json
import time
import uuid

import httpx

RETRY_STATUSES = {429, 502, 503, 504}


def call_with_retry(send, attempts=3, delay=0.01):
    for attempt in range(1, attempts + 1):
        try:
            r = send()
        except httpx.TransportError as e:
            print(f"попытка {attempt}: {type(e).__name__}")
        else:
            if r.status_code not in RETRY_STATUSES:
                print(f"попытка {attempt}: {r.status_code}")
                return r
            print(f"попытка {attempt}: {r.status_code}")
        if attempt < attempts:
            time.sleep(delay * 2 ** (attempt - 1))
    raise RuntimeError(f"нет ответа после {attempts} попыток")


quote_calls = []


def busy_delivery(request):
    quote_calls.append(1)
    if len(quote_calls) <= 2:
        return httpx.Response(503, headers={"Retry-After": "1"})
    return httpx.Response(200, json={"price": "340.00"})


delivery = httpx.Client(transport=httpx.MockTransport(busy_delivery))
r = call_with_retry(lambda: delivery.get("https://delivery.example/v1/quote/"))
print(r.json())
```
Результат:
```
попытка 1: 503
попытка 2: 503
попытка 3: 200
{'price': '340.00'}
```
Паузы между попытками — `delay`, `2 × delay`: растут вдвое. `send` — функция без аргументов, которая отправляет запрос: так одну логику повторов можно применить к любому вызову. Сервис прислал `Retry-After: 1` — настоящий код ждал бы не меньше секунды.

### Шаг 2. Повтор POST — двойное списание
Платёжка списывает деньги, но первый ответ теряется по дороге (обработчик выбрасывает `ReadTimeout` уже после списания):
```python
charges = []
saved = {}
lost = {"first": True}


def payment_api(request):
    key = request.headers.get("Idempotency-Key")
    if key in saved:
        return httpx.Response(201, json=saved[key])
    data = json.loads(request.content)
    charges.append(data["amount"])
    result = {"payment": len(charges), "amount": data["amount"]}
    if key:
        saved[key] = result
    if lost["first"]:
        lost["first"] = False
        raise httpx.ReadTimeout("ответ не дошёл", request=request)
    return httpx.Response(201, json=result)


pay = httpx.Client(
    base_url="https://pay.example",
    transport=httpx.MockTransport(payment_api),
)
order = {"order": 126, "amount": "9479.00"}
r = call_with_retry(lambda: pay.post("/v1/payments/", json=order))
print(r.json(), "списаний:", charges)
```
Результат:
```
попытка 1: ReadTimeout
попытка 2: 201
{'payment': 2, 'amount': '9479.00'} списаний: ['9479.00', '9479.00']
```
Клиент видел ошибку и одну удачную попытку, а покупатель заплатил дважды.

### Шаг 3. Ключ идемпотентности
Тот же сценарий, но с ключом — один на всю оплату, во всех попытках:
```python
charges.clear()
lost["first"] = True
headers = {"Idempotency-Key": str(uuid.uuid4())}
r = call_with_retry(
    lambda: pay.post("/v1/payments/", json=order, headers=headers)
)
print(r.json(), "списаний:", charges)
```
Результат:
```
попытка 1: ReadTimeout
попытка 2: 201
{'payment': 1, 'amount': '9479.00'} списаний: ['9479.00']
```
Второй запрос пришёл с тем же ключом, и платёжка вернула сохранённый результат первого. Ключ создан до `call_with_retry`, поэтому одинаков во всех попытках; в магазине его хранят вместе с заказом, чтобы он пережил и перезапуск процесса.

## Частые ошибки
- **Повторять всё подряд.** `422` или `401` повтор не исправит — только нагрузит сервис и задержит ответ пользователю.
- **Повторять без паузы.** Перегруженный сервис получает втрое больше запросов именно тогда, когда не справляется.
- **Бесконечные повторы.** Число попыток и общее время — ограничены; дальше — понятная ошибка пользователю.
- **Повторять `POST` без ключа идемпотентности.** Тайм-аут не значит «не выполнилось»: двойной заказ, двойное списание.
- **Новый ключ на каждую попытку.** `uuid4()` внутри цикла повторов — каждая попытка для сервера новая операция.
- **Повторы на нескольких уровнях.** Повторяет `httpx`-клиент, view и очередь задач — 3 × 3 × 3 = 27 запросов на одну операцию. Повторы — в одном месте.
- **Тайм-ауты длиннее, чем у Gunicorn.** Воркер убит посреди вызова, пользователь видит 502, а платёж мог пройти.

## Итог
**Повторы**
- Только временные ошибки: сеть, тайм-аут, `429`, `502`–`504`; не 4xx.
- Пауза растёт (1, 2, 4 с), учитывают `Retry-After`, число попыток ограничено.

**Идемпотентность**
- `GET`, `PUT`, `DELETE` повторять можно; `POST` — с `Idempotency-Key`.
- Ключ — один на операцию, сервер возвращает сохранённый результат.

## Вопросы на собеседовании
<details><summary>Что такое экспоненциальная задержка и зачем jitter?</summary>

Пауза перед повтором растёт геометрически: `base × 2^попытка` (1, 2, 4, 8 с) с верхней границей — сервис успевает восстановиться, а клиенты не забрасывают его запросами. Jitter — случайная добавка к паузе, чтобы тысячи клиентов, получивших ошибку одновременно, не повторили запрос тоже одновременно («thundering herd»).
</details>

<details><summary>Как сделать повтор POST-запроса безопасным?</summary>

Ключ идемпотентности: клиент генерирует уникальный ключ на операцию и отправляет его в заголовке (`Idempotency-Key`). Сервер сохраняет ключ с результатом (с уникальным индексом, чтобы два параллельных запроса не прошли оба) и на повтор возвращает сохранённый ответ, не выполняя операцию повторно. Ключи хранят ограниченное время.
</details>

<details><summary>Какие ошибки стоит повторять?</summary>

Временные: сетевые ошибки и тайм-ауты (для идемпотентных запросов или с ключом идемпотентности), `429` (после `Retry-After`), `502`, `503`, `504`. Не стоит — ошибки клиента 4xx: запрос неверный, повтор вернёт то же. `500` — осторожно: чаще это ошибка в коде сервиса.
</details>
