## Теория
`GET /api/v1/products/` в настоящем магазине — тысячи товаров. Отдать их одним ответом — мегабайты JSON, секунды на сервере и в приложении. Поэтому коллекции отдают **страницами**, а что именно показать — клиент задаёт **query-параметрами**:
- **фильтр** — `?category=2`, `?price_max=5000`, `?in_stock=true`;
- **сортировка** — `?sort=price` по возрастанию, `?sort=-price` по убыванию (минус — общепринятая запись, так делает DRF в `ordering`);
- **страница** — `?page=2&page_size=20`.

Ответ — **конверт** со страницей и служебными полями:
```
{"count": 6, "next": "/api/v1/products/?category=2&sort=-price&page=2", "previous": null, "results": [...]}
```
- `count` — сколько всего объектов под фильтром (для «Найдено 6 товаров» и числа страниц);
- `next` / `previous` — готовые ссылки на соседние страницы с теми же фильтрами; `null` — страницы нет. Клиент не собирает адрес сам, а идёт по ссылке;
- `results` — сама страница.

Виды пагинации:
- **по номеру страницы** (`page`, `page_size`) — просто и понятно, можно перейти на любую страницу. Минус — `OFFSET` в SQL: для 1000-й страницы база перебирает все предыдущие строки (курс SQL, тема «Сортировка и пагинация»), а если между запросами добавили товар, строки сдвигаются — один товар покажется дважды или пропадёт;
- **по смещению** (`limit`, `offset`) — то же самое другими словами;
- **курсорная** — `?cursor=…`: «дай 20 после товара с такой-то ценой и id». Быстро на любой глубине и без сдвигов, но нельзя прыгнуть на страницу 50. Её используют ленты и бесконечная прокрутка.

Сервер **проверяет** параметры: размер страницы ограничен сверху (иначе `?page_size=1000000` вернёт всю базу), сортировать можно только по разрешённым полям (иначе — 400, а не тихая сортировка по умолчанию), несуществующая страница — 404. Фильтры по полям — тоже явный список, как поля для записи в теме «Атаки на API».

## На практике
Задача: каталог аксессуаров (категория 2) от дорогих к дешёвым, по три товара на странице. Запросы — `curl` к учебному API магазина.

### Шаг 1. Первая и вторая страницы
Первая страница:
```
$ curl -s 'http://localhost:8000/api/v1/products/?category=2&sort=-price'
{"count": 6, "next": "/api/v1/products/?category=2&sort=-price&page=2", "previous": null, "results": [{"id": 8, "name": "Наушники", "price": "6990.00"}, {"id": 7, "name": "Веб-камера", "price": "4590.00"}, {"id": 3, "name": "Клавиатура", "price": "3990.00"}]}
```
Приложение идёт по ссылке `next`:
```
$ curl -s -i 'http://localhost:8000/api/v1/products/?category=2&sort=-price&page=2'
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 301

{"count": 6, "next": null, "previous": "/api/v1/products/?category=2&sort=-price&page=1", "results": [{"id": 2, "name": "Беспроводная мышь", "price": "1499.00"}, {"id": 6, "name": "USB-хаб", "price": "1290.00"}, {"id": 4, "name": "Коврик для мыши", "price": "490.00"}]}
```
`next: null` — страница последняя. Фильтр и сортировка сохранились в ссылках — клиенту не нужно их помнить.

### Шаг 2. Неверные параметры
Сортировка по полю, которого API не разрешает:
```
$ curl -s -i 'http://localhost:8000/api/v1/products/?sort=rating'
HTTP/1.1 400 Bad Request
Content-Type: application/json
Content-Length: 115

{"error": {"code": "invalid_param", "message": "Нельзя сортировать по rating", "field": "sort"}}
```
Страница за пределами списка:
```
$ curl -s -i 'http://localhost:8000/api/v1/products/?page=9'
HTTP/1.1 404 Not Found
Content-Type: application/json
Content-Length: 89

{"error": {"code": "not_found", "message": "Страницы 9 нет", "field": "page"}}
```
Ошибка в параметре видна сразу, а не как «странный порядок товаров».

### Шаг 3. Как это собрано
Логика списка без Django — фильтр, сортировка, срез страницы, ссылки:
```python
from urllib.parse import urlencode

PRODUCTS = [
    {"id": 1, "name": "Ноутбук Air 13", "category": 1, "price": "84990.00"},
    {"id": 2, "name": "Беспроводная мышь", "category": 2, "price": "1499.00"},
    {"id": 3, "name": "Клавиатура", "category": 2, "price": "3990.00"},
    {"id": 4, "name": "Коврик для мыши", "category": 2, "price": "490.00"},
    {"id": 5, "name": "Ноутбук Pro 16", "category": 1, "price": "189990.00"},
    {"id": 6, "name": "USB-хаб", "category": 2, "price": "1290.00"},
    {"id": 7, "name": "Веб-камера", "category": 2, "price": "4590.00"},
    {"id": 8, "name": "Наушники", "category": 2, "price": "6990.00"},
]


def product_list(params, size=3):
    items = [p for p in PRODUCTS if p["category"] == int(params["category"])]
    sort = params["sort"]
    items.sort(key=lambda p: float(p["price"]), reverse=sort.startswith("-"))
    page = int(params.get("page", 1))
    pages = (len(items) + size - 1) // size

    def link(n):
        return "?" + urlencode({**params, "page": n})

    return {
        "count": len(items),
        "next": link(page + 1) if page < pages else None,
        "previous": link(page - 1) if page > 1 else None,
        "ids": [p["id"] for p in items[(page - 1) * size: page * size]],
    }


print(product_list({"category": "2", "sort": "-price"}))
print(product_list({"category": "2", "sort": "-price", "page": "2"}))
```
Результат:
```
{'count': 6, 'next': '?category=2&sort=-price&page=2', 'previous': None, 'ids': [8, 7, 3]}
{'count': 6, 'next': None, 'previous': '?category=2&sort=-price&page=1', 'ids': [2, 6, 4]}
```
Порядок тот же, что у API. Число страниц — деление с округлением вверх: `(6 + 3 − 1) // 3 = 2`. В Django то же делает `Paginator` (курс Django, тема «Сортировка и пагинация»), а в DRF — `PageNumberPagination` с конвертом `count`/`next`/`previous`/`results`.

## Частые ошибки
- **Список без пагинации.** Пока товаров 20, всё работает; при 20 000 падает приложение и тормозит база.
- **Нет верхней границы `page_size`.** `?page_size=1000000` — та же выгрузка всей базы.
- **Сортировка по любому полю из параметра.** `order_by(request.GET["sort"])` даёт 500 на неизвестном поле и позволяет сортировать по служебным полям. Разрешённые поля — списком.
- **Сортировка без уникального ключа.** `sort=price` у товаров с одинаковой ценой даёт разный порядок между запросами — товар «прыгает» со страницы на страницу. Добавляют `id`: `order_by("-price", "id")`.
- **Клиент собирает адрес следующей страницы сам.** Теряет фильтры или ошибается в номере. Ссылки `next`/`previous` даёт сервер.
- **Глагольные адреса для фильтров.** `/api/v1/products/cheap/`, `/api/v1/getByCategory/2/` — это тот же список с параметрами: `?price_max=1000`, `?category=2`.

## Итог
**Параметры**
- Фильтр, сортировка (`-` — по убыванию), страница — в query; сервер их проверяет.

**Ответ**
- Конверт: `count`, `next`, `previous`, `results`; ссылки сохраняют параметры.

**Пагинация**
- По номеру страницы — просто, медленно на глубине; курсорная — быстро и без сдвигов, без перехода на N-ю страницу.

## Вопросы на собеседовании
<details><summary>Чем пагинация через offset отличается от курсорной?</summary>

Offset (`LIMIT 20 OFFSET 10000`) заставляет базу пройти и отбросить все пропущенные строки — чем дальше страница, тем медленнее; при вставке или удалении строк между запросами элементы сдвигаются, появляются дубли и пропуски. Курсорная пагинация запрашивает «следующие 20 после значения ключа сортировки» (`WHERE (price, id) < (…) ORDER BY price DESC, id DESC LIMIT 20`), работает по индексу с одинаковой скоростью и устойчива к изменениям, но не позволяет перейти на произвольную страницу.
</details>

<details><summary>Почему сортировку по параметру нужно ограничивать списком полей?</summary>

Иначе запрос с неизвестным полем даёт 500, а с внутренним (`password`, `cost_price`) позволяет по порядку объектов узнать скрытые значения. Кроме того, сортировка по неиндексированному полю на большой таблице нагружает базу. Разрешённые поля перечисляют явно (`ordering_fields` в DRF), остальное — 400.
</details>

<details><summary>Что вернуть, если запрошена страница за пределами списка?</summary>

Обычно 404 с понятной ошибкой (так делает `PageNumberPagination` в DRF: «Invalid page.»). Пустая первая страница — не ошибка: `200` и `results: []` с `count: 0`.
</details>
