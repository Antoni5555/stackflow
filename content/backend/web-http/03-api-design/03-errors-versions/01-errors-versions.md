## Теория
**Единый формат ошибки.** Клиент API — программа, и разбирать ошибки она должна одним кодом. Если один view отвечает `{"error": "…"}`, другой — `{"detail": "…"}`, а неизвестный адрес — HTML-страницей Django, приложению приходится угадывать. Поэтому для всего API выбирают **одну форму** ошибки, например:
```
{"error": {"code": "validation_error", "message": "Проверьте поля", "fields": {"address": ["Нужен адрес для курьера"]}}}
```
- `code` — стабильный машинный код: по нему программа решает, что делать (`validation_error`, `not_found`, `out_of_stock`). Текст можно переписать, код — нет;
- `message` — текст для человека (разработчика или пользователя);
- `fields` — ошибки по полям для формы в приложении: какое поле подсветить и что написать. Значение — список: у поля бывает несколько ошибок.

Форма одна для **всех** ошибок, включая 404 на неизвестный адрес и 500 — для этого в Django переопределяют `handler404` и `handler500` в корневом `urls.py`. Есть и стандарт — **RFC 9457 «Problem Details»** (`Content-Type: application/problem+json`, поля `type`, `title`, `status`, `detail`); главное — не какой формат, а что он один.

**Код ответа + тело.** Код говорит **класс** проблемы, тело — **подробности**:
- **400** — запрос не разобрать (битый JSON, параметр не того типа);
- **415** — тело не в том формате;
- **422** — JSON разобран, но данные не проходят проверку: ошибки полей в `fields`;
- **404**, **405**, **409** — как в разделе «HTTP подробнее».

В тексте ошибки 500 не показывают traceback и SQL: клиенту — общий текст, подробности — в журнал сервера.

**Версии API.** Мобильное приложение обновляют не все: старая версия на телефонах живёт месяцами. Поэтому API **нельзя ломать**: убрать поле, переименовать, сменить тип — и старые приложения упадут. Совместимые изменения (новое поле, новый необязательный параметр, новый адрес) делают в той же версии. Несовместимые — в **новой версии** рядом со старой:
- в адресе — `/api/v1/…`, `/api/v2/…` — самый распространённый и наглядный способ;
- в заголовке — `Accept: application/vnd.shop.v2+json` — адреса чище, но версию не видно в журнале и браузере.

Старую версию поддерживают, пока ею пользуются, объявляют дату отключения (заголовки `Deprecation` и `Sunset`) и только потом выключают.

## На практике
Задача: ошибки оформления заказа в API магазина и новая версия цены товара. Запросы — `curl` к учебному API магазина, служебные заголовки убраны.

### Шаг 1. Три ошибки — одна форма
Курьерская доставка без адреса:
```
$ curl -s -i -X POST http://localhost:8000/api/v1/orders/ -H 'Content-Type: application/json' -d '{"delivery": "courier"}'
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json
Content-Length: 153

{"error": {"code": "validation_error", "message": "Проверьте поля", "fields": {"address": ["Нужен адрес для курьера"]}}}
```
Обрезанный JSON:
```
$ curl -s -i -X POST http://localhost:8000/api/v1/orders/ -H 'Content-Type: application/json' -d '{"delivery": "courier"'
HTTP/1.1 400 Bad Request
Content-Type: application/json
Content-Length: 71

{"error": {"code": "parse_error", "message": "Тело — не JSON"}}
```
Данные формой:
```
$ curl -s -i -X POST http://localhost:8000/api/v1/orders/ -d 'delivery=pickup'
HTTP/1.1 415 Unsupported Media Type
Content-Type: application/json
Content-Length: 109

{"error": {"code": "unsupported_media_type", "message": "Ожидается Content-Type: application/json"}}
```
Даже 404 на опечатку в адресе (`/api/v1/carts/`, тема «REST и CRUD») пришёл JSON-ом той же формы — в учебном API переопределён `handler404`. Приложению хватает одной функции разбора ошибок.

### Шаг 2. Ошибки полей все сразу
Позиция корзины с несуществующим товаром и нулевым количеством:
```
$ curl -s -i -X POST http://localhost:8000/api/v1/cart/items/ -H 'Content-Type: application/json' -d '{"product": 99, "quantity": 0}'
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json
Content-Length: 201

{"error": {"code": "validation_error", "message": "Проверьте поля", "fields": {"product": ["Такого товара нет"], "quantity": ["Должно быть не меньше 1"]}}}
```
Обе ошибки в одном ответе: пользователь исправит всё за раз, а не по одному полю на запрос. Логика view оформления заказа — упрощённо:
```python
import json


def api_error(status, code, message, fields=None):
    body = {"error": {"code": code, "message": message}}
    if fields:
        body["error"]["fields"] = fields
    return status, json.dumps(body, ensure_ascii=False)


def create_order(raw):
    try:
        data = json.loads(raw)
    except json.JSONDecodeError:
        return api_error(400, "parse_error", "Тело — не JSON")
    fields = {}
    if data.get("delivery") not in ("courier", "pickup"):
        fields["delivery"] = ["Выберите courier или pickup"]
    if data.get("delivery") == "courier" and not data.get("address"):
        fields["address"] = ["Нужен адрес для курьера"]
    if fields:
        return api_error(422, "validation_error", "Проверьте поля", fields)
    return 201, json.dumps({"id": 126, "status": "new"})


print(create_order('{"delivery": "courier"'))
print(create_order('{"delivery": "courier"}'))
print(create_order('{"delivery": "drone"}'))
print(create_order('{"delivery": "pickup"}'))
```
Результат:
```
(400, '{"error": {"code": "parse_error", "message": "Тело — не JSON"}}')
(422, '{"error": {"code": "validation_error", "message": "Проверьте поля", "fields": {"address": ["Нужен адрес для курьера"]}}}')
(422, '{"error": {"code": "validation_error", "message": "Проверьте поля", "fields": {"delivery": ["Выберите courier или pickup"]}}}')
(201, '{"id": 126, "status": "new"}')
```
Все ошибки идут через одну функцию `api_error` — формат не разъедется по view.

### Шаг 3. Новая версия цены
Магазину понадобилась валюта цены. Поменять `"price": "1499.00"` на объект в `v1` — сломать все установленные приложения. Поэтому объект — только в `v2`:
```
$ curl -s http://localhost:8000/api/v1/products/2/
{"id": 2, "name": "Беспроводная мышь", "price": "1499.00"}
```
Новая версия:
```
$ curl -s http://localhost:8000/api/v2/products/2/
{"id": 2, "name": "Беспроводная мышь", "price": {"amount": "1499.00", "currency": "RUB"}}
```
Старые приложения ходят в `v1` и получают строку, новые — в `v2`. Обе версии читают одни и те же данные — различается только представление.

## Частые ошибки
- **Разный формат в разных view.** `{"error": …}`, `{"detail": …}`, `{"message": …}` в одном API — клиент пишет три разбора.
- **HTML-страница 404/500 в API.** Приложение пытается разобрать JSON и падает. `handler404`/`handler500`, отдающие JSON.
- **Только текст без кода.** Клиент сравнивает `message == "Нужен адрес для курьера"` — и ломается, когда текст поправят. Решения — по `code`.
- **Ошибки полей по одной.** Пользователь исправляет поле, отправляет — получает следующую ошибку. Проверяют все поля и возвращают все ошибки.
- **Traceback в ответе 500.** Утечка путей, SQL, версий библиотек. Клиенту — общий текст, подробности — в журнал.
- **Ломающее изменение без новой версии.** Переименовали `price` в `cost` — старые приложения показывают пустую цену.
- **Новая версия на каждое изменение.** Новое поле или адрес совместимы — `v7` через полгода никто не поддержит.

## Итог
**Ошибки**
- Одна форма на весь API: `code` (для программы), `message` (для человека), `fields` (по полям, списками).
- Класс ошибки — код ответа: 400 разбор, 415 формат, 422 поля, 404/405/409; 500 без подробностей.

**Версии**
- Совместимые изменения — в той же версии; ломающие — в новой (`/api/v2/`) рядом со старой.
- Старая версия живёт, пока ею пользуются; отключение объявляют заранее.

## Вопросы на собеседовании
<details><summary>Как оформить ошибки в REST API?</summary>

Правильный код ответа (4xx — ошибка клиента, 5xx — сервера) и единое тело для всех ошибок: машинный код, человекочитаемое сообщение, подробности по полям. Пример стандарта — RFC 9457 (Problem Details, `application/problem+json`). В Django — общий helper и `handler404`/`handler500`, в DRF — `EXCEPTION_HANDLER`, в FastAPI — обработчики исключений.
</details>

<details><summary>Какие изменения API ломают обратную совместимость?</summary>

Удаление или переименование поля, изменение его типа или формата, новое обязательное поле запроса, изменение смысла кода ответа или поведения, удаление адреса. Совместимы: новые необязательные поля и параметры, новые адреса, новые значения там, где клиент готов к неизвестным. Ломающие изменения выпускают в новой версии.
</details>

<details><summary>Где указывать версию API: в URL или в заголовке?</summary>

В URL (`/api/v1/`) — наглядно, видно в журналах, легко проверить в браузере и маршрутизировать на прокси; минус — версия «размножает» адреса. В заголовке (`Accept: application/vnd.shop.v2+json`) — адрес ресурса не меняется, но версию сложнее увидеть и протестировать. Большинство публичных API используют URL.
</details>
