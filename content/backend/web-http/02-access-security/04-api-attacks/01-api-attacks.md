## Теория
У API нет страниц и кнопок, которые «не дают» сделать лишнее: клиент — программа, и злоумышленник отправит любой запрос, который можно составить руками. Самые частые дыры (по списку OWASP API Security Top 10):

**IDOR** (Insecure Direct Object Reference, в OWASP — BOLA): объект выбирают по id из URL и не проверяют, чей он. `GET /api/orders/125/` с токеном Анны отдаёт заказ Бориса — достаточно перебрать номера. Защита — выбирать объект **в рамках пользователя**: `Order.objects.get(pk=pk, user=request.user)`, а чужой — 404 (как «нет такого»), чтобы не подтверждать, что заказ существует.

**Mass assignment** (массовое присвоение): сервер записывает в модель все поля из тела запроса. Клиент присылает `{"name": "Аня", "is_staff": true}` — и становится сотрудником. Защита — **явный список** полей, которые можно менять (форма Django с `fields`, сериализатор DRF); на лишние поля — 400, а не тихое игнорирование, чтобы ошибку клиента было видно.

**Лишние данные в ответе** (excessive data exposure): view отдаёт объект целиком — с хешем пароля, телефоном, внутренними пометками — в расчёте, что клиент «покажет только нужное». Ответ видит любой. Отдают только перечисленные поля.

**Перебор** (brute force): подбор пароля к `POST /api/token/` или кода из SMS без ограничений — миллионы попыток. Защита — **лимит** неудачных попыток за окно времени, по IP и по аккаунту; превышен — **429 Too Many Requests** с `Retry-After`. Лимит нужен и обычным запросам — от перегрузки и выкачивания каталога (`throttle` в DRF, `limit_req` в Nginx).

**Инъекции** — SQL-инъекция (курс Django: ORM и параметры запросов закрывают её, `raw()` с f-строкой — открывает), а для API — ещё и внутренние адреса в параметрах: сервер скачивает «картинку по ссылке» `http://169.254.169.254/…` из внутренней сети (SSRF).

Общее правило: **не доверять ничему, что пришло от клиента** — id, полям тела, заголовкам. Права проверяют на сервере для каждого объекта и каждого действия.

## На практике
Задача: найти и закрыть дыры в API магазина. В учебном API уязвимые версии view живут на `/api/v0/…`, исправленные — на `/api/…`. Токен Анны (пользователь 1) — в `$TOKEN`, служебные заголовки убраны.

### Шаг 1. Чужой заказ
Уязвимая версия:
```
$ curl -s -i http://localhost:8000/api/v0/orders/125/ -H "Authorization: Bearer $TOKEN"
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 44

{"id": 125, "user_id": 2, "total": "980.00"}
```
Анна прочитала заказ Бориса. Исправленная — заказ ищется по id и пользователю из токена:
```
$ curl -s -i http://localhost:8000/api/orders/125/ -H "Authorization: Bearer $TOKEN"
HTTP/1.1 404 Not Found
Content-Type: application/json
Content-Length: 41

{"error": "Заказ не найден"}
```

### Шаг 2. Лишнее поле в профиле
Уязвимая версия записывает всё из тела:
```
$ curl -s -i -X PATCH http://localhost:8000/api/v0/me/ -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"name": "Аня", "is_staff": true}'
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 45

{"id": 1, "name": "Аня", "is_staff": true}
```
Исправленная принимает только `name`:
```
$ curl -s -i -X PATCH http://localhost:8000/api/me/ -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"name": "Аня", "is_staff": true}'
HTTP/1.1 400 Bad Request
Content-Type: application/json
Content-Length: 78

{"error": "Эти поля менять нельзя", "fields": ["is_staff"]}
```
Проверка списка полей — несколько строк:
```python
ALLOWED = {"name", "phone"}


def clean_update(data):
    extra = sorted(set(data) - ALLOWED)
    if extra:
        return None, extra
    return data, []


print(clean_update({"name": "Аня"}))
print(clean_update({"name": "Аня", "is_staff": True, "balance": 10**6}))
```
Результат:
```
({'name': 'Аня'}, [])
(None, ['balance', 'is_staff'])
```
Разрешённое перечислено явно; всё, о чём сервер не знает, отклоняется — в том числе поля, которые добавят в модель позже.

### Шаг 3. Подбор пароля
Пять неверных паролей подряд с одного адреса получили 401. Шестая попытка — уже с верным паролем:
```
$ curl -s -i -X POST http://localhost:8000/api/token/ -H 'Content-Type: application/json' -d '{"email": "anna@shop.example", "password": "anna-pass-1"}'
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 60
Content-Length: 64

{"error": "Слишком много попыток входа"}
```
Пока лимит исчерпан, сервер пароль даже не проверяет: если бы верный пароль проходил, перебор продолжался бы — злоумышленник просто ждал бы ответа не 429. Скользящее окно в учебном API — неудачные попытки за последние 60 секунд:
```python
from collections import defaultdict, deque

LIMIT = 5
WINDOW = 60
failures = defaultdict(deque)


def retry_after(ip, now):
    q = failures[ip]
    while q and q[0] <= now - WINDOW:
        q.popleft()
    if len(q) < LIMIT:
        return 0
    return q[0] + WINDOW - now


for t in [0, 2, 4, 6, 8]:
    failures["10.0.0.7"].append(t)

for now in [10, 59, 60, 61]:
    print(now, retry_after("10.0.0.7", now))
print(retry_after("10.0.0.8", 10))
```
Результат:
```
10 50
59 1
60 0
61 0
0
```
Неудачи были на 0–8-й секунде. На 10-й ждать ещё 50 секунд — до момента, когда самая старая попытка выйдет из окна; на 60-й она вышла, попыток стало 4 — можно снова. Другой адрес лимит не задевает. На сервере с несколькими процессами Gunicorn счётчики хранят в общем месте — Redis или кэше Django, а не в памяти процесса.

## Частые ошибки
- **Проверять только токен.** «Вошёл» не значит «владелец заказа 125». Каждый объект выбирают с фильтром по пользователю.
- **403 на чужой объект.** Подтверждает, что заказ 125 существует; перебором узнают число заказов. Для чужого — 404.
- **`Model(**data)` или `setattr` по всем ключам тела.** Mass assignment; записывать только разрешённые поля.
- **Молча игнорировать лишние поля.** Безопасно, но клиент не узнает об опечатке `nmae`; 400 со списком полей понятнее.
- **Лимит в памяти процесса.** У каждого воркера Gunicorn свой счётчик — лимит умножается на число воркеров и сбрасывается при перезапуске.
- **Лимит только по IP.** Перебор паролей одного аккаунта идёт с тысяч адресов; лимитируют и по аккаунту.
- **Последовательные id как секрет.** UUID вместо числа затрудняет перебор, но не заменяет проверку владельца.

## Итог
**Не доверять клиенту**
- id из URL — проверять владельца (чужое — 404); поля тела — явный список (лишнее — 400); ответ — только нужные поля.

**Лимиты**
- Неудачные входы — лимит по IP и аккаунту, 429 + `Retry-After`; счётчики — в общем хранилище.

**Инъекции**
- ORM и параметры вместо склейки строк; внешние адреса от клиента не скачивать без проверки.

## Вопросы на собеседовании
<details><summary>Что такое IDOR (BOLA) и как от него защититься?</summary>

Уязвимость, при которой сервер выдаёт или меняет объект по идентификатору из запроса, не проверив, что он принадлежит пользователю. Защита — авторизация на уровне объекта: выбирать объект в queryset пользователя (`Order.objects.filter(user=request.user)`), проверять права в каждом view (в DRF — `get_queryset` и object permissions); чужой объект — 404.
</details>

<details><summary>Что такое mass assignment?</summary>

Автоматическое присвоение всех полей из запроса полям модели, из-за которого клиент меняет то, что не должен: `is_staff`, `balance`, `user_id`. Защита — явный список изменяемых полей (allowlist): `ModelForm.Meta.fields`, `read_only_fields` в сериализаторах DRF, отдельные схемы ввода в FastAPI.
</details>

<details><summary>Как защитить вход от подбора пароля?</summary>

Ограничить число неудачных попыток за окно времени по IP и по аккаунту (rate limiting, 429 с `Retry-After`), хранить счётчики в общем хранилище (Redis); одинаковое сообщение для неверной почты и пароля; медленные хеши паролей (PBKDF2, Argon2); для важных аккаунтов — второй фактор и уведомление о входе.
</details>
