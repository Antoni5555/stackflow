## Теория
Два вопроса, которые API задаёт на каждый защищённый запрос:
- **аутентификация** — «кто вы?»: проверить, что клиент тот, за кого себя выдаёт (пароль, токен). Не прошла — **401 Unauthorized**;
- **авторизация** — «что вам можно?»: проверить права на этот ресурс и действие (свой заказ, роль менеджера). Нельзя — **403 Forbidden** (или 404, если существование ресурса — чужая информация).

Сначала всегда аутентификация, потом авторизация: права проверяют у известного пользователя.

**Сессии** (курс Django, раздел «Пользователи и доступ») хорошо работают для сайта в браузере: после входа сервер хранит запись сессии, браузер сам отправляет cookie `sessionid` с каждым запросом. Для API у сессий неудобства: мобильному приложению и сервису партнёра неудобно жить с cookie, а cookie, которую браузер отправляет сам, требует защиты от CSRF.

**Токен** — строка, которую клиент получает при входе и **сам** прикладывает к каждому запросу в заголовке:
```
Authorization: Bearer <токен>
```
`Bearer` — «предъявитель»: кто показал токен, тот и считается его владельцем. Поэтому токен — как пароль: его не кладут в URL, не пишут в журналы и передают только по HTTPS. Токены бывают:
- **непрозрачные** (opaque) — случайная строка, сервер хранит в базе, кому она выдана (`rest_framework.authtoken` в DRF);
- **самодостаточные** — **JWT**: данные о пользователе внутри токена, подписанные сервером; базе не нужно хранить токен (следующая тема).

Схема входа в API: клиент отправляет почту и пароль на `POST /api/token/`, получает токен и срок его жизни, дальше ходит с `Authorization: Bearer …`. Неверный пароль — 401; на неверный пароль не говорят, что именно неверно — почта или пароль, иначе можно узнать, какие почты зарегистрированы.

## На практике
Задача: вход в API магазина и запрос заказов покупателя. Запросы — `curl` к учебному API магазина; служебные заголовки убраны.

### Шаг 1. Получить токен
Неверный пароль:
```
$ curl -s -i -X POST http://localhost:8000/api/token/ -H 'Content-Type: application/json' -d '{"email": "anna@shop.example", "password": "wrong"}'
HTTP/1.1 401 Unauthorized
Content-Type: application/json
Content-Length: 60

{"error": "Неверная почта или пароль"}
```
Верный пароль:
```
$ curl -s -i -X POST http://localhost:8000/api/token/ -H 'Content-Type: application/json' -d '{"email": "anna@shop.example", "password": "anna-pass-1"}'
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 196

{"access": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjEsImlhdCI6MTc5NTI0MDExMCwiZXhwIjoxNzk1MjQxMDEwfQ.xn1uqT_fA6H-oJxMgGCsbV8YhH85mp0JOPpUCtRnqtI", "token_type": "Bearer", "expires_in": 900}
```
Токен действует 900 секунд — 15 минут.

### Шаг 2. Запрос с токеном
Без заголовка:
```
$ curl -s -i http://localhost:8000/api/orders/
HTTP/1.1 401 Unauthorized
Content-Type: application/json
Content-Length: 34

{"error": "Нужен токен"}
```
С токеном Анны (здесь он сокращён до `$TOKEN`):
```
$ curl -s -i http://localhost:8000/api/orders/ -H "Authorization: Bearer $TOKEN"
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 59

{"orders": [{"id": 124, "user_id": 1, "total": "2998.00"}]}
```
Сервер узнал Анну по токену (аутентификация) и вернул только её заказы (авторизация: фильтр по пользователю).

## Частые ошибки
- **401 и 403 наоборот.** 401 — не узнали, кто это (нет или плохой токен); 403 — узнали, но нельзя.
- **Токен в URL.** `/api/orders/?token=…` попадает в журналы сервера, историю браузера и заголовок `Referer`. Только `Authorization`.
- **Разные ошибки для «нет такой почты» и «неверный пароль».** Так перебором узнают зарегистрированные почты. Одно сообщение на оба случая.
- **Только аутентификация.** «Пользователь вошёл» не значит «может видеть заказ 125» — права проверяют на каждый ресурс (тема «Атаки на API»).
- **Токен без срока жизни.** Утёкший токен работает вечно. Короткий срок и обновление — тема JWT.
- **Хранить токены в базе открытым текстом.** Утечка базы — утечка всех токенов; непрозрачные токены хранят хешем.

## Итог
**Два вопроса**
- Аутентификация — кто (401), авторизация — что можно (403/404).

**Токен**
- Выдаётся при входе (`POST /api/token/`), передаётся в `Authorization: Bearer …`, имеет срок.
- Как пароль: только HTTPS, не в URL и журналы.
- Непрозрачный (запись в базе) или JWT (данные внутри, подпись).

## Вопросы на собеседовании
<details><summary>Чем аутентификация отличается от авторизации?</summary>

Аутентификация устанавливает личность: проверка пароля, токена, сертификата. Авторизация решает, разрешено ли этому пользователю действие над ресурсом: роли, права, владение объектом. Аутентификация — первой; её отказ — 401, отказ авторизации — 403 (или 404).
</details>

<details><summary>Почему API на токенах не нужна защита от CSRF?</summary>

CSRF возможен, потому что браузер сам прикладывает cookie к запросу на сайт, даже если запрос инициировала чужая страница. Заголовок `Authorization` браузер сам не добавляет — его ставит код клиента, и чужой сайт не знает токен. Если же токен хранят в cookie, защита от CSRF снова нужна.
</details>

<details><summary>Что такое Bearer-токен?</summary>

Схема аутентификации HTTP (`Authorization: Bearer <token>`), в которой доступ получает любой предъявитель токена — без доказательства, что он его законный владелец. Поэтому токен передают только по HTTPS, хранят как секрет и ограничивают срок жизни.
</details>
