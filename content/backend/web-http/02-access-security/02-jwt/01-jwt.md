## Теория
**JWT** (JSON Web Token, произносят «джот») — токен, внутри которого лежат данные о пользователе, а целостность подтверждает **подпись** сервера. Серверу не нужно хранить выданные токены: достаточно проверить подпись.

JWT — три части через точку: `заголовок.данные.подпись`. Каждая часть — **base64url** (base64 с `-` и `_` вместо `+` и `/`, без `=` на конце):
- **заголовок** — алгоритм подписи: `{"alg": "HS256", "typ": "JWT"}`;
- **данные** (payload, «утверждения», claims) — `sub` (кто: id пользователя), `iat` (когда выдан), `exp` (когда истекает, секунды Unix), можно добавить роль;
- **подпись** — HMAC-SHA256 от строки `заголовок.данные` с секретным ключом сервера (`HS256`), либо подпись закрытым ключом (`RS256`).

Главное, что нужно понимать:
- **данные JWT не зашифрованы** — их прочитает любой, кто видит токен: это просто base64. Пароли, адреса и прочие секреты туда не кладут;
- **подделать данные нельзя**: подпись считается от них, и без секрета новую правильную подпись не получить. Сервер пересчитывает подпись и сравнивает; не совпала — 401;
- сервер **обязательно проверяет `exp`**: истёкший токен — 401.

**Срок жизни и refresh.** JWT нельзя «отозвать» без хранилища на сервере: он действует до `exp`. Поэтому access-токен делают **коротким** (5–15 минут), а для продления выдают **refresh-токен** — долгий (дни), его клиент обменивает на новый access на `POST /api/token/refresh/`. Refresh хранят в базе, и его можно отозвать при выходе или краже.

**Где хранить на клиенте.** Мобильное приложение — в защищённом хранилище системы (Keychain, Keystore). Браузер: `localStorage` удобен, но токен оттуда украдёт любой внедрённый скрипт (XSS); `httpOnly`-cookie скрипт не прочитает, но тогда нужна защита от CSRF. Универсально «правильного» места нет — выбирают по угрозам.

## На практике
Задача: разобрать токен, который API магазина выдал Анне, проверить его подпись и посмотреть, что API ответит на истёкший и подделанный токен. В учебном API JWT собирается стандартной библиотекой (`base64`, `hmac`, `json`), секрет — `shop-demo-secret`.

### Шаг 1. Прочитать токен без секрета
Токен Анны из ответа `POST /api/token/` — делим на части и раскодируем:
```python
import base64
import hashlib
import hmac
import json

token = (
    "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9"
    ".eyJzdWIiOjEsImlhdCI6MTc5NTI0MDExMCwiZXhwIjoxNzk1MjQxMDEwfQ"
    ".xn1uqT_fA6H-oJxMgGCsbV8YhH85mp0JOPpUCtRnqtI"
)
header, payload, signature = token.split(".")


def unb64(part):
    return base64.urlsafe_b64decode(part + "=" * (-len(part) % 4))


print(json.loads(unb64(header)))
print(json.loads(unb64(payload)))
```
Результат:
```
{'alg': 'HS256', 'typ': 'JWT'}
{'sub': 1, 'iat': 1795240110, 'exp': 1795241010}
```
Секрет не понадобился — данные видит любой. `exp − iat = 900` секунд.

### Шаг 2. Проверить подпись
Продолжение того же кода:
```python
signing_input = f"{header}.{payload}".encode()
expected = hmac.new(b"shop-demo-secret", signing_input, hashlib.sha256).digest()
print(hmac.compare_digest(expected, unb64(signature)))
wrong = hmac.new(b"other-secret", signing_input, hashlib.sha256).digest()
print(hmac.compare_digest(wrong, unb64(signature)))
```
Результат:
```
True
False
```
С секретом сервера подпись сходится, с другим — нет. `hmac.compare_digest` сравнивает за постоянное время — по скорости сравнения нельзя подобрать подпись по байту.

### Шаг 3. Истёкший и подделанный токен
Токен с `exp` в прошлом (подписан правильно):
```
$ curl -s -i http://localhost:8000/api/orders/ -H 'Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjEsImlhdCI6MTcwMDAwMDAwMCwiZXhwIjoxNzAwMDAwOTAwfQ.K1OhbXoEeNHLbcU_ImC2ocLWNZQYJLmrD2rRvmINvHc'
HTTP/1.1 401 Unauthorized
Content-Type: application/json
Content-Length: 34

{"error": "Токен истёк"}
```
Токен Анны, в данных которого `sub` заменён на `2` (Борис), подпись — старая:
```
$ curl -s -i http://localhost:8000/api/orders/ -H 'Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjIsImlhdCI6MTc5NTI0MDExMCwiZXhwIjoxNzk1MjQxMDEwfQ.xn1uqT_fA6H-oJxMgGCsbV8YhH85mp0JOPpUCtRnqtI'
HTTP/1.1 401 Unauthorized
Content-Type: application/json
Content-Length: 42

{"error": "Подпись неверна"}
```
Прочитать данные может любой, изменить — никто без секрета.

## Частые ошибки
- **Секреты в данных JWT.** Payload — base64, не шифрование. Пароль, телефон, адрес туда не кладут.
- **Разбирать токен без проверки подписи.** `json.loads(unb64(payload))` на сервере без `compare_digest` — кто угодно впишет `"sub": 1` и войдёт как Анна.
- **Не проверять `exp`.** Украденный токен работает вечно.
- **`alg: none` и подмена алгоритма.** Старые библиотеки принимали токен без подписи, если так написано в заголовке. Сервер сам задаёт допустимые алгоритмы (`algorithms=["HS256"]` в PyJWT), а не верит заголовку токена.
- **Долгий access-токен вместо refresh.** Access на месяц не отозвать. Короткий access + отзываемый refresh.
- **Слабый секрет HS256.** `secret` перебирается по словарю офлайн — по любому выданному токену. Длинный случайный ключ (как `SECRET_KEY`).

## Итог
**Устройство**
- `заголовок.данные.подпись`, base64url; данные — `sub`, `iat`, `exp`; подпись HS256 — HMAC-SHA256 с секретом сервера.
- Данные читает любой, подделать без секрета нельзя.

**Проверка на сервере**
- Подпись (`compare_digest`), допустимый алгоритм, `exp`; иначе 401.

**Срок**
- Короткий access, долгий отзываемый refresh.

## Вопросы на собеседовании
<details><summary>Из чего состоит JWT?</summary>

Из трёх частей base64url через точку: заголовок (алгоритм и тип), полезная нагрузка (claims: `sub`, `iat`, `exp`, роли) и подпись от `base64(header).base64(payload)`. HS256 — HMAC-SHA256 с общим секретом, RS256/ES256 — подпись закрытым ключом, проверка открытым (удобно, когда токены проверяют несколько сервисов).
</details>

<details><summary>Можно ли прочитать данные JWT без ключа? А изменить?</summary>

Прочитать — да: payload только закодирован base64url, не зашифрован. Изменить — нет: подпись вычислена от заголовка и данных, и без ключа новую корректную подпись не получить; сервер обнаружит несовпадение. Шифрованные токены — отдельный стандарт JWE.
</details>

<details><summary>Зачем нужен refresh-токен?</summary>

JWT нельзя отозвать без серверного состояния, поэтому access-токен делают коротким. Чтобы пользователь не входил заново каждые 15 минут, вместе с ним выдают долгоживущий refresh-токен, который хранится на сервере и обменивается на новый access. При выходе или краже refresh отзывают — новые access-токены по нему не выдаются.
</details>
