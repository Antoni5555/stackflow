## Теория
Сайту на страницах хватает `GET` и `POST`. API работает с **ресурсами** — корзиной, позицией корзины, заказом — и для каждого действия над ресурсом есть свой метод:
- **`GET`** — получить ресурс;
- **`POST`** — создать новый ресурс в коллекции (`POST /api/orders/` — новый заказ) или выполнить действие;
- **`PUT`** — **заменить** ресурс целиком: в теле — все поля. Чего нет в теле — того не будет;
- **`PATCH`** — **изменить часть** ресурса: в теле только меняемые поля;
- **`DELETE`** — удалить ресурс;
- **`HEAD`** — как `GET`, но без тела: только заголовки (размер, дата изменения, `ETag`);
- **`OPTIONS`** — какие методы разрешены; браузер посылает его сам перед запросами с другого сайта (тема CORS).

Два свойства методов решают, можно ли повторить запрос:
- **безопасный** метод ничего не меняет на сервере: `GET`, `HEAD`, `OPTIONS`. Их делают ссылки, поисковые роботы, предзагрузка браузера — поэтому `GET` никогда не должен удалять или покупать;
- **идемпотентный** метод даёт тот же **результат на сервере** при повторе: `PUT` (заменить на то же — то же), `DELETE` (удалённое остаётся удалённым), а также все безопасные. `POST` — не идемпотентен: повтор создаст второй заказ. `PATCH` — зависит от тела: `{"quantity": 3}` идемпотентен, «прибавить 1» — нет.

Идемпотентность — про состояние сервера, а не про код ответа: повторный `DELETE` вернёт 404, но позиция удалена и после первого, и после второго.

Повтор — обычное дело: телефон потерял сеть, клиент повторил запрос по таймауту, балансировщик переслал запрос второй раз. Идемпотентные запросы повторять безопасно, `POST` — нет (как сделать повтор `POST` безопасным — раздел «HTTP-клиенты», тема «Надёжные вызовы»).

## На практике
Задача: работа с позицией корзины через API магазина. Позиция 7 — беспроводная мышь (товар 2), одна штука. Запросы отправлены `curl` к учебному API магазина; в ответах убраны служебные заголовки (`Server`, `Date` и заголовки безопасности).

### Шаг 1. Прочитать и изменить количество
Чтение позиции:
```
$ curl -s -i http://localhost:8000/api/cart/items/7/
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 38

{"id": 7, "product": 2, "quantity": 1}
```
Изменить только количество — `PATCH`:
```
$ curl -s -i -X PATCH http://localhost:8000/api/cart/items/7/ -H 'Content-Type: application/json' -d '{"quantity": 3}'
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 38

{"id": 7, "product": 2, "quantity": 3}
```

### Шаг 2. PUT — замена целиком
Тот же «изменить количество» через `PUT` с одним полем:
```
$ curl -s -i -X PUT http://localhost:8000/api/cart/items/7/ -H 'Content-Type: application/json' -d '{"quantity": 5}'
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json
Content-Length: 63

{"error": "Нужны все поля", "missing": ["product"]}
```
`PUT` заменяет ресурс, поэтому сервер требует все поля. С полным телом — `{"product": 2, "quantity": 5}` — ответ `200 OK` и `{"id": 7, "product": 2, "quantity": 5}`.

### Шаг 3. DELETE дважды
Первое удаление:
```
$ curl -s -i -X DELETE http://localhost:8000/api/cart/items/7/
HTTP/1.1 204 No Content
Content-Type: text/html; charset=utf-8
```
Повтор:
```
$ curl -s -i -X DELETE http://localhost:8000/api/cart/items/7/
HTTP/1.1 404 Not Found
Content-Type: application/json
Content-Length: 52

{"error": "Позиции нет в корзине"}
```
Код другой, а состояние то же — позиции нет. Это и есть идемпотентность.

### Шаг 4. HEAD и OPTIONS
Страница товара в учебном API разрешает `GET` и `HEAD` (во view — `@require_http_methods(["GET", "HEAD"])`). `curl -I` отправляет `HEAD`:
```
$ curl -s -I http://localhost:8000/api/products/2/
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=60
ETag: "1499.00-40"
Content-Length: 87
```
Заголовки — как у `GET`, включая `Content-Length: 87`, а тела нет. `OPTIONS` view не обрабатывает:
```
$ curl -s -i -X OPTIONS http://localhost:8000/api/products/2/
HTTP/1.1 405 Method Not Allowed
Content-Type: text/html; charset=utf-8
Allow: GET, HEAD
Content-Length: 0
```
Заголовок `Allow` перечисляет разрешённые методы. Если бы во view было только `["GET"]`, `HEAD` тоже получил бы 405 — его нужно разрешать явно (классы Django `View` делают это сами).

## Частые ошибки
- **`GET` с изменением данных.** `GET /api/cart/clear/` очистит корзину при предзагрузке ссылки браузером или проходе поискового робота. Изменения — только небезопасными методами.
- **`PUT` с частью полей.** По смыслу метода отсутствующие поля сбрасываются; для изменения части — `PATCH`.
- **`POST` для изменения существующей позиции.** Повтор запроса после обрыва сети применит его дважды; изменение — `PATCH`/`PUT` на URL ресурса.
- **Ждать, что идемпотентный метод вернёт тот же код.** Повторный `DELETE` — 404; клиент должен считать его успехом удаления.
- **`PATCH` «прибавить 1».** `{"add": 1}` не идемпотентен: повтор добавит ещё. Передавайте итоговое значение: `{"quantity": 3}`.
- **Забыть `HEAD`.** `@require_http_methods(["GET"])` отвечает на `HEAD` кодом 405 — мониторинг и некоторые клиенты проверяют страницы именно `HEAD`.

## Итог
**Методы**
- `GET`/`HEAD`/`OPTIONS` — читают; `POST` — создаёт; `PUT` — заменяет целиком; `PATCH` — меняет часть; `DELETE` — удаляет.

**Свойства**
- Безопасные — ничего не меняют: `GET`, `HEAD`, `OPTIONS`.
- Идемпотентные — повтор не меняет итог: безопасные, `PUT`, `DELETE`; `POST` — нет, `PATCH` — смотря что в теле.

## Вопросы на собеседовании
<details><summary>Чем `PUT` отличается от `PATCH`?</summary>

`PUT` заменяет ресурс целиком представлением из тела — отсутствующие поля сбрасываются, поэтому клиент присылает все поля. `PATCH` применяет частичное изменение — только присланные поля. `PUT` идемпотентен, `PATCH` — только если тело задаёт итоговые значения.
</details>

<details><summary>Что такое идемпотентность и какие методы идемпотентны?</summary>

Свойство, при котором повторное выполнение запроса не меняет состояние сервера сверх первого выполнения. Идемпотентны `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`; `POST` — нет. Код ответа при повторе может отличаться (повторный `DELETE` — 404), важен итог на сервере.
</details>

<details><summary>Зачем нужен `HEAD`?</summary>

Получить заголовки без тела: проверить, существует ли ресурс, его размер (`Content-Length`), дату изменения или `ETag` — не скачивая содержимое. Используют мониторинг, проверка ссылок, кэши. Ответ на `HEAD` должен совпадать по заголовкам с ответом на `GET`.
</details>
