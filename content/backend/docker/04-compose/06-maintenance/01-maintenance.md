## Теория
Через пару месяцев деплоев сервер магазина пишет `No space left on device`: база перестаёт принимать заказы, `docker build` падает. Docker ничего не удаляет сам — копятся старые версии образа магазина, кэш сборки, остановленные контейнеры, анонимные тома и бесконечные журналы контейнеров. Обслуживание — понять, что занимает место, и убрать лишнее, **не задев данные**.

**Что занимает место** — `docker system df`: образы, контейнеры, тома и кэш сборки; колонка `RECLAIMABLE` — сколько можно освободить. `docker system df -v` — подробно по каждому объекту. Плюс обычные `df -h` и `du -sh` (курс Linux).

**Команды очистки (`prune`)** — удаляют неиспользуемое:
- `docker container prune` — все **остановленные** контейнеры;
- `docker image prune` — «висящие» образы (без имени — старые версии после пересборки с тем же тегом); с **`-a`** — все образы, из которых не создан ни один контейнер. Старые версии магазина уходят — но откатиться на них потом можно только скачав из реестра;
- `docker builder prune` — кэш сборки; следующая сборка будет медленнее;
- `docker volume prune` — тома, не подключённые ни к одному контейнеру. С Docker 23 без `-a` удаляет только **анонимные** тома, с **`-a`** — и именованные. **Том базы, чей контейнер в этот момент удалён или остановлен через `down`, тоже «не подключён»** — и будет удалён;
- `docker system prune` — контейнеры, сети, висящие образы и кэш сразу; `-a` — все неиспользуемые образы; `--volumes` — ещё и тома. С Docker 23 — только **анонимные**: именованный том базы `system prune --volumes` не тронет, его удаляет только `volume prune -a`. В Docker до 23 `--volumes` удалял и именованные.

`-f` — без вопроса «Are you sure?». `--filter` — ограничить: `label=…`, `until=24h` (старше суток).

**Безопасная последовательность на сервере:** посмотреть `system df` → `container prune` → `image prune` (или `-a`, если старые версии есть в реестре) → `builder prune`. Тома — только вручную, по имени, после бэкапа. Если «лишний» том оказался базой — данных больше нет.

**Журналы контейнеров.** По умолчанию драйвер `json-file` пишет всё, что вывел контейнер, в файл `/var/lib/docker/containers/<id>/<id>-json.log` **без ограничения размера**. Болтливый контейнер за месяц съедает гигабайты. Ограничение — `--log-opt max-size=10m --log-opt max-file=3` (до трёх файлов по 10 МБ), в compose — ключ `logging`, для всего сервера — в `/etc/docker/daemon.json`. Настройка действует на контейнеры, созданные после неё.

**Таблица 1.** Команды очистки.

| Команда | Что удаляет | Риск |
|---|---|---|
| `docker container prune` | остановленные контейнеры | их слои изменений |
| `docker image prune` | висящие образы | нет |
| `docker image prune -a` | все образы без контейнеров | откат только через реестр |
| `docker builder prune` | кэш сборки | медленная следующая сборка |
| `docker volume prune` | анонимные неподключённые тома | данные анонимных томов |
| `docker volume prune -a` | **все** неподключённые тома | **данные баз** |
| `docker system prune [-a] [--volumes]` | всё вместе; `--volumes` — анонимные тома | данные анонимных томов (до Docker 23 — всех) |

**Таблица 2.** Журналы.

| Где | Как ограничить |
|---|---|
| `docker run` | `--log-opt max-size=10m --log-opt max-file=3` |
| compose | `logging: {driver: json-file, options: {max-size: "10m", max-file: "3"}}` |
| весь сервер | `/etc/docker/daemon.json`: `"log-opts": {"max-size": "10m", "max-file": "3"}` |

## На практике
Задача: посмотреть, что занимает место, и проверить, что удаляют команды `prune`. Чтобы не задеть чужие данные на учебном сервере, все объекты помечены меткой `sf-lesson=1`, а очистка ограничена фильтром `--filter label=sf-lesson=1`. Команды выполнены на Ubuntu 24.04 с Docker Engine 29.

### Шаг 1. Что занимает место
Сводка по всему Docker на сервере разработчика:
```bash
docker system df
```
Результат:
```
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          21        14        6.812GB   1.993GB (29%)
Containers      18        11        13.29MB   606.2kB (4%)
Local Volumes   29        15        821.4MB   430.4MB (52%)
Build Cache     285       0         10.29GB   5.134GB
```
Больше всего — кэш сборки (10 ГБ, из них 5 ГБ освобождается) и образы. Тома: 29, из них подключено 15 — половину места занимают неподключённые. Среди них могут быть как мусор, так и базы остановленных проектов — разбираться по одному.

### Шаг 2. Остановленные контейнеры
Остановленный контейнер с меткой и его удаление:
```bash
docker run --label sf-lesson=1 --name old-job alpine:3 true
docker container prune -f --filter label=sf-lesson=1
```
Результат:
```
Deleted Containers:
2c7cfec037e145a460786803ca4d13da182701d2ca4c962487662a0695219059

Total reclaimed space: 4.096kB
```
Без фильтра удалились бы все остановленные контейнеры сервера.

### Шаг 3. Именованный том не удаляется без -a
Создаём неподключённый именованный том и чистим тома:
```bash
docker volume create --label sf-lesson=1 junk
docker volume prune -f --filter label=sf-lesson=1
docker volume ls --filter label=sf-lesson=1
docker volume prune -a -f --filter label=sf-lesson=1
```
Результат:
```
junk
Total reclaimed space: 0B
DRIVER    VOLUME NAME
local     junk
Deleted Volumes:
junk

Total reclaimed space: 0B
```
Без `-a` Docker 23+ трогает только анонимные тома — именованный `junk` остался. С `-a` удалился и он. Именно `-a` удалит `shop_pgdata`, если в этот момент контейнер базы удалён. `system prune --volumes` в Docker 23+ тоже ограничен анонимными томами — в его вопросе так и написано: «all anonymous volumes not used by at least one container».

### Шаг 4. Образы без контейнеров
Образ, из которого не создано ни одного контейнера:
```bash
docker image prune -f --filter label=sf-lesson=1
docker image prune -a -f --filter label=sf-lesson=1
```
Результат:
```
Total reclaimed space: 0B
Deleted Images:
untagged: junk:1
deleted: sha256:324dc6bc4ad3603472af0043cc22f597b92a24a305a85871e2a6c7e9c692bab4
deleted: sha256:7940f804ec6b13a52f65d4c6c35663b8b26fc5dff812b4c17ba31d38c24095e9
deleted: sha256:e699b1eb30c24a03fd8f67de46f4217324f6fcdeddc8e0dae99cf7240dbc3b09

Total reclaimed space: 12.67kB
```
Обычный `image prune` убирает только висящие образы, а у этого есть имя — он остался. `-a` удалил образ с именем: из него не создан ни один контейнер. Так уходят и старые версии магазина — поэтому перед `-a` убедитесь, что они есть в реестре.

### Шаг 5. Ограничить журналы
Контейнер с ограничением журнала и где этот журнал лежит:
```bash
docker run -d --name worker --log-opt max-size=10m --log-opt max-file=3 alpine:3 sleep 30
docker inspect -f '{{json .HostConfig.LogConfig}}' worker
docker inspect -f '{{.LogPath}}' worker
```
Результат:
```
3d05c4c7073d97523c65be1f4a940e0a8c507fe744214bc1d70ed4d3f26d7485
{"Type":"json-file","Config":{"max-file":"3","max-size":"10m"}}
/var/lib/docker/containers/3d05c4c7073d97523c65be1f4a940e0a8c507fe744214bc1d70ed4d3f26d7485/3d05c4c7073d97523c65be1f4a940e0a8c507fe744214bc1d70ed4d3f26d7485-json.log
```
Журнал этого контейнера не вырастет больше 30 МБ. Без настройки `Config` пустой, и файл растёт бесконечно. В compose то же — у сервиса:
```yaml
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

## Частые ошибки
- **`docker volume prune -a` «чтобы почистить».** Удаляет все неподключённые тома, в том числе базы остановленных проектов. На сервере тома удаляют только по имени и после бэкапа.
- **Надеяться на версию Docker.** `system prune --volumes` в Docker 23+ трогает только анонимные тома, а в более старых — и именованные. На незнакомом сервере сначала `docker version`, а лучше — не чистить тома этими командами вовсе.
- **`docker compose down` + `volume prune -a`.** После `down` том базы не подключён ни к одному контейнеру — `prune -a` его удалит.
- **`image prune -a` без реестра.** Старые версии магазина удалены, откатиться не на что. Публикуйте образы (тема 3.06) или оставляйте последние версии.
- **Журналы без ограничения.** `/var/lib/docker/containers/*-json.log` на десятки гигабайт. `max-size`/`max-file` для сервисов или в `daemon.json`; применяется к новым контейнерам.
- **Удалять файлы в `/var/lib/docker` руками.** Ломает состояние Docker. Только команды `docker …`.
- **Чистить, не посмотрев.** Сначала `docker system df` (и `-v`), потом точечные `prune` — понятно, что именно освобождается.

## Итог
**Посмотреть**
- `docker system df [-v]`: образы, контейнеры, тома, кэш сборки, `RECLAIMABLE`.

**Почистить безопасно**
- `container prune`, `image prune`, `builder prune`; `image prune -a` — если старые версии в реестре.

**Осторожно**
- `volume prune -a` удаляет и именованные тома с данными (`system prune --volumes` — только анонимные, до Docker 23 — все); тома — вручную, по имени, после бэкапа.

**Журналы**
- `json-file` без ограничения растёт бесконечно: `max-size`, `max-file` (в `run`, compose или `daemon.json`).

## Вопросы на собеседовании
<details><summary>Как освободить место, которое занимает Docker на сервере?</summary>

Посмотреть `docker system df`, затем удалить остановленные контейнеры (`container prune`), висящие и ненужные образы (`image prune`, с `-a` — если версии есть в реестре), кэш сборки (`builder prune`). Тома трогать только осознанно — в них данные. И ограничить размер журналов контейнеров, чтобы проблема не вернулась.
</details>

<details><summary>Чем опасен `docker volume prune -a`?</summary>

Он удаляет все тома, не подключённые к контейнерам в момент запуска команды, — и анонимные, и именованные. Если проект остановлен (`docker compose down`), его том с базой не подключён и будет удалён безвозвратно. `docker system prune --volumes` с Docker 23 удаляет только анонимные тома, но в старых версиях вёл себя так же опасно.
</details>

<details><summary>Почему на сервере кончается место из-за логов Docker?</summary>

Драйвер журналов по умолчанию `json-file` сохраняет весь вывод контейнера в файл без ограничения размера. Долго работающий и много пишущий контейнер создаёт файлы на гигабайты. Решение — опции `max-size` и `max-file` (на контейнер, в compose или глобально в `daemon.json`) или другой драйвер журналов.
</details>
