## Теория
Django в контейнере, PostgreSQL — в другом. В `settings.py` по привычке `HOST = "localhost"` — и `connection refused`, хотя база работает и `docker ps` её показывает. Чтобы контейнеры говорили друг с другом, нужно понимать, как Docker устраивает сеть.

У каждого контейнера своя сеть (тема 1.01): свой IP-адрес, свои порты и **свой `localhost`**. Внутри контейнера `localhost` — это **сам контейнер**, а не сервер и не соседний контейнер. Поэтому `localhost:5432` из контейнера Django указывает в пустоту: PostgreSQL слушает в другом контейнере.

Сети Docker:
- **`bridge`** (по умолчанию) — сюда попадают все контейнеры, запущенные без `--network`. Связь по IP есть, но **имена контейнеров не работают**, а IP меняются при каждом пересоздании;
- **пользовательская сеть** — `docker network create shop`. Контейнеры в ней находят друг друга **по имени**: встроенный DNS Docker превращает `shop-db` в IP контейнера. Django пишет `HOST = "shop-db"`, и это работает при любых пересозданиях;
- `host` и `none` — особые: контейнер без своей сети (видит сеть сервера) и совсем без сети. В веб-проектах почти не нужны.

Подключить контейнер: `docker run --network shop …` или к работающему — `docker network connect shop shop-db`.

**Публикация порта (`-p`) нужна только для связи с внешним миром** — с сервером и интернетом. Контейнеры внутри одной сети ходят друг к другу напрямую по внутреннему порту (`shop-db:5432`) без всяких `-p`. Базу наружу вообще публиковать не стоит: меньше открытых портов — меньше атак.

Compose (раздел 4) сам создаёт для проекта пользовательскую сеть, где имя сервиса — это имя хоста.

## На практике
Задача: научить «приложение» в контейнере находить базу по имени. Вместо Django используем `pg_isready` из образа `postgres` — он проверяет, отвечает ли PostgreSQL по адресу. Команды выполнены на Ubuntu 24.04 с Docker Engine 29 (имена в выводе заменены на учебные).

### Шаг 1. Какие сети есть
Список сетей на сервере:
```bash
docker network ls
```
Результат (сети других проектов убраны):
```
NETWORK ID     NAME      DRIVER    SCOPE
9014cedbefdf   bridge    bridge    local
7eb959d6a32b   host      host      local
9cd89ae10769   none      null      local
```
Три сети есть всегда. Каждый проект compose добавляет свою, вида `проект_default`.

### Шаг 2. По имени в bridge — нельзя
База и проверка запущены без `--network`, то есть обе в `bridge`:
```bash
docker run -d --name shop-db -e POSTGRES_PASSWORD=shop postgres:16
docker run --rm postgres:16 pg_isready -h shop-db
docker run --rm alpine:3 ping -c 1 shop-db
```
Результат:
```
a1a29a53f7d2dbe3381a10c34d223d71a81d698f710e4f0f906e26d51afc82f9
shop-db:5432 - no response
ping: bad address 'shop-db'
```
В сети по умолчанию имя `shop-db` никто не знает.

### Шаг 3. Своя сеть
Создаём сеть и подключаем к ней работающую базу:
```bash
docker network create shop
docker network connect shop shop-db
docker run --rm --network shop postgres:16 pg_isready -h shop-db
```
Результат:
```
0f1045c12407c37def86842dfe87b1c3d794c7299a647f76e37beae0b631b07f
shop-db:5432 - accepting connections
```
В пользовательской сети встроенный DNS нашёл контейнер по имени. Порт базы мы не публиковали — внутри сети он доступен и так.

### Шаг 4. localhost — это сам контейнер
Та же проверка, но с привычным `localhost`:
```bash
docker run --rm --network shop postgres:16 pg_isready -h localhost
```
Результат:
```
localhost:5432 - no response
```
Контейнер проверки искал PostgreSQL у себя, а там его нет. Именно это происходит с Django и `HOST = "localhost"`.

### Шаг 5. Кто в сети и как её удалить
Имена и адреса участников сети, затем удаление:
```bash
docker network inspect --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{end}}' shop
docker network rm shop
```
Результат:
```
shop-db 172.23.0.2/16
Error response from daemon: error while removing network: network shop has active endpoints (name:"shop-db" id:"548f596497a4")
exit status 1
```
IP выдаёт Docker — рассчитывать на него нельзя, только на имя. Сеть с подключёнными контейнерами не удаляется: сначала `docker rm -f shop-db`, потом `docker network rm shop`.

## Частые ошибки
- **`localhost` для соседнего контейнера.** `connection refused` или `no response`: это сам контейнер. Пишите имя контейнера (или имя сервиса в compose).
- **Контейнеры в `bridge` по умолчанию.** Имена не работают, IP меняются. Создайте свою сеть и запускайте с `--network`.
- **`-p` для связи между контейнерами.** Не нужен: внутри сети — внутренний порт напрямую. `-p` — только для доступа снаружи.
- **Опубликованная наружу база.** `-p 5432:5432` на сервере с публичным IP — база доступна из интернета, и её начнут подбирать. Наружу — только Nginx; базу — разве что `-p 127.0.0.1:5432:5432` для отладки.
- **Опубликованный порт изнутри сети.** Из контейнера `shop-db:55432` не работает: 55432 — порт **сервера**, внутри сети база слушает 5432.
- **Жёстко прописанный IP контейнера.** После пересоздания адрес другой. Только имена.

## Итог
**localhost**
- Внутри контейнера — сам контейнер; к соседям так не попасть.

**Сети**
- `bridge` по умолчанию — без имён; своя сеть (`docker network create`) — связь по имени через встроенный DNS.
- `--network` при запуске, `network connect` — к работающему.

**Порты**
- Внутри сети — внутренний порт напрямую; `-p` — только для доступа снаружи. Базу наружу не публикуют.

## Вопросы на собеседовании
<details><summary>Как контейнеры находят друг друга?</summary>

В пользовательской сети Docker работает встроенный DNS: имя контейнера (и сетевой алиас, а в compose — имя сервиса) превращается в его IP. В сети `bridge` по умолчанию такого DNS нет, там остаются только IP-адреса, которые меняются при пересоздании.
</details>

<details><summary>Почему из контейнера с Django не подключиться к базе по `localhost`?</summary>

У каждого контейнера своё сетевое пространство: `localhost` внутри — это сам контейнер. База работает в другом контейнере со своим адресом. Нужно обращаться к ней по имени контейнера или сервиса в общей сети: `HOST = "db"`.
</details>

<details><summary>Зачем публиковать порт, если контейнеры и так видят друг друга?</summary>

Публикация (`-p`) нужна только для связи снаружи: с сервера, из интернета, с ноутбука разработчика. Внутри Docker-сети контейнеры обращаются друг к другу по внутренним портам напрямую. Чем меньше опубликовано, тем меньше поверхность атаки: в бою наружу обычно открыт только Nginx.
</details>
