## Теория
Один и тот же образ магазина запускается на ноутбуке, на тестовом сервере и в бою. Отличаются только настройки: пароль базы, `DEBUG`, адрес почтового сервера. Пересобирать образ под каждое место нельзя — образ должен быть один. Настройки передают **переменными окружения** при запуске (как в курсе Linux, тема «Переменные окружения»), а приложение читает их через `os.environ` (Python, раздел 9).

Как передать:
- **`-e ИМЯ=значение`** — одну переменную;
- **`-e ИМЯ`** без значения — взять значение из окружения сервера, где запускается `docker run`. Если на сервере её нет, внутри будет пустая строка;
- **`--env-file .env`** — все переменные из файла. Формат строгий: `ИМЯ=значение` по одной на строку, `#` — комментарий. **Кавычки не убираются** — `GREETING="привет"` даст значение вместе с кавычками, — а пробелы вокруг `=` — ошибка.

Секреты (пароли, ключи API, `SECRET_KEY`):
- **не кладут в образ** — ни файлом `.env`, ни инструкцией `ENV` в Dockerfile. Образ уходит в реестр, его скачивают другие, а всё внутри можно прочитать (`docker history`, `docker run … env`). `.env` — в `.gitignore` и `.dockerignore` (раздел 3);
- переменные контейнера видны тому, кто может выполнить `docker inspect` или `docker exec`. Доступ к Docker на сервере равен доступу `root`;
- для серьёзной защиты есть Docker secrets и внешние хранилища (Vault) — в этом курсе достаточно `--env-file` с правами `600`.

Официальные образы описывают свои переменные на странице Docker Hub: у `postgres` — `POSTGRES_PASSWORD`, `POSTGRES_USER`, `POSTGRES_DB`. Учтите: они работают только при **первой** инициализации базы. Поменять пароль в переменной для уже созданного тома — пароль в базе не изменится.

## На практике
Задача: передать настройки базы магазина из файла, убедиться, как Docker читает этот файл, и посмотреть, кто видит секреты. Команды выполнены на Ubuntu 24.04 с Docker Engine 29 (имена контейнеров в выводе заменены на учебные).

### Шаг 1. Файл настроек
Файл `.env` на сервере (права `600`, курс Linux):
```
# База магазина
POSTGRES_PASSWORD=s3cr3t
POSTGRES_DB=shop
GREETING="привет"
```
Смотрим, что увидит контейнер:
```bash
docker run --rm --env-file .env alpine:3 env
```
Результат:
```
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
HOSTNAME=25e0bff3da95
POSTGRES_PASSWORD=s3cr3t
POSTGRES_DB=shop
GREETING="привет"
HOME=/root
```
Комментарий пропущен, переменные на месте — а `GREETING` получил значение **с кавычками**. Пароль `"s3cr3t"` в кавычках стал бы паролем из восьми символов.

### Шаг 2. Пробел вокруг =
Добавим в файл строку `SPACED = 1` — так часто пишут по привычке:
```bash
docker run --rm --env-file .env alpine:3 env
```
Результат:
```
docker: --env-file: invalid env file (.env): variable 'SPACED ' contains whitespaces

Run 'docker run --help' for more information
```
Контейнер не запустился вовсе. Убираем пробелы: `SPACED=1`.

### Шаг 3. Значение из окружения сервера
`-e ИМЯ` без значения берёт переменную сервера:
```bash
docker run --rm -e SHOP_ENV alpine:3 sh -c 'echo "SHOP_ENV=[$SHOP_ENV]"'
export SHOP_ENV=prod
docker run --rm -e SHOP_ENV alpine:3 sh -c 'echo "SHOP_ENV=[$SHOP_ENV]"'
```
Результат:
```
SHOP_ENV=[]
SHOP_ENV=[prod]
```
Пока на сервере переменной не было, внутри — пустая строка, без ошибки. Так передают секреты из CI: в скрипте деплоя они есть в окружении, а в истории команд — только имя.

### Шаг 4. Кто видит секреты
Запускаем базу с файлом и смотрим её настройки:
```bash
docker run -d --name shop-db --env-file .env postgres:16
docker inspect --format '{{json .Config.Env}}' shop-db
```
Результат:
```
245b1d4c3e4a1fd0fa707c8084b0c0fb7cf7d55b19b642a475eb025cb49e7b8d
["POSTGRES_PASSWORD=s3cr3t","POSTGRES_DB=shop","GREETING=\"привет\"","PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/lib/postgresql/16/bin","GOSU_VERSION=1.19","LANG=en_US.utf8","PG_MAJOR=16","PG_VERSION=16.15-1.pgdg13+2","PGDATA=/var/lib/postgresql/data"]
```
Пароль виден открытым текстом. `--env-file` прячет секрет от истории терминала и от `ps`, но не от тех, у кого есть доступ к Docker. Поэтому пользователей в группе `docker` на сервере держат минимум.

## Частые ошибки
- **Кавычки в `--env-file`.** `PASSWORD="s3cr3t"` — пароль вместе с кавычками. Пишите без кавычек. (В compose `env_file` и в `python-dotenv` кавычки убираются — привычка из них здесь подводит.)
- **Пробелы вокруг `=`.** `invalid env file … contains whitespaces` — контейнер не запустится.
- **Секрет в Dockerfile.** `ENV SECRET_KEY=…` или `COPY .env .` — секрет навсегда в образе и в реестре. Только при запуске.
- **`.env` в git.** Пароли в истории репозитория — даже после удаления файла. `.env` в `.gitignore`, в репозитории — `.env.example` без значений.
- **Сменили `POSTGRES_PASSWORD` — пароль не поменялся.** Переменная работает только при первой инициализации тома. Для существующей базы — `ALTER USER … PASSWORD`.
- **`-e ИМЯ` без переменной на сервере.** Тихо передаётся пустая строка. Проверяйте обязательные настройки в приложении (`os.environ["…"]` упадёт сразу, а `os.getenv` — нет).

## Итог
**Передать**
- `-e ИМЯ=значение`, `-e ИМЯ` (из окружения сервера), `--env-file файл`.

**Формат файла**
- `ИМЯ=значение`, без пробелов вокруг `=`, кавычки остаются в значении, `#` — комментарий.

**Секреты**
- Не в образе и не в git; файл с правами `600`; видны всем, у кого есть доступ к Docker.

## Вопросы на собеседовании
<details><summary>Как передать настройки в контейнер без пересборки образа?</summary>

Переменными окружения при запуске: `-e`, `--env-file`, в compose — `environment` и `env_file`. Приложение читает их через `os.environ`. Так один образ работает в разработке, на тесте и в бою с разными настройками (принцип 12-factor app).
</details>

<details><summary>Почему нельзя класть секреты в образ?</summary>

Образ уходит в реестр и на все серверы, его могут скачать другие; всё, что в нём лежит, включая `ENV` и скопированные файлы, читается командами `docker history`, `docker inspect` или из контейнера. Удалить секрет из уже опубликованного образа нельзя — только сменить сам секрет. Секреты передают при запуске или через специализированные хранилища.
</details>

<details><summary>Видно ли значение переменной окружения контейнера снаружи?</summary>

Да: `docker inspect` показывает `Config.Env` открытым текстом, `docker exec контейнер env` — тоже. Поэтому доступ к Docker на сервере дают только тем, кому можно знать секреты (это фактически `root`). Для строгой защиты используют Docker secrets или внешние хранилища, которые передают секрет файлом.
</details>
