## Теория
Новый разработчик два дня не может запустить магазин: у него Python 3.10 вместо 3.12, PostgreSQL 14 вместо 16, на macOS другой драйвер, а Redis вообще не установлен. На сервере — третья комбинация версий. «У меня работает» — главная беда командной разработки и деплоя.

**Docker** упаковывает программу вместе со всем, что ей нужно: интерпретатором нужной версии, библиотеками, системными пакетами, настройками. Такая упаковка запускается одинаково на ноутбуке, у коллеги и на сервере — где угодно, где есть Docker.

Три главных слова:
- **образ** (image) — упаковка, «шаблон»: файлы системы и программы плюс команда запуска. Образ только читают, он не меняется. Пример — `postgres:16`: Debian, PostgreSQL 16 и скрипт запуска;
- **контейнер** — запущенный экземпляр образа: процесс со своей файловой системой (копией образа с тонким слоем для изменений), своими переменными окружения и сетью. Из одного образа можно запустить сколько угодно контейнеров;
- **реестр** (registry) — хранилище образов. Главный — **Docker Hub**: там официальные образы `postgres`, `python`, `nginx`, `redis`. `docker run` скачивает образ оттуда, если его нет локально.

**Контейнер — не виртуальная машина.** Виртуальная машина эмулирует целый компьютер со своим ядром ОС, загружается минуту и занимает гигабайты. Контейнер — обычный процесс Linux, которому ядро показывает «свою» файловую систему, процессы и сеть (механизмы namespaces и cgroups). Ядро у всех контейнеров общее — хостовое, поэтому контейнер стартует за доли секунды. На macOS и Windows Docker Desktop запускает для этого маленькую виртуальную машину с Linux.

Docker состоит из двух частей: **демон** `dockerd` (служба, которая скачивает образы и запускает контейнеры) и **клиент** `docker` — команда, которой вы управляете демоном.

## На практике
Задача: убедиться, что контейнер — отдельная система со своими файлами, и что одна команда даёт одинаковый Python на любой машине. Команды выполнены на Ubuntu 24.04 с Docker Engine 29.

### Шаг 1. Первый контейнер
Запускаем образ `alpine` (минимальный Linux, 8 МБ). Docker скачивает его, выполняет команду и удаляет контейнер (`--rm`):
```bash
docker run --rm alpine:3.20 echo ok
```
Результат (строки загрузки слоёв сокращены):
```
Unable to find image 'alpine:3.20' locally
3.20: Pulling from library/alpine
25f1d6b1951a: Pull complete
Digest: sha256:d9e853e87e55526f6b2917df91a2115c36dd7c696a35be12163d44e6e2a4b6bc
Status: Downloaded newer image for alpine:3.20
ok
```
Образа не было — Docker скачал его с Docker Hub и запустил. Второй запуск пройдёт мгновенно, без загрузки.

### Шаг 2. Внутри — другая система
Сервер у нас — Ubuntu. Посмотрим, что за система внутри контейнера:
```bash
docker run --rm alpine:3 cat /etc/os-release
```
Результат:
```
NAME="Alpine Linux"
ID=alpine
VERSION_ID=3.24.3
PRETTY_NAME="Alpine Linux v3.24"
HOME_URL="https://alpinelinux.org/"
BUG_REPORT_URL="https://gitlab.alpinelinux.org/alpine/aports/-/issues"
```
Внутри — файлы Alpine Linux, хотя ядро то же, что у Ubuntu. Программе в контейнере всё равно, на какой системе стоит Docker.

### Шаг 3. Одна версия Python везде
На сервере может стоять какой угодно Python. Внутри образа — ровно тот, что в его теге:
```bash
docker run --rm python:3.12-slim python --version
```
Результат:
```
Python 3.12.16
```
Эта команда даст тот же Python 3.12 у коллеги на macOS и на сервере с Ubuntu 22.04 — без `pyenv` и установки пакетов (курс Linux, раздел 4).

## Частые ошибки
- **«Контейнер — это лёгкая виртуальная машина».** Нет своего ядра: контейнер — процесс хоста с изоляцией. Отсюда и скорость, и ограничения (Linux-контейнер на Windows-ядре сам по себе не запустится).
- **Путать образ и контейнер.** `docker rmi` удаляет образ, `docker rm` — контейнер. Изменения внутри контейнера образ не меняют.
- **Хранить данные «в контейнере».** Слой изменений удаляется вместе с контейнером — база пропадёт. Данные — в томах (раздел 2).
- **Docker как замена `venv`.** В разработке Docker нужен не для изоляции пакетов (с этим справляется `venv`), а чтобы весь стек — Python, PostgreSQL, Redis, Nginx — был одинаковым у всех и на сервере.

## Итог
**Зачем**
- Программа + всё нужное для неё → одинаковый запуск на любой машине с Docker.

**Слова**
- Образ — неизменяемый шаблон; контейнер — запущенный экземпляр; реестр (Docker Hub) — хранилище образов.

**Устройство**
- Контейнер — процесс Linux с изоляцией и общим ядром, а не виртуальная машина.
- `dockerd` — демон, `docker` — клиент.

## Вопросы на собеседовании
<details><summary>Чем контейнер отличается от виртуальной машины?</summary>

Виртуальная машина эмулирует компьютер целиком и запускает своё ядро ОС; контейнер — процесс на ядре хоста, которому ядро показывает изолированную файловую систему, процессы и сеть (namespaces) и ограничивает ресурсы (cgroups). Поэтому контейнеры стартуют за доли секунды и занимают меньше места, но изоляция слабее: ядро общее.
</details>

<details><summary>Чем образ отличается от контейнера?</summary>

Образ — неизменяемый шаблон из слоёв файловой системы и метаданных (команда запуска, переменные, порты). Контейнер — запущенный экземпляр образа с собственным тонким слоем для изменений. Из одного образа можно запустить много контейнеров; удаление контейнера не трогает образ.
</details>

<details><summary>Какую проблему решает Docker?</summary>

Разницу окружений: у разработчиков и на сервере разные версии языка, базы, системных библиотек. Docker фиксирует окружение в образе, и приложение запускается одинаково везде. Заодно упрощается деплой: на сервер доставляют готовый образ, а не устанавливают зависимости руками.
</details>
