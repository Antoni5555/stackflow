## Теория
Магазин полгода работал на `postgres` без тега. Однажды сервер перезапустили, Docker скачал свежий образ — а там новая мажорная версия PostgreSQL, которая не читает старые файлы базы. Сайт лёг. Чтобы такого не было, нужно понимать, как называются образы и что значит тег.

**Имя образа** — `[реестр/][владелец/]репозиторий[:тег]`:
- `postgres:16` — официальный образ из Docker Hub (`docker.io/library/postgres:16`);
- `ghcr.io/shop/web:1.4.2` — образ магазина в реестре GitHub;
- **тег** — версия или вариант: `16`, `16.4`, `16-alpine`, `3.12-slim`. Без тега Docker подставляет **`latest`**.

`latest` — не «самая новая стабильная», а просто тег по умолчанию, который владелец образа передвигает куда хочет. Сегодня `postgres:latest` — 17, завтра — 18. На сервере теги **фиксируют**: `postgres:16` (обновления внутри 16-й версии) или точнее `postgres:16.4`. Самое строгое — **digest** (`postgres@sha256:…`): ссылка на одно конкретное содержимое, которое не изменится никогда.

**Варианты** одного образа:
- полный (`python:3.12`) — Debian со множеством пакетов для сборки: компиляторы, заголовки библиотек;
- `slim` (`python:3.12-slim`) — Debian без лишнего, в разы меньше;
- `alpine` (`nginx:1.27-alpine`) — на Alpine Linux, самый маленький. Для Python осторожно: другая библиотека C (musl), многие пакеты придётся собирать из исходников.

Команды:
- **`docker pull образ`** — скачать (`run` делает это сам, если образа нет);
- **`docker images`** (или `docker image ls`) — локальные образы;
- **`docker tag источник новое_имя`** — дать образу ещё одно имя (копии не создаётся);
- **`docker rmi образ`** — удалить имя образа, а если имён больше нет — сам образ. Образ, из которого создан контейнер (даже остановленный), удалить нельзя.

Образ состоит из **слоёв** — по слою на шаг сборки. Одинаковые слои у разных образов хранятся один раз: `python:3.12` и `python:3.12-slim` используют общую основу Debian. Как появляются слои — раздел 3.

**Таблица 1.** Теги.

| Как писать | Что получите | Где использовать |
|---|---|---|
| `postgres` (= `postgres:latest`) | что угодно, сегодня одно, завтра другое | нигде, кроме экспериментов |
| `postgres:16` | последняя 16.x | разработка и сервер: исправления без смены мажорной версии |
| `postgres:16.4` | ровно 16.4 | сервер, где важна точная воспроизводимость |
| `postgres@sha256:…` | конкретное содержимое навсегда | CI и строгие окружения |
| `python:3.12-slim` | вариант без инструментов сборки | основа образов Django |

**Таблица 2.** Команды образов.

| Задача | Команда |
|---|---|
| скачать | `docker pull python:3.12-slim` |
| список | `docker images` |
| только одного репозитория | `docker images python` |
| ещё одно имя | `docker tag python:3.12-slim shop-python:base` |
| удалить | `docker rmi shop-python:base` |

## На практике
Задача: скачать базовый образ для Django, сравнить варианты по размеру и разобраться, когда образ нельзя удалить. Команды выполнены на Ubuntu 24.04 с Docker Engine 29.

### Шаг 1. Скачать два варианта Python
Сначала полный образ:
```bash
docker pull python:3.12
```
Результат (строки загрузки слоёв сокращены):
```
3.12: Pulling from library/python
685e2037ccfc: Pull complete
411d2dc8717d: Pull complete
…
Digest: sha256:5411fa1b302c43f510324381162b5f5d0d93b9ee2af538f09d944f0d290ee3cb
Status: Downloaded newer image for python:3.12
docker.io/library/python:3.12
```
Образ скачивается слоями; `Digest` — уникальный отпечаток содержимого. Последняя строка — полное имя: Docker Hub, официальная библиотека, тег `3.12`. Так же скачиваем `python:3.12-slim`.

### Шаг 2. Сравнить размеры
Локальные образы репозитория `python`:
```bash
docker images python
```
Результат:
```
IMAGE              ID             DISK USAGE   CONTENT SIZE   EXTRA
python:3.12        5411fa1b302c       1.62GB          430MB        
python:3.12-slim   5e2bdb1b0d54        179MB         45.5MB        
```
Полный образ на диске — 1,62 ГБ, `slim` — 179 МБ: в девять раз меньше, а Python тот же — 3.12. `CONTENT SIZE` — сколько скачивается по сети (в сжатом виде). В Docker до 29-й версии колонки другие: `REPOSITORY`, `TAG`, `IMAGE ID`, `CREATED`, `SIZE`.

### Шаг 3. Ещё одно имя
Дадим образу имя магазина:
```bash
docker tag python:3.12-slim shop-python:prod
docker images shop-python
```
Результат:
```
IMAGE              ID             DISK USAGE   CONTENT SIZE   EXTRA
shop-python:prod   5e2bdb1b0d54        179MB         45.5MB        
```
ID тот же — это не копия, а второе имя того же образа. Место на диске не удвоилось.

### Шаг 4. Образ занят контейнером
Запускаем контейнер из образа и пробуем удалить имена:
```bash
docker run -d --name shop-sleep python:3.12-slim sleep 300
docker rmi python:3.12-slim
docker rmi shop-python:prod
```
Результат:
```
5987dc07e61367d9de4a5ecb5d0dbf7d1545abaaa05e154094e6ea02d5c47b96
Untagged: python:3.12-slim
Error response from daemon: conflict: unable to delete shop-python:prod (must be forced) - container 5987dc07e613 is using its referenced image 5e2bdb1b0d54
```
Первое имя убралось (`Untagged`): у образа оставалось второе. Последнее имя Docker не отдаёт — из образа создан контейнер. Сначала `docker rm -f shop-sleep`, потом `rmi`.

### Шаг 5. Версия внутри тега
Внутри тега `3.12` — конкретная версия исправлений:
```bash
docker run --rm python:3.12-slim python --version
```
Результат:
```
Python 3.12.16
```
Тег `3.12` со временем будет указывать на 3.12.17, 3.12.18 — с исправлениями безопасности, но без смены мажорной версии. Это обычно то, что нужно.

## Частые ошибки
- **Образ без тега на сервере.** `postgres` = `postgres:latest`: после очередного `pull` — другая мажорная версия и несовместимые файлы базы. Всегда фиксируйте тег.
- **«latest — значит свежий».** Это просто тег по умолчанию; локальный `latest` может быть годовалым, если вы давно не делали `pull`.
- **Полный образ «на всякий случай».** 1,6 ГБ вместо 180 МБ: дольше загрузка на сервер, больше места и уязвимостей. Для Django обычно хватает `slim`.
- **Alpine для Python-проекта.** Колёса многих пакетов собраны под glibc, а в Alpine — musl: `pip install` начинает компилировать и требует компиляторов. Начинайте со `slim`.
- **`rmi` образа с контейнером.** `conflict: unable to delete … container … is using its referenced image`. Сначала удалите контейнеры, в том числе остановленные.
- **Считать, что `tag` копирует образ.** Это второе имя того же ID. Удаление одного имени не трогает данные, пока есть другие имена.

## Итог
**Имя**
- `[реестр/][владелец/]репозиторий:тег`; без тега — `latest`.
- На сервере тег фиксируют (`16` или `16.4`), строже всего — digest.

**Варианты**
- Полный — для сборки; `slim` — основа для Django; `alpine` — самый маленький, для Python с осторожностью.

**Команды**
- `pull`, `images`, `tag` (второе имя), `rmi` (нельзя, пока есть контейнер из образа).

## Вопросы на собеседовании
<details><summary>Почему не стоит использовать тег `latest`?</summary>

Он не означает конкретную версию: владелец образа передвигает его на новые выпуски. Один и тот же `docker run image:latest` в разные дни даёт разные версии, сборки становятся невоспроизводимыми, а обновление может сломать совместимость (например, мажорная версия PostgreSQL). Используют явные теги, а для строгой воспроизводимости — digest.
</details>

<details><summary>Чем `python:3.12` отличается от `python:3.12-slim` и `python:3.12-alpine`?</summary>

Полный образ — Debian с инструментами сборки (около 1,6 ГБ). `slim` — тот же Debian и Python без лишних пакетов (около 180 МБ). `alpine` — на Alpine Linux с библиотекой musl, самый маленький, но многие Python-пакеты под него не имеют готовых колёс и собираются из исходников. Для веб-приложений обычно выбирают `slim`.
</details>

<details><summary>Что такое слои образа?</summary>

Образ состоит из неизменяемых слоёв файловой системы — по слою на шаг сборки. Слои с одинаковым содержимым хранятся и скачиваются один раз и разделяются между образами. Контейнер добавляет сверху свой слой для изменений.
</details>
