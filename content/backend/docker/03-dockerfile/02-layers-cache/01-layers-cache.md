## Теория
Разработчик поменял одну строку в шаблоне — а `docker build` снова пять минут ставит Django, psycopg, Pillow и ещё сорок пакетов. На настоящем проекте `pip install` идёт минутами, и если он повторяется при каждой правке кода, сборка становится пыткой. Причина почти всегда в порядке инструкций Dockerfile.

**Слой** — результат одной инструкции, которая меняет файлы (`RUN`, `COPY`, `ADD`). Образ — стопка слоёв (тема 1.04, `docker history`). **Кэш сборки**: перед каждым шагом Docker проверяет, не собирал ли он уже ровно такой же шаг поверх ровно такого же предыдущего слоя. Если да — берёт готовый слой (`CACHED`), не выполняя инструкцию.

Как Docker решает, что шаг «тот же»:
- `RUN` — совпадает текст команды. Docker не знает, что пакеты в интернете обновились: `RUN apt-get update` из кэша — это вчерашний список пакетов;
- `COPY` и `ADD` — совпадают **содержимое и права копируемых файлов** (контрольные суммы). Поменяли любой файл, попадающий в `COPY . .`, — шаг выполнится заново;
- **как только один шаг выполнен заново, все шаги после него тоже выполняются заново**: кэш привязан к предыдущему слою.

Отсюда главное правило: **то, что меняется редко, — выше; то, что часто, — ниже.** Для Python-проекта:
1. `COPY requirements.txt .` — только список зависимостей;
2. `RUN pip install -r requirements.txt` — пакеты ставятся, только если изменился список;
3. `COPY . .` — код, который меняется постоянно, — в самом конце.

Ещё две привычки:
- связанные команды — в один `RUN` через `&&`: `apt-get update && apt-get install -y … && rm -rf /var/lib/apt/lists/*`. Отдельный `RUN apt-get update` закэшируется и устареет, а удаление файлов **следующим** `RUN` образ не уменьшит — файлы остались в предыдущем слое;
- `--no-cache` у `docker build` — собрать всё заново, если нужен свежий результат `apt-get` или `pip` (например, для исправлений безопасности).

**Таблица 1.** Когда шаг берётся из кэша.

| Инструкция | Из кэша, если… | Заново, если… |
|---|---|---|
| `FROM` | тот же образ | новый тег или `--pull` скачал обновлённый |
| `RUN` | тот же текст и предыдущий слой из кэша | изменился текст или любой шаг выше |
| `COPY`, `ADD` | те же файлы (содержимое и права) и предыдущий слой из кэша | изменился хоть один копируемый файл или шаг выше |
| любой шаг | — | `docker build --no-cache` |

**Таблица 2.** Порядок для Python-проекта.

| Порядок | Что меняется | Как часто |
|---|---|---|
| `FROM python:3.12-slim` | версия Python | раз в месяцы |
| `RUN apt-get …` (если нужно) | системные пакеты | редко |
| `COPY requirements.txt .` + `RUN pip install …` | зависимости | раз в недели |
| `COPY . .` | код | каждый коммит |
| `CMD […]` | команда запуска | редко, но это только настройка |

## На практике
Задача: убедиться, что правка кода не переустанавливает пакеты, если `requirements.txt` копируется отдельно, и что переставленные инструкции это ломают. Проект и Dockerfile — из прошлой темы. Команды выполнены на Ubuntu 24.04 с Docker Engine 29 (имена образов в выводе заменены на учебные).

### Шаг 1. Правка кода при правильном порядке
Меняем `shop/wsgi.py` и собираем снова:
```bash
docker build -t shop-web:1.1 .
```
Результат (строки загрузки контекста и экспорта сокращены):
```
#5 [1/5] FROM docker.io/library/python:3.12-slim@sha256:5e2bdb1b0d542d5039cffb8181c65930093949194a65c365dfb1b0fe13a4fa5b
#5 DONE 0.0s

#6 [2/5] WORKDIR /app
#6 CACHED

#7 [3/5] COPY requirements.txt .
#7 CACHED

#8 [4/5] RUN pip install --no-cache-dir -r requirements.txt
#8 CACHED

#9 [5/5] COPY . .
#9 DONE 0.0s

#10 DONE 0.1s
```
`requirements.txt` не менялся — шаги до `pip install` включительно взяты из кэша. Заново скопирован только код. Вся сборка — доли секунды.

### Шаг 2. Неправильный порядок
Файл `Dockerfile.bad` — код копируется целиком до установки пакетов:
```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install --no-cache-dir -r requirements.txt
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "shop.wsgi"]
```
Собираем его один раз, снова меняем одну строку в `shop/wsgi.py` и собираем ещё раз:
```bash
docker build -f Dockerfile.bad -t shop-bad:1.1 .
```
Результат (строки загрузки контекста, предупреждения pip и экспорта сокращены):
```
#6 [2/4] WORKDIR /app
#6 CACHED

#7 [3/4] COPY . .
#7 DONE 0.1s

#8 [4/4] RUN pip install --no-cache-dir -r requirements.txt
#8 1.597 Collecting gunicorn==23.0.0 (from -r requirements.txt (line 1))
#8 1.880   Downloading gunicorn-23.0.0-py3-none-any.whl.metadata (4.4 kB)
#8 2.361 Installing collected packages: packaging, gunicorn
#8 2.503 Successfully installed gunicorn-23.0.0 packaging-26.4
#8 DONE 3.0s
```
Изменился файл из `COPY . .` — шаг выполнился заново, а за ним и `pip install`: пакеты снова скачаны, хотя список не менялся. Здесь это 3 секунды на один пакет; в настоящем магазине с Django, Pillow и psycopg — минуты на каждую правку.

## Частые ошибки
- **`COPY . .` до `pip install`.** Любая правка кода переустанавливает все зависимости. Сначала `COPY requirements.txt .` и `RUN pip install`, потом `COPY . .`.
- **`RUN apt-get update` отдельной строкой.** Закэшируется навсегда, а следующий `apt-get install` через месяц возьмёт устаревший список — `404 Not Found` или старые версии. `update` и `install` — в одном `RUN`.
- **`RUN rm` в отдельном слое.** `RUN rm -rf /var/lib/apt/lists/*` после установки образ не уменьшит: файлы остались в предыдущем слое. Удаляют в том же `RUN`, где создали.
- **Ждать обновлений от кэша.** `RUN pip install -r requirements.txt` из кэша не узнает о новой версии пакета без фиксированной версии. Фиксируйте версии в `requirements.txt` или собирайте с `--no-cache` для обновлений.
- **Изменчивое выше стабильного.** `ARG BUILD_DATE` или `COPY version.txt` в начале файла сбрасывают кэш всех шагов ниже при каждой сборке. Переменное — как можно ниже.
- **Лишние файлы в контексте.** `.git`, `venv`, `__pycache__` в `COPY . .` меняются постоянно и сбрасывают кэш шага с кодом — даже если код не менялся. Решение — следующая тема, `.dockerignore`.

## Итог
**Слои и кэш**
- Каждый `RUN`/`COPY` — слой; шаг берётся из кэша, если не изменились он сам (текст или файлы) и всё выше.
- Шаг выполнен заново — все шаги ниже тоже.

**Порядок**
- Редкое — вверх, частое — вниз: `requirements.txt` → `pip install` → `COPY . .`.

**Привычки**
- `apt-get update && install && rm …` — одним `RUN`; удалять в том же слое.
- `--no-cache` — когда нужен свежий результат `apt`/`pip`.

## Вопросы на собеседовании
<details><summary>Как работает кэш при сборке Docker-образа?</summary>

Для каждой инструкции Docker проверяет, есть ли готовый слой, собранный той же инструкцией поверх того же родительского слоя. Для `RUN` сравнивается текст команды, для `COPY`/`ADD` — контрольные суммы копируемых файлов. При совпадении слой берётся из кэша. Как только шаг выполняется заново, кэш для всех последующих шагов недействителен.
</details>

<details><summary>Почему `requirements.txt` копируют отдельно от остального кода?</summary>

Чтобы шаг `pip install` зависел только от списка зависимостей. Код меняется постоянно, а зависимости — редко. Если скопировать всё сразу, любая правка кода инвалидирует кэш и переустанавливает пакеты; при отдельном `COPY requirements.txt` + `RUN pip install` пакеты ставятся заново, только когда изменился сам список.
</details>

<details><summary>Почему `apt-get update` и `apt-get install` пишут в одном `RUN`?</summary>

Отдельный `RUN apt-get update` закэшируется, и при следующих сборках `apt-get install` будет работать с устаревшим списком пакетов — получит старые версии или ошибки 404. В одном `RUN` обновление списка выполняется вместе с установкой. Там же удаляют `/var/lib/apt/lists/*`, чтобы не тащить списки в образ.
</details>

## Глубже
Как не дать `.git`, `venv` и `.env` попасть в контекст и сбивать кэш — следующая тема. Кэш для `pip` между сборками (`RUN --mount=type=cache`) — возможность BuildKit, описана в документации Docker.
