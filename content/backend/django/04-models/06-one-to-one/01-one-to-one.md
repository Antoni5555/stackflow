## Теория
У покупателя есть учётная запись — встроенная модель Django `User` (логин, почта, пароль) — и данные, которые нужны магазину: телефон, дата рождения, адрес доставки по умолчанию. Менять `User` нельзя: это модель из `django.contrib.auth`. Поэтому заводят отдельную модель **профиля**, у которой **ровно одна** строка на пользователя. Это связь **«один к одному»** (1:1) — поле **`OneToOneField`**.

Файл `models.py` (фрагмент модели `Profile`):
```python
user = models.OneToOneField(User, on_delete=models.CASCADE)
```
По сути это `ForeignKey` с **уникальностью**: в таблице `shop_profile` колонка `user_id` с ограничением `UNIQUE` — второй профиль тому же пользователю база не даст создать (`IntegrityError`).

Доступ — в обе стороны, и обратно — **один объект**, а не менеджер:
- `profile.user` — пользователь;
- `user.profile` — профиль (имя — модель строчными, или `related_name`). Если профиля нет, обращение выбрасывает **`RelatedObjectDoesNotExist`** — подкласс `Profile.DoesNotExist` и `AttributeError`. Поэтому проверяют `hasattr(user, "profile")` или создают профиль сразу с пользователем.

Когда 1:1, а когда просто поля в той же модели: связь нужна, если основную модель менять нельзя (`User`), если данные нужны редко и не стоит их грузить каждый раз, или если у части объектов их нет вовсе. Иначе — обычные поля. Свою модель пользователя с нужными полями заводят в начале проекта (раздел «Пользователи и доступ»), но профиль 1:1 всё равно встречается во многих проектах.

## Наглядно
**Таблица 1.** Три вида связей.

| | `ForeignKey` | `OneToOneField` | `ManyToManyField` |
|---|---|---|---|
| Связь | многие к одному | один к одному | многие ко многим |
| В базе | колонка `x_id` | колонка `x_id` + `UNIQUE` | отдельная таблица-связка |
| Прямой доступ | `product.category` | `profile.user` | `product.tags.all()` |
| Обратный доступ | `category.products.all()` (менеджер) | `user.profile` (объект) | `tag.products.all()` |
| Нет связанного | пустой список | `RelatedObjectDoesNotExist` | пустой список |
| Пример | товар → категория | пользователь → профиль | товар ↔ метки |

## На практике
Задача: профиль покупателя с телефоном и датой рождения рядом со встроенной моделью `User`.

### Шаг 1. Модель
Файл `models.py`:
```python
from django.contrib.auth.models import User
from django.db import models


class Profile(models.Model):
    user = models.OneToOneField(User, on_delete=models.CASCADE)
    phone = models.CharField(max_length=20, blank=True)
    birth_date = models.DateField(null=True, blank=True)

    def __str__(self):
        return f"Профиль {self.user.username}"
```
Таблица в PostgreSQL:
```
CREATE TABLE "shop_profile" ("id" bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY, "user_id" integer NOT NULL UNIQUE, "phone" varchar(20) NOT NULL, "birth_date" date NULL);
```
`user_id` — `integer`: у встроенной `User` ключ `AutoField`, а ваш внешний ключ повторяет его тип. И главное — `UNIQUE`.

### Шаг 2. Доступ и уникальность
Файл `orm.py`:
```python
anna = User.objects.create_user("anna", "anna@shop.example", "x")
Profile.objects.create(user=anna, phone="+79001112233")
print(anna.profile.phone)
boris = User.objects.create_user("boris", "boris@shop.example", "x")
print(hasattr(boris, "profile"))
Profile.objects.create(user=anna)
```
Результат:
```
+79001112233
False
django.db.utils.IntegrityError: UNIQUE constraint failed: shop_profile.user_id
```
`anna.profile` — объект профиля, а не список. У Бориса профиля нет — `hasattr` вернул `False`. Второй профиль Анны база не приняла.

### Шаг 3. Профиля нет
Обращение `boris.profile` без проверки:
```
django.contrib.auth.models.User.profile.RelatedObjectDoesNotExist: User has no profile.
```
На странице профиля это ошибка 500. Варианты: проверить `hasattr(user, "profile")`, получить профиль через `Profile.objects.get_or_create(user=user)` или создавать профиль сразу при регистрации.

## Частые ошибки
- **`ForeignKey` вместо `OneToOneField`.** Ничто не мешает создать пользователю два профиля, а обратная связь — `user.profile_set.all()` вместо `user.profile`.
- **`user.profile` без проверки.** У пользователей, созданных до появления профилей (или через `createsuperuser`), профиля нет — `RelatedObjectDoesNotExist`.
- **Профиль ради пары полей, которые нужны всегда.** Каждое обращение — лишний запрос. Если поля нужны на каждой странице, место им в основной модели (своей модели пользователя).
- **Ссылаться на `User` напрямую в большом проекте.** В модели пишут `settings.AUTH_USER_MODEL`, а в коде — `get_user_model()`: так связь не сломается при переходе на свою модель пользователя.

## Итог
**OneToOneField**
- `ForeignKey` + `UNIQUE`: ровно один связанный объект.
- `profile.user`, `user.profile` — оба объекты; нет профиля — `RelatedObjectDoesNotExist`.

**Когда**
- Расширить модель, которую менять нельзя (`User`), или вынести редкие данные.

## Вопросы на собеседовании
<details><summary>Чем `OneToOneField` отличается от `ForeignKey(unique=True)`?</summary>

В базе — одинаково: колонка с внешним ключом и `UNIQUE`. Разница в обратной связи: у `OneToOneField` это один объект (`user.profile`), у `ForeignKey(unique=True)` — менеджер (`user.profile_set.get()`), и Django предупреждает: `fields.W342 Setting unique=True on a ForeignKey has the same effect as using a OneToOneField.`
</details>

<details><summary>Как расширить встроенную модель `User`?</summary>

Два пути. Профиль — отдельная модель с `OneToOneField` на пользователя; подходит, если проект уже работает. Своя модель пользователя (`AbstractUser`/`AbstractBaseUser`) и `AUTH_USER_MODEL` — лучше задать в самом начале проекта: поля лежат в одной таблице, без лишних запросов.
</details>

<details><summary>Что будет, если обратиться к `user.profile`, когда профиля нет?</summary>

Исключение `RelatedObjectDoesNotExist` — наследник `Profile.DoesNotExist` и `AttributeError`. Его ловят `try/except Profile.DoesNotExist`, проверяют `hasattr(user, "profile")` или используют `Profile.objects.get_or_create(user=user)`.
</details>
