## Теория
Обычный запрос загружает все колонки и собирает из каждой строки объект модели. Для страницы товара это правильно. Но для рассылки нужны только почты, для выпадающего списка — пары «id, название», для выгрузки — несколько колонок из ста тысяч строк. Тянуть описания и собирать сто тысяч объектов незачем.
- **`values("name", "price")`** — QuerySet **словарей** `{"name": …, "price": …}` только с этими колонками; без аргументов — все поля словарём;
- **`values_list("name", "stock")`** — QuerySet **кортежей**; с одним полем и **`flat=True`** — просто значения: `["aster-14", …]`;
- **`only("name")`** — объекты модели, но загружены только перечисленные поля (и `pk`); **`defer("description")`** — наоборот, все, кроме перечисленных.

Через связь тоже можно: `values("name", "category__name")` — с `JOIN`.

Главная ловушка `only`/`defer`: объект выглядит обычным, но обращение к незагруженному полю тихо делает **отдельный запрос** — на каждый объект. `only("name")` и вывод цены в цикле по сотне товаров — сотня лишних запросов. Поэтому `only`/`defer` берут, когда точно знают, какие поля нужны, а для «данных без объектов» — `values`/`values_list`.

Объект из `values()` — это словарь: у него нет методов модели, `__str__` и связей. Это ответ «что лежит в колонках», а не объект товара.

## Наглядно
**Таблица 1.** Способы выбрать поля.

| Метод | Каждый элемент | SQL | Когда |
|---|---|---|---|
| (обычный запрос) | объект модели, все поля | `SELECT` всех колонок | страница объекта, логика |
| `values("name", "price")` | `{"name": …, "price": …}` | только `name`, `price` | данные для JSON, отчёты |
| `values_list("name", "stock")` | `("…", 5)` | только эти колонки | пары для списков |
| `values_list("slug", flat=True)` | `"aster-14"` | одна колонка | список значений |
| `only("name")` | объект, загружено `id` и `name` | `id`, `name` | объекты, но без тяжёлых полей |
| `defer("description")` | объект без `description` | все, кроме `description` | скрыть тяжёлое поле |

## На практике
Задача: данные для JSON-ответа каталога, список slug для карты сайта и посмотреть, что `only` делает с незагруженным полем.

### Шаг 1. values и values_list
Файл `orm.py`:
```python
print(Product.objects.filter(is_active=True).values("name", "price")[:2])
print(Product.objects.values_list("slug", flat=True)[:3])
print(Product.objects.values_list("name", "stock")[:2])
```
Результат:
```
<QuerySet [{'name': 'Ноутбук Aster 14', 'price': Decimal('64990.00')}, {'name': 'Ноутбук Nimbus Air', 'price': Decimal('54990.00')}]>
<QuerySet ['aster-14', 'gaming-mouse', 'mouse-pad']>
<QuerySet [('Ноутбук Aster 14', 5), ('Ноутбук Nimbus Air', 0)]>
```
SQL:
```
SELECT "shop_product"."name" AS "name", "shop_product"."price" AS "price" FROM "shop_product" WHERE "shop_product"."is_active" LIMIT 2
SELECT "shop_product"."slug" AS "slug" FROM "shop_product" LIMIT 3
SELECT "shop_product"."name" AS "name", "shop_product"."stock" AS "stock" FROM "shop_product" LIMIT 2
```
Только нужные колонки. Обратите внимание на slug: без `order_by` SQLite вернул их по алфавиту — прочитал по уникальному индексу slug. Это случайность реализации, а не гарантия: порядок задают явно.

### Шаг 2. only и лишний запрос
Файл `orm.py`:
```python
p = Product.objects.only("name").get(slug="aster-14")
print(p.name)
print(p.price)
```
Результат:
```
Ноутбук Aster 14
64990.00
```
SQL:
```
SELECT "shop_product"."id", "shop_product"."name" FROM "shop_product" WHERE "shop_product"."slug" = 'aster-14' LIMIT 21
SELECT "shop_product"."id", "shop_product"."price" FROM "shop_product" WHERE "shop_product"."id" = 1 LIMIT 21
```
Цена не была загружена, и Django молча догрузил её вторым запросом. В цикле по товарам это запрос на каждый товар.

## Частые ошибки
- **`only()` и обращение к другим полям.** Каждое незагруженное поле — отдельный запрос на объект. Перечислите все поля, которые использует код и шаблон.
- **Методы модели у результата `values()`.** У словаря нет `get_absolute_url`, `__str__` и связей: `{{ product.category.name }}` в шаблоне выведет пустоту.
- **`values_list("slug")` без `flat=True`.** Получится список кортежей из одного элемента `[("aster-14",), …]`.
- **`flat=True` с несколькими полями.** `TypeError: 'flat' is not valid when values_list is called with more than one field.`
- **Ранняя оптимизация.** `only` по всему проекту «на всякий случай» усложняет код и порождает догрузки. Начинают с обычных запросов и меряют число SQL.

## Итог
**Данные без объектов**
- `values(...)` — словари, `values_list(...)` — кортежи, `values_list("поле", flat=True)` — значения.
- Только нужные колонки, можно через связь (`category__name`).

**Объекты без части полей**
- `only(...)` / `defer(...)`; незагруженное поле догружается отдельным запросом на объект.

## Вопросы на собеседовании
<details><summary>Чем `values()` отличается от `values_list()`?</summary>

Оба выбирают только указанные колонки и не создают объекты моделей. `values()` возвращает словари с именами полей, `values_list()` — кортежи; с одним полем и `flat=True` — сами значения. Удобны для отчётов, выгрузок, JSON и подзапросов.
</details>

<details><summary>Чем опасны `only()` и `defer()`?</summary>

Объекты выглядят полными, но незагруженные поля догружаются при первом обращении — отдельным запросом на каждый объект. Если шаблон или код использует такое поле в цикле, получается N+1. Список полей нужно держать в соответствии с тем, что реально используется.
</details>

<details><summary>Когда выбирать `values_list(flat=True)`?</summary>

Когда нужен список значений одной колонки: почты для рассылки, id для фильтра `__in`, slug для карты сайта. Это дешевле объектов. Если QuerySet передаётся в `__in` другого запроса, Django сделает из него подзапрос — без загрузки значений в Python.
</details>
