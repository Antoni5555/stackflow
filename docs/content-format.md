## 1. Контекст: backend интернет-магазина
Во всех курсах направления Backend задачи взяты из работы backend-разработчика интернет-магазина: «менеджер просит выгрузку», «тимлид просит исправить», «упал сервер». Абстрактных примеров (`foo/bar`, котики, `a = 5`) нет.

**Магазин — предметная область, а не собираемый проект.** Каждая тема и задача самостоятельна, итоговой версии магазина нет.

- Сущности и поля берём только из [shop-schema.md](shop-schema.md). Нужно новое поле — сначала меняем схему.
- В Python товар — `dict` или класс с ключами из таблицы `products`; в Linux лог — запросы к страницам этих товаров и т. д.
- Деньги — `Decimal` (Python) и `numeric` (SQL), никогда не `float`.

**Таблица 1.** Чем ученик занят в каждом курсе.

| Шаг | Курс | Чем занят ученик | С чем работает |
|---|---|---|---|

## 2. Читатель и сложность
- **Читатель** — новичок в теме, но не в компьютерах: знает, что такое сайт, сервер, форма, URL, умеет гуглить. Термины не разжёвываем. Но и не усложняем: в базовых курсах — только то, что нужно на этом шаге; «как устроено» — в блок «Глубже» и в «Python под капотом».
- **Разделы** курса имеют уровень ●○○ основы → ●●○ применение → ●●● продвинутое и идут от простого к сложному.
- **Без пробелов:** тема опирается только на пройденное — выше в своём курсе или в курсах с меньшим шагом.
- Первые разделы — уроки на 5–8 минут; последние — до 13 минут.

## 3. Структура папок
```
content/
  backend/                          # направление
    _track.yaml                     # title, description, order
    _shared/schema.sql              # учебная БД «магазин»
    python/                         # курс
      _course.yaml                  # title, description, engine, kind, order (шаг 10)
      01-first-steps/               # раздел: NN-slug
        _section.yaml               # title, level (1–3)
        02-variables-and-types/     # тема: NN-slug
          _topic.yaml               # title
          01-variables-and-types.md # урок
          02-form-quantity.yaml     # задачи
          _practice.yaml            # задачник темы (тренажёр)
          img/names-to-values.svg   # рисунки урока
  _plan/                            # программы курсов (рабочие документы)
  _tools/check_tasks.py             # проверка эталонов задач
```
`NN` задаёт порядок. Slug — латиница, kebab-case; после публикации не меняется (от него зависят URL и прогресс).

`_course.yaml` → `engine`: `python`, `sql`, `django`, `linux`, `git` (терминал Linux + Git, `venv`, `pip`), `html` или `null` (курс без тренажёра — только задачи `quiz`/`fix`).

`_course.yaml` → `kind`: `main` (по умолчанию, если поля нет) — курс основного пути, на карточке «Шаг N»; `module` — дополнительный модуль («Python под капотом», «Git в команде»): без «Шаг N», в каталоге — отдельным блоком «Дополнительные модули», на главной — строкой под картой пути. `order` у модуля задаёт порядок внутри блока модулей.

`_course.yaml` заводится сразу для **всех курсов этапа 1**, даже если тем ещё нет: курс без опубликованных тем показывается в каталоге карточкой «скоро». Так каталог с первого дня показывает весь путь обучения. Slug курса после создания не меняется.

## 4. Урок
**Тема = 1 урок + 2–5 задач.** Урок — Markdown с front matter:
```yaml
---
title: Переменные и типы данных
type: lesson
level: 1            # уровень раздела
reading_time: 8     # минуты
---
```

**Заголовки H2 одинаковые во всех уроках**, чтобы читатель знал, какой блок его ждёт:

**Таблица 2.** Блоки урока по порядку.

| Заголовок | Что в блоке |
|---|---|
| `## Теория` | 1–2 абзаца: что это, зачем, главная идея; кода нет или почти нет |
| `## Наглядно` | вся тема одним взглядом: таблица и/или рисунок |
| `## На практике` | одна рабочая ситуация из магазина и разбор по шагам: `### Шаг 1. <глагол…>` |
| `## Частые ошибки` | ошибка → почему → как правильно |
| `## Итог` | подробный конспект: 6–10 пунктов в смысловых группах (`**Группа**` + список) с мини-примерами |
| `## Вопросы на собеседовании` | 3–5 вопросов, ответы в `<details>` |
| `## Глубже` | только в базовом Python и только если есть связанная тема в «Python под капотом» |
| `## Связанные темы` | в «Python под капотом»: ссылка обратно на базу |

**Подписи — у каждого блока:**
- таблица: `**Таблица N.** Что в таблице и зачем.`;
- рисунок: `**Рисунок N.** Что показывает, на что смотреть.`;
- код: одно предложение перед ним, заканчивается двоеточием;
- вывод программы: перед ним «Результат:».

Нумерация таблиц и рисунков — сквозная в пределах урока.

**Рисунки:**
- только SVG в `img/` рядом с уроком: `![Рисунок 1. …](img/<имя>.svg)`; псевдографика в Markdown запрещена;
- цвета — переменные темы сайта с запасным цветом светлой темы: `fill:#ffffff;fill:var(--surface,#ffffff)`; шрифты — `var(--font-main)`, `var(--font-code)`;
- в `<title>` — описание рисунка; ширина до 900 px; текст не мельче 12 px;
- сайт вставляет SVG в страницу inline — тогда рисунок меняет цвета вместе с темой. Поэтому стили рисунка не должны задевать страницу: все классы — с префиксом `fig-`, корневой `<svg>` — класс `fig`, общие селекторы — только внутри `.fig`. `id` внутри SVG загрузчик делает уникальными сам;
- рисунки рисуются кодом: стиль и примитивы — `content/_tools/svgkit.py`, все рисунки — `content/_tools/figures.py` (`python3 content/_tools/figures.py` пересобирает файлы). Вручную SVG не правим.

**Файлы в уроках:** если подпись перед блоком кода имеет вид «Файл `pricing.py`:» — слово «Файл» и имя в обратных кавычках, блок — это содержимое файла: проверка записывает его в рабочую папку, а следующие блоки могут его импортировать или читать. Примеры урока выполняются как одна программа ученика по правилам раздела «Как выполняются тесты».

**Правила текста:** начинаем с «зачем»; каждое понятие — на примере с результатом; сравнения — таблицей; актуальные версии (Python 3.12, PostgreSQL 16, Django 5.x); весь код реально запускается.

**Воспроизводимость:** вывод примеров и задач не должен зависеть от случайного хеша строк (`PYTHONHASHSEED`): не печатаем множества строк (только `sorted(...)`), не строим примеры на совпадении ячеек словаря для строковых ключей — для таких демонстраций берём числа. Иначе ответ «предскажи вывод» или блок «Результат:» будет верен не в каждом запуске. Задачи на сайте выполняются с `PYTHONHASHSEED=0`, но Python в браузере (Pyodide) **32-битный**: конкретные значения `hash()` (кроме маленьких целых), `id()` и `sys.getsizeof()` там другие, чем в обычном Python. В ответах `predict` и в «Результат:» таких значений не печатаем — только сравнения (`hash(a) == hash(b)`, `a is b`, `size_a < size_b`).

## 5. Задачи
**Задачи — подводные камни, а не тренировка.** Тренируется ученик сам, в песочнице. Каждая задача ловит **один подводный камень** — то, что легко упустить и на чём ошибаются в работе и на собеседовании. Задачи не повторяют примеры урока; если задачу нельзя сформулировать через подводный камень, её не делаем.

- 2–5 задач на тему, у каждой `pitfall` — одна фраза: какой камень ловит.
- `difficulty`: 1 — лёгкая, 2 — средняя, 3 — сложная.
- 1–3 подсказки (`hints`): от намёка к почти готовому решению.
- `explanation` объясняет, почему решение работает, а не пересказывает код.

**Таблица 3.** Типы задач.

| Тип | Где | Проверка |
|---|---|---|
| `exercise` | базовые курсы | тесты; у каждого теста своё сообщение `fail` — подсказка, какой камень не учтён |
| `predict` | «Python под капотом» | тренажёр запускает `code` и сравнивает вывод с ответом ученика |
| `quiz` | темы без живого запуска | выбор одного или нескольких ответов, расстановка шагов по порядку |
| `fix` | конфиги и код без движка | найти и исправить ошибку в файлах; проверка по правилам (регулярные выражения) |
| `exercise` + `check.type: dom` | «HTML, CSS и основы веба» | ученик правит файлы страницы; правила проверяют готовую страницу в браузере: элементы, атрибуты, текст, вычисленные стили |

### exercise (Python)
```yaml
title: Тарифы доставки
type: exercise
difficulty: 2
pitfall: В цепочке elif срабатывает первая подходящая ветка — порядок важен.
statement: |
  Условие. Что дано, что нужно получить (имена переменных, формат вывода).
inputs: |               # необязательно: входные данные задачи — код Python
  total = 2500
starter_code: |
  ...
check:
  type: tests
  tests:
    - code: assert run(total=500)["delivery"] == 399
      fail: Сообщение-подсказка, если тест не прошёл.
solution: |
  ...
hints: [...]
explanation: |
  ...
```

**Как выполняются тесты:**
1. Сначала выполняется `inputs` — короткий код, задающий входные данные (`total = 2500`, `price = Decimal("999")`), затем код ученика в том же пространстве имён. Код ученика **не присваивает** входные переменные — их значения приходят снаружи (в песочнице ученик видит `inputs` как блок «Входные данные»).
2. Тесты выполняются в пространстве имён этого запуска. Кроме переменных ученика им доступны:
   - `output` — всё, что программа вывела в stdout **и stderr** вместе, как в терминале (`print` и сообщения `logging`);
   - `source` — текст кода ученика;
   - `run(**значения)` — запустить код ученика заново: выполняется `inputs`, переданные значения подменяют входные (`run(total=500)`), затем код ученика. Возвращает пространство имён, где есть и `output`.
3. Код ученика выполняется как главный модуль: `__name__ == "__main__"`.
4. Каждый запуск — в **новой пустой рабочей папке**: она текущая и первая в `sys.path`, после запуска удаляется. Файлы для задачи создают в `inputs` **относительными путями** (`Path("orders.csv").write_text(...)`); свой модуль, созданный в `inputs`, импортируется обычным `import`. Тесты выполняются в папке основного запуска — им видны файлы, которые записала программа (`Path("report.txt").read_text()`). Каждый `run()` — в своей пустой папке.
5. Настройки `logging` сбрасываются перед каждым запуском — `logging.basicConfig()` работает без `force=True`.
6. `zoneinfo` доступен: тренажёр подгружает базу часовых поясов, если код её использует (`ZoneInfo("Europe/Moscow")`).
7. Тайм-аут выполнения — 2 секунды: бесконечный цикл засчитывается как непройденный тест с сообщением «Программа не завершилась».
8. Глубина рекурсии — около 300 вызовов (в обычном Python — 1000): в браузере стек меньше. Задачи и примеры не должны требовать рекурсии глубже; бесконечная рекурсия даёт обычный `RecursionError`.

Тесты по возможности проверяют несколько входных данных через `run()` — так нельзя «подогнать» ответ под один случай.

### predict
```yaml
title: Какой ключ останется
type: predict
difficulty: 2
pitfall: Равные значения разных типов — один ключ словаря.
statement: |
  Что выведет код?
code: |
  ...
answer: |                # точный вывод; проверяется запуском code
  ...
explanation: |
  ...
```
- Сайт сравнивает вывод без пробелов в конце строк и без пустых строк в конце.
- Если `code` падает с необработанной ошибкой, к выводу добавляется traceback — ученику пришлось бы угадывать его построчно. Поэтому ошибки в `predict` ловим `try/except` и печатаем `print(f"{type(e).__name__}: {e}")`.

### exercise (SQL)
```yaml
title: Покупатели без заказов
type: exercise
difficulty: 2
pitfall: INNER JOIN отбрасывает строки без пары.
statement: |
  Выведите `id` и `email` пользователей без заказов. Отсортируйте по `id`.

  order_matters: true

  ...
```
В условии всегда сказано, какие колонки и в каком порядке вывести и нужна ли сортировка — чтобы проверка была однозначной.

Формат многофайловых задач (Django: `models.py`, `views.py`, `urls.py`, шаблон) — ⏳ на этапе 5 разработки, вместе с тренажёром Django.

### quiz
```yaml
title: Код ответа «товар закончился»
type: quiz
kind: single             # single — один ответ, multiple — несколько, order — расставить по порядку
difficulty: 1
pitfall: 404 — «нет такого ресурса», а не «действие невозможно в текущем состоянии».
statement: |
  Покупатель оформляет заказ, а товар только что закончился. Какой код ответа вернуть из API?
options:
  - 200 OK
  - 404 Not Found
  - 409 Conflict
  - 500 Internal Server Error
answer: [2]              # индексы options с нуля
explanation: |
  ...
```
- `single` — в `answer` ровно один индекс; `multiple` — один или больше, ученик должен отметить все и только их;
- `order` — `answer` содержит **все** индексы `options` в правильном порядке; в YAML варианты можно писать в любом порядке, на сайте они перемешиваются;
- `hints` — как у `exercise`, по желанию.

### fix
```yaml
title: Фото товара не загружается
type: fix
difficulty: 2
pitfall: Nginx по умолчанию принимает тело запроса до 1 МБ — больше даёт 413.
statement: |
  Менеджер загружает фото товара на 5 МБ и получает «413 Request Entity Too Large».
  Исправьте конфиг так, чтобы принимались файлы до 10 МБ.
files:                   # файлы, которые видит и правит ученик: имя → исходный текст
  nginx.conf: |
    server {
        listen 80;
        location / {
            proxy_pass http://web:8000;
        }
    }
check:
  type: rules
  rules:
    - must_match: '^\s*client_max_body_size\s+10[mM];'
      fail: Ограничение на размер тела запроса задаётся директивой client_max_body_size.
    - must_not_match: '^\s*client_max_body_size\s+0;'
      fail: "0 снимает ограничение совсем — так любой может загрузить файл любого размера."
solution:                # исправленные файлы: эталон для проверки правил и показа после решения
  nginx.conf: |
    server {
        listen 80;
        client_max_body_size 10m;
        location / {
            proxy_pass http://web:8000;
        }
    }
hints: [...]
explanation: |
  ...
```
- правило — `must_match` (шаблон обязан найтись) или `must_not_match` (не должен найтись) + `fail`;
- `file:` в правиле — какой файл проверять; можно не писать, если файл один;
- шаблон ищется в любом месте файла, `^` и `$` — границы строк. Пишем регулярные выражения, одинаково работающие в Python и JavaScript: без `(?P<имя>)`, без флагов внутри шаблона, без `\A`/`\Z`;
- шаблон директивы или строки кода начинаем с `^\s*` — иначе засчитается и закомментированная строка (`# client_max_body_size 10m;`);
- правила проверяют смысл, а не форму: допускают лишние пробелы (`\s+`), разный регистр единиц (`[mM]`), любое место директивы в файле.

### exercise (HTML/CSS) — `check.type: dom`
Задача на вёрстку в курсе с `engine: html`. Ученик правит файлы в редакторе на вкладках, рядом — живой предпросмотр; «Проверить» прогоняет правила по готовой странице в предпросмотре.
````yaml
title: Жирная цена на карточке
type: exercise
difficulty: 1
pitfall: Стили из style.css применяются, только если файл подключён через <link> в <head>.
statement: |
  На карточке товара цена должна быть жирной и зелёной. Стили уже написаны в `style.css`, но на странице их не видно. Подключите файл стилей и допишите правило для `.price`.
files:
  index.html: |
    <!doctype html>
    <html lang="ru">
    <head>
      <meta charset="utf-8">
      <title>Кружка «Код»</title>
    </head>
    <body>
      <article class="card">
        <h2>Кружка «Код»</h2>
        <p class="price">499 ₽</p>
      </article>
    </body>
    </html>
  style.css: |
    .price {
      color: #2e7d32;
    }
check:
  type: dom
  rules:
    - must_match: '<link[^>]+href="style\.css"'
      fail: Стили не подключены — добавьте в <head> тег <link rel="stylesheet" href="style.css">.
    - selector: .card .price
      count: 1
      fail: Цена — один элемент с классом price внутри карточки.
    - selector: .price
      style:
        font-weight: "700"
        color: rgb(46, 125, 50)
      fail: Цена должна быть жирной (font-weight) и зелёной.
solution:
  index.html: |
    <!doctype html>
    <html lang="ru">
    <head>
      <meta charset="utf-8">
      <title>Кружка «Код»</title>
      <link rel="stylesheet" href="style.css">
    </head>
    <body>
      <article class="card">
        <h2>Кружка «Код»</h2>
        <p class="price">499 ₽</p>
      </article>
    </body>
    </html>
  style.css: |
    .price {
      color: #2e7d32;
      font-weight: 700;
    }
hints:
  - Файл стилей подключается в <head> тегом <link>.
  - "Жирность задаёт свойство font-weight: 700 (то же, что bold)."
explanation: |
  Браузер не ищет `style.css` сам: стили попадают на страницу, только если HTML на них ссылается.
````
- `files` — файлы, которые видит ученик (имя → текст); `index.html` обязателен, это страница предпросмотра. Стили работают, только если ученик подключил файл: `<link href="style.css">` заменяется содержимым файла.
- `solution` — те же файлы в решённом виде: эталон для проверки и показа после решения.
- Правила проверяются по порядку; ученик видит `fail` первого непройденного — поэтому сначала правила «подключено ли / есть ли элемент», потом — стили.
- **Правило по странице:** `selector` (CSS-селектор) + одна или несколько проверок:
  - `count: N` — найдено ровно N элементов; `min: N` — не меньше N; `exists: false` — ни одного (не `count: 0`);
  - без `exists: false` хотя бы один элемент обязан найтись, а `attr`, `text`, `style` должны выполняться **у каждого** найденного;
  - `attr: {имя: шаблон}` — атрибут есть и подходит под регулярное выражение (`alt: '\S'` — непустой `alt`);
  - `text: шаблон` — регулярное выражение по тексту элемента (без пробелов по краям);
  - `style: {свойство: значение}` — вычисленный стиль, **точная строка, как её отдаёт браузер**: цвета — `rgb(46, 125, 50)` (не `#2e7d32`), размеры — в `px` (`16px`, не `1rem`), жирность — `"700"` (не `bold`), `display: flex`. Значение-число пишем в кавычках;
  - `width: 375` — проверить при этой ширине предпросмотра (для `@media`); без `width` — при 1024 px, одинаково у всех учеников.
- **Правило по тексту файла** — как у `fix`: `must_match` / `must_not_match` + `fail`; `file:` по умолчанию `index.html`. Нужно для того, чего не видно на странице: подключён ли файл стилей, нет ли `style="…"` вместо класса.
- Регулярные выражения — совместимые с Python и JavaScript (те же ограничения, что у `fix`).
- `<script>` ученика не выполняется, формы не отправляются: проверяем разметку и стили, не поведение.

**Проверка эталона.** `check_tasks.py` проверяет форму правил, значения `style` (подсказывает, если цвет или размер записан не так, как отдаёт браузер) и правила по тексту для `solution`. Селекторы и стили считает только браузер, поэтому каждую задачу дополнительно прогоняем на `http://localhost:8000/dev/html-check/` (запущенный compose + `load_content`, только при `DEBUG`): **эталон проходит все правила, заготовка (`files`) хотя бы одно не проходит.**

### exercise с проверкой состояния (Linux, Git)
> Linux — утверждено (2026-11-10, симулятор готов: тренажёр `/playground/?engine=linux`). Git, `venv` и `pip` — утверждено (2026-11-10, симулятор готов: тренажёр `/playground/?engine=git`).

Эталон проверяет тест сайта в симуляторе: `solution` выполняется без ошибок и проходит все правила, нетронутый `setup` хотя бы одно правило не проходит.

```yaml
title: Резервная копия конфига
type: exercise
difficulty: 1
pitfall: cp без -r не копирует папку.
statement: |
  Скопируйте папку `/srv/shop/config` в `/srv/shop/backup/`.
setup:                       # состояние до начала
  cwd: /srv/shop
  files:                     # путь → содержимое; папки создаются сами
    /srv/shop/config/settings.ini: |
      DEBUG=False
  dirs: [/srv/shop/backup]   # пустые папки
check:
  type: state
  expect:                    # каждое правило + своё fail, как у тестов Python
    - path: /srv/shop/backup/config/settings.ini
      exists: true
      fail: Папка не скопировалась — для папок нужен cp -r.
    - path: /srv/shop/config/settings.ini
      exists: true
      fail: Исходный конфиг пропал — нужен cp, а не mv.
solution: |                  # команды по одной на строку
  cp -r config backup/
hints: [...]
explanation: |
  ...
```

**Файлы и папки в `setup`:**
- `files: {путь: текст}` — обычный файл с содержимым;
- `files: {путь: {size: 6M}}` — «тяжёлый» файл: вместо содержимого только размер (`K`, `M`, `G`) — для `find -size`, фото и бэкапов;
- у файла можно задать владельца и права: `{content: "...", owner: www-data, mode: '640'}` или `{size: 6M, owner: root}` — запись файла: текст или словарь `{content | size, owner, mode}`;
- `dirs` — пустые папки: в списке каждый элемент — путь (`/srv/shop/backup`) или путь со словарём (`/etc/nginx/sites-enabled: {owner: root, mode: '755'}`);
- у файла можно задать возраст `mtime: 10` (дней назад) — для `find -mtime`;
- по умолчанию: владелец `shop`, права файла `644`, папки `755`; папки-родители, которые `setup` создаёт сам, получают владельца ближайшей существующей папки: под `/etc` и `/var` — `root`, под `/srv` и `/home/shop` — `shop`; нужна папка с другим владельцем — пишем её в `dirs` явно; общего `setup.owner` нет — владелец задаётся у конкретного файла или папки.

**Правила Linux:** `path` + `exists: true|false`; `path` + `contains: <regex>` (содержимое файла, флаг `m`); `path` + `mode: '644'`; `path` + `owner: <пользователь>`; `path` + `link_to: <путь>` (символическая ссылка — для `ln -s`); `output_matches: <regex>` (вывод последней команды — для задач «найди и выведи»).

**Git** (движок `git` — терминал Linux + Git; все Linux-ключи `setup` и правила работают и здесь). Пути в `commits`, `tracked`, `staged` — от корня репозитория; остальные пути — абсолютные, как в Linux. Без `commits` репозитория нет (задача на `git init`), `commits: []` — репозиторий без коммитов. Правила Git смотрят в репозиторий задачи (`repo`, иначе `cwd`).

```yaml
setup:
  repo: /home/shop/shop        # где репозиторий; по умолчанию — cwd
  cwd: /home/shop/shop
  commits:                     # история, от старых к новым
    - message: Каркас магазина
      files:                   # что изменил коммит: путь → текст; null — файл удалён
        shop/settings.py: |
          DEBUG = True
    - message: Промокоды — модель
      branch: promo            # новая ветка ответвляется от from (по умолчанию main)
      from: main
      files:
        promo/models.py: |
          class Promo: ...
  head: promo                  # текущая ветка; по умолчанию main
  gitconfig:                   # ~/.gitconfig; по умолчанию Shop Developer / dev@shop.example
    user.name: Анна            # null — Git не настроен (тема про git config)
    user.email: anna@shop.example
  remote:                      # «GitHub»; без ключа — удалённого нет
    url: git@github.com:shop/shop.git
    commits: [...]             # коммиты, которых нет локально (для pull / fetch), формат тот же
    pushed: [main]             # ветки, уже отправленные на GitHub
  files:                       # незакоммиченные правки — обычные files поверх истории
    /home/shop/shop/shop/settings.py: |
      DEBUG = False
  venv:                        # готовое окружение (для freeze, uninstall)
    path: venv                 # от cwd
    packages: {django: 5.1.4}
```

**Правила Git:** `branch: <имя>` / `tag: <имя>` / `tracked: <путь>` (файл в последнем коммите текущей ветки) / `staged: <путь>` (изменение в индексе) — по умолчанию «есть», с `exists: false` — «нет»; `head: <ветка>`; `commit_in: {branch, message: <regex>}`; `commit_count: {branch, count}` (сколько коммитов в ветке — для `--amend`, `reset`, «не создал лишний коммит»); `clean: true` (нет незакоммиченных изменений; конфликт решён — `contains`/`exists` по файлу + `clean: true`); `merged: {from, into}`; `pushed: <ветка>` (на «GitHub» то же, что локально); `config: {key: user.email, value: <regex>}`; `stash_count: N`; `pip_package: {name, version}` + `venv: <путь>` (по умолчанию `venv`; без `version` — любая).

**Команды симулятора** — в `solution` и в задачах только они; нужна другая — согласовать с «Разработкой»:
- Linux: `pwd`, `cd`, `ls [-l -a]`, `cat`, `echo`, `mkdir [-p]`, `touch`, `rm [-r]`, `cp [-r]`, `mv`, `ln [-s]`, `head [-n N]`, `tail [-n N]`, `wc [-l]`, `grep [-i -n -r -c -v]`, `sort [-n -r]`, `uniq [-c]`, `cut [-d -f]`, `find [-name -type -size -mtime]`, `tar [-czf -xzf]`, `gzip`, `gunzip`, `chmod` (числом и буквами: `u+x`), `chown [-R]`, `chgrp [-R]`, `whoami`, `id`, `which`, `df [-h]`, `du [-sh]`; `--help` у всех команд; флаги можно писать вместе (`ls -la`); код выхода — `echo $?`; свой скрипт — `./script.sh` (shebang + `chmod +x`; переменные `NAME=x`, `$NAME`, аргументы `$1` — да, `if`/`for` — нет); `nano <файл>` — редактор на месте строки ввода (Ctrl+O — сохранить, Ctrl+X — выйти), в `solution` не пишется: там файлы меняем через `echo >` / `>>`; конвейер `|`, перенаправления `>`, `>>`, `2>`, `2>&1`, `/dev/null`, цепочка `&&`, `sudo`. Права проверяются: пользователь `shop` не пишет в `/etc` и чужие файлы без `sudo`. Сообщения об ошибках — на английском, как в настоящем Linux (`Permission denied`, `No such file or directory`) — в уроках и `fail` цитируем их дословно;
- Git: `init`, `config [--global] [--list]` (`user.name`, `user.email`), `status`, `add` (`.`, `-A`, пути), `rm --cached [-r]`, `commit -m [--amend] [--no-edit]`, `log [--oneline --graph --all -n N -S<текст> --grep=<текст>]`, `diff [--staged]`, `restore [--staged]`, `branch [-d -D -a]`, `switch [-c]`, `checkout <ветка>`, `merge [--abort --no-ff]`, `reset [--soft --mixed --hard] [HEAD~N]`, `revert`, `cherry-pick`, `tag`, `stash [push list pop apply drop]`, `reflog`, `blame`, `rebase [--continue --abort]` (без `-i`), `remote add`, `remote -v`, `push [-u]`, `clone`, `fetch`, `pull [--no-rebase --rebase]`. Редактора нет: `commit` без `-m` — ошибка, `merge` и `revert` берут сообщение по умолчанию. Конфликт — маркеры `<<<<<<<`, `=======`, `>>>>>>>` как в настоящем Git; в `solution` файл после конфликта пишем через `echo >`. Сообщения — на английском, как в настоящем Git. `bisect`, `rebase -i`, `ssh-keygen` — нет (теория и `quiz`);
- окружение Python (тоже движок `git`): `python3 -m venv <папка>`, `source <папка>/bin/activate`, `deactivate`, `pip install [-r файл] <пакет>[==версия]`, `pip freeze` (с `>` — в `requirements.txt`), `pip uninstall -y`, `pip list`, `sudo apt install`; `which python` после активации показывает окружение. Пакеты — из учебного списка «Разработки»; сам Python в симуляторе не выполняется (`python3 script.py` — нет).

`check_tasks.py` проверяет у таких задач структуру, шаблоны и то, что `solution` использует только команды и флаги из списка. Сам эталон в симуляторе прогоняет тест сайта: каждая строка `solution` должна завершиться с кодом 0 — `git commit` при пустом индексе или `git pull` при разошедшихся ветках без `--no-rebase` упадут.

### Задачник (`_practice.yaml`)
**Задачник — тренировка, а не подводные камни.** Задачи темы ловят ошибки и проверяются тестами; задачник даёт ученику типовые упражнения, чтобы набить руку в песочнице. Показывается в тренажёре третьей плашкой правой панели — рядом с «Заметкой» и «Программой курса»: краткое условие, ученик решает в редакторе песочницы сам, ответ скрыт до нажатия. Автопроверки и прогресса нет.

Файл `_practice.yaml` лежит в папке темы (необязательный) — список задач в порядке от простой к сложной:
````yaml
- title: Сумма корзины              # коротко, без точки

    Дан список цен товаров в корзине:
    ```python

  hint: |                           # необязательно: намёк до ответа, Markdown

  answer: |                         # решение, Markdown: код + 1–2 фразы
````

- 3–6 задач на тему, только на пройденное (правило «без пробелов»), в контексте магазина.
- Данные, которые нужны для решения, — в условии, блоком кода: ученик копирует их в редактор.
- Код условия и ответа вместе — одна программа: `check_tasks.py` выполняет блоки ```` ```python ```` по порядку и сверяет с блоками «Результат:», как в уроке.
- Полей кроме `title`, `text`, `hint`, `answer` нет.

### Проверка эталонов
`python3 content/_tools/check_tasks.py` проверяет задачи. Задачи Python (`exercise`, `predict`) выполняет **тот же `runner.py`, что и тренажёр сайта** (`src/static/js/engines/python/runner.py`), — прошедшее проверку пройдёт и у ученика:
- `exercise` (Python): эталон (`solution`) проходит все тесты, `starter_code` хотя бы один не проходит;
- `predict`: ответ совпадает с реальным выводом;
- `quiz`: индексы `answer` существуют и соответствуют `kind`;
- `exercise` с `check.type: state`: структура `setup` и правил, шаблоны, команды `solution` из списка симулятора;
- `_practice.yaml`: у каждой задачи есть `title`, `text`, `answer`; код условия и ответа выполняется и совпадает с «Результат:»;
- `exercise` с `check.type: dom`: форма правил, значения `style` в записи браузера, `solution` проходит правила по тексту; эталон и заготовка по странице — в браузере на `/dev/html-check/`;
- `fix`: все шаблоны компилируются, `solution` проходит все правила, исходные `files` хотя бы одно не проходят, а `solution`, в котором исправленные строки закомментированы, правила **не** проходит.

Вся проверка выполняется параллельно при 16 разных `PYTHONHASHSEED`; ошибка, которая есть не во всех запусках, помечается как нестабильная. `--quick` — один запуск, для черновой работы.

## 6. Связь базового Python и «Python под капотом»
Урок базы заканчивается блоком «Глубже» (1–2 предложения + ссылка на тему «Под капотом»), если связанная тема есть. Урок «Под капотом» заканчивается «Связанными темами» со ссылкой на базу.
